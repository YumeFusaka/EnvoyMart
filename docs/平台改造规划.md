# EnvoyMart 平台改造规划

> 2026-09-29 起实施。把平台从「能跑通的单项目」升级为「全栈完整 + 知识增强」的可演示系统。

## 一、定位

**EnvoyMart 是一个知识增强的智能电商平台。**

两条主线并行推进，缺一不可：

- **全栈电商**——用户、地址、商品、SKU、搜索、推荐、购物车、订单、支付、物流、售后、营销、评价、客服
- **Agent 能力**——编排、记忆、RAG、工具、MCP、护栏、可观测、成本

两条线在**知识层**交汇：知识图谱与强溯源**既是 Agent 的推理底座，也是电商自身的业务能力**——售后政策问答、商品参数问答、推荐理由解释，都是电商业务本身需要的东西，不是给 Agent 专配的附属品。一份投入，两处受益。

## 二、改造原则

1. **每批保持可运行、可演示**——前端随批次一起做，不留"最后再补前端"的坑
2. **不做假的**——真实的表结构、真实的状态机、真实的并发处理。广度上覆盖全，深度上不糊弄
3. **骨架保留，领域层重构**——微服务治理、并发控制、缓存防护、部署链路是已投入的资产，不动；商品、订单、用户等领域模型重新设计

## 四、知识层

### 4.1 知识图谱

**为什么电商需要图谱——用向量检索的盲区来论证：**

`"我买了 A，能再买 B 吗"` 是一条 **A → 属性 → 冲突规则 → B** 的四跳推理。结论**藏在关系里，不在任何一段文本里**——把整库文档喂给模型也检索不到，因为没有任何一段文本说过"A 和 B 冲突"。只有图能做这个。

| 图谱 | 节点 / 关系 | 支撑什么 |
|---|---|---|
| **商品关系图** | 商品 → 替代品 / 配件 / 搭配 / 升级款 | 关联推荐、兼容性判断 |
| **品类属性图** | 类目 → 属性 → 规格值 → 约束 | 属性推理：哪些规格组合合法、哪些互斥 |
| **售后政策图** | 政策 → 适用条件 → 例外 → 流程 | 多跳条件判定："我这种情况能退吗" |
| **用户兴趣图** | 用户 → 行为 → 商品 → 属性 → 相似用户 | 推荐的可解释依据 |

**选型**：Neo4j。理由是查询表达力（可变长路径、子图匹配）与可视化现成——知识库台可以直接复用其浏览器式展示，前端图谱面板成本大幅降低。

### 4.2 强溯源

| 回答类型 | 溯源到什么 |
|---|---|
| 售后政策 | 政策条款**原文位置** |
| 商品参数 | 商品详情 / 说明书 / 质检报告 |
| 推荐理由 | 匹配了哪些属性、依据哪条规则 |
| 订单状态 | 依据哪条事件推进 |

**链路**：

```
切片时记结构化位置（文档 + 版本 + 章节 + 页码 + 字符偏移）
  → 检索带出位置元数据
  → 证据编号 [1][2][3]
  → 生成时强制引用
  → 后置逐句校验（这句是否真的被引用的证据支撑）
  → 前端点击跳原文并高亮
```

### 4.3 零幻觉

三道闸：

1. **拒答门**——检索分数低于阈值 / 无有效证据 → 拒答，不让模型自由发挥
2. **引用覆盖**——没有引用的句子删掉或重写
3. **冲突显式呈现**——多份证据矛盾时列出冲突，不让模型自己挑一个

## 五、Agent 能力

| 能力 | 目标态 |
|---|---|
| **编排** | 图编排保留，**补质量评估循环**——评估用模型、答案参与循环，不合格可回退重做 |
| **上下文** | 会话压缩摘要、token 级预算、工具输出清洗与截断 |
| **记忆** | 三轨保留；情节记忆补时间戳与类型落库、淘汰策略从纯 FIFO 改为按价值 |
| **RAG** | 三路召回（BM25 + 向量 + 图谱子图）+ RRF 融合 + 重排 |
| **工具** | MCP 发布保留；工具输出字段按用途筛选并控制长度 |
| **护栏** | 循环预算保留；新增拒答门 |
| **可观测** | 指标扩充：幻觉率、引用准确率、拒答准确率、多跳命中率 |
| **幂等** | 对话请求带 requestId，工具调用带幂等键 |

## 六、批次计划

每批含前端，保证随时可投屏。

| 批次 | 内容 | 可演示点 |
|---|---|---|
| **0 · 地基** | 领域模型重设计、库表、认证、前端骨架 + 设计系统 | 登录进首页 |
| **1 · 商品域** | SPU/SKU/类目/属性/详情/搜索/后台商品管理 | 逛商品、搜商品 |
| **2 · 交易域** | 购物车 / 下单 / 订单状态机 / 支付 / 后台订单管理 | 完整下单到支付 |
| **3 · 履约售后** | 物流 / 售后政策引擎 / 退款流程 | 申请退货走完全程 |
| **4 · 营销评价** | 优惠券 / 活动 / 评价 / 客服工单 | 领券下单、评价 |
| **5 · 知识层** | 文档模型 / 切分 / 三路检索 / Neo4j 图谱 / 融合 / 重排 | 后台可查知识库 |
| **6 · 溯源与防幻觉** | 证据编号 / 强制引用 / 后置校验 / 拒答门 / 冲突呈现 | **点引用跳原文高亮** |
| **7 · Agent 强化** | 编排升级 / 上下文压缩 / token 预算 / 记忆修复 / MCP / 可观测 | 多轮对话 + 工具轨迹 |
| **8 · 知识可视化台** | 图谱可视化 / 溯源面板 / 评测报告 | 演示主秀 |
| **9 · 评测与部署** | 幻觉率 / 引用准确率 / 多跳命中率 + 演示环境打包 | 数据说话 |

批次 0–4 是电商主线，5–8 是知识与 Agent 主线，9 收口。5–7 可与 3–4 部分并行。

## 七、技术决策记录

| 决策 | 选择 | 理由 | 放弃的方案 |
|---|---|---|---|
| 知识图谱存储 | Neo4j | 可变长路径查询表达力强；可视化现成，前端直接受益 | MySQL 邻接表（3 跳以上难写、无可视化）；Milvus 兼做图（讲不出图的价值） |
| 前端技术栈 | 保留 Vue3 + Element Plus | 现有问题在实现简陋，不在选型；换栈是纯成本无收益 | 换 React / Next.js |
| 代码策略 | 保留仓库与骨架，重构领域层 | 微服务治理、并发控制、缓存防护、部署链路是几个月踩坑换来的资产 | 新仓库从零重写（要重踩一遍工程坑） |
| 领域方向 | 通用电商，不向垂直领域倾斜 | 需同时支撑全栈岗与 Agent 岗的多场面试；通用电商的类目里本就含食品保健，知识图谱与溯源照常覆盖 | 转成医药垂直领域（牺牲全栈完整度） |
