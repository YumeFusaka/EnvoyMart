# EnvoyMart 平台改造规划

> 2026-09-29 起实施。把平台从「能跑通的单项目」升级为「全栈完整 + 知识增强」的可演示系统。

## 一、定位

**EnvoyMart 是一个知识增强的智能电商平台。**

两条主线并行推进，缺一不可：

- **全栈电商**——用户、地址、商品、SKU、搜索、推荐、购物车、订单、支付、物流、售后、营销、评价、客服
- **Agent 能力**——编排、记忆、RAG、工具、MCP、护栏、可观测、成本

两条线在**知识层**交汇：知识图谱与强溯源**既是 Agent 的推理底座，也是电商自身的业务能力**——售后政策问答、商品参数问答、推荐理由解释，都是电商业务本身需要的东西，不是给 Agent 专配的附属品。一份投入，两处受益。

## 二、改造原则

1. **每批保持可运行、可演示**——前端随批次一起做，不留"最后再补前端"的坑
2. **不做假的**——真实的表结构、真实的状态机、真实的并发处理。广度上覆盖全，深度上不糊弄
3. **骨架保留，领域层重构**——微服务治理、并发控制、缓存防护、部署链路是已投入的资产，不动；商品、订单、用户等领域模型重新设计

## 四、知识层

### 4.1 知识图谱

**为什么电商需要图谱——用向量检索的盲区来论证：**

`"我买了 A，能再买 B 吗"` 是一条 **A → 属性 → 冲突规则 → B** 的四跳推理。结论**藏在关系里，不在任何一段文本里**——把整库文档喂给模型也检索不到，因为没有任何一段文本说过"A 和 B 冲突"。只有图能做这个。

| 图谱 | 节点 / 关系 | 支撑什么 |
|---|---|---|
| **商品关系图** | 商品 → 替代品 / 配件 / 搭配 / 升级款 | 关联推荐、兼容性判断 |
| **品类属性图** | 类目 → 属性 → 规格值 → 约束 | 属性推理：哪些规格组合合法、哪些互斥 |
| **售后政策图** | 政策 → 适用条件 → 例外 → 流程 | 多跳条件判定："我这种情况能退吗" |
| **用户兴趣图** | 用户 → 行为 → 商品 → 属性 → 相似用户 | 推荐的可解释依据 |

**选型**：Neo4j。理由是查询表达力（可变长路径、子图匹配）与可视化现成——知识库台可以直接复用其浏览器式展示，前端图谱面板成本大幅降低。

### 4.2 强溯源

| 回答类型 | 溯源到什么 |
|---|---|
| 售后政策 | 政策条款**原文位置** |
| 商品参数 | 商品详情 / 说明书 / 质检报告 |
| 推荐理由 | 匹配了哪些属性、依据哪条规则 |
| 订单状态 | 依据哪条事件推进 |

**链路**：

```
切片时记结构化位置（文档 + 版本 + 章节 + 页码 + 字符偏移）
  → 检索带出位置元数据
  → 证据编号 [1][2][3]
  → 生成时强制引用
  → 后置逐句校验（这句是否真的被引用的证据支撑）
  → 前端点击跳原文并高亮
```

### 4.3 零幻觉

三道闸：

1. **拒答门**——检索分数低于阈值 / 无有效证据 → 拒答，不让模型自由发挥
2. **引用覆盖**——没有引用的句子删掉或重写
3. **冲突显式呈现**——多份证据矛盾时列出冲突，不让模型自己挑一个

### 批次 15 的立约（2026-10-01，动工前核实过现状）

**为什么是它**：U19 说「四个工具摊开——查订单、查物流、政策问答、售后判定，都能被一个按钮或搜索框替代；**唯一替代不了的是商品推荐**（需求开放、要跨多轮收敛、要记忆参与）」——而推荐这条链路的复杂能力恰恰没做。**Agent 在本项目的立足点，就在这一条上。**

**动工前核实的现状**（待改进清单写于更早，形状已变，以本节为准）：

| 清单说的 | 现在实际是 |
|---|---|
| U3 工具签名装不下多条件 | **仍然成立**：`product_search(query, limit)`，价格/属性/否定条件无处可放 |
| U4 `matchesKeyword` 是 OR 不是 AND | **代码已不存在**。现在下游是 MySQL `like '%整串%'`（name OR subtitle）——比 OR 更粗：**整串子串匹配**，「2k 左右 拍照 512GB」整句下去命中 0 条 |
| U6 ES 建好了 Agent 没用 | **仍然成立**：`/products/search` 已有 multiMatch 加权、类目子树、品牌、价格区间**重叠**语义、排序；Agent 走的还是 `/products/recommendations` |
| U7 全表查 + 内存过滤 | **已修**（改走分页查询），但走错了那条路 |
| U8 硬编码关键词白名单 | **已删**（`extractKeywords` 整个方法不存在了） |
| U18 演示库没有手机品类 | **例子举错了域**——本项目的域是营养保健（用户定过：数据偏营养与医疗）。真问题不是「没有手机」，是**品类少到举不出一个像样的多条件场景**，且商品没有**可筛选的结构化属性** |

**改法（三层，一处判定）**：
1. **契约层**：`ProductQuery` 增 `excludeKeywords`（否定条件）与属性筛选入参；`/products/search` 落成 `bool.mustNot` 与 `bool.filter`。**判据只在这一处**——工具、搜索页、推荐共用同一条 ES 查询。
2. **工具层**：`product_search` 签名扩为 `query` + `minPrice`/`maxPrice` + `excludeKeywords` + `categoryName?`；下游从 `/products/recommendations` 改接 `/products/search`；**输出里要写出"是按哪些条件筛的"**，让模型有依据向用户复述约束，而不是只报一堆商品名。
3. **数据层**：种子库在营养保健域内补品类（睡眠、护眼、关节、运动营养等）**并给商品补可筛选属性**（如「是否含乳糖」「钙的形式」「适用人群」）——**没有可筛选的属性，多条件就只是个说法**。

**验收（每条都要有证据来源）**：
- 多条件查询端到端：一句含「价格区间 + 正向条件 + 否定条件」的话 → 返回的**每一条**都满足全部条件（逐条核对，不是抽查）；对照实验：同一句话走旧路（整串 LIKE）返回 0 条
- 否定条件真的生效：`excludeKeywords=折叠屏` 之类，返回集合与不带该条件时**严格做差**
- 与图谱联动：推荐结果里的商品若与用户提到的药物有相互作用，回答要带上风险提示（复用现有 `interaction_check`，不新造判定）
- 回归：`verify-agent-retrieval` / `verify-chat-ui` / `verify-trade-flow` 不回归
- 新脚本 `verify-recommend.mjs` 覆盖以上，并挂进 `verify-all.mjs`

**已知风险**：
- 改 `ProductQuery` 会碰 `/products/search` 的既有调用方（搜索页）——**必须跑 `verify-search-ui`**，且新增字段一律可选、缺省行为与现在逐位相同
- 种子数据是**新增**不是改写（`where not exists` 守卫已在），但新品类要同步进 ES 索引与图谱语料，否则「加了个商品但搜不到」
- 工具签名变长会让模型填错参数的概率上升——**参数一律可选**，缺失时退回原来的纯关键词行为

### 批次 16 的立约（2026-10-01，动工前核实过现状）

**为什么是它**：三档里字面 1.000、口语 0.950、**语义 0.625**——40 条语义鸿沟样本里约 15 条
一次都没召回（`docs/检索效果对照实验结果.md` §混合）。这一档的天花板不是「排序不够好」，
而是**候选池里根本没有那篇文档**：查询与文档没有共享词元，向量空间里也离得远。
重排、加权、调 topK 都救不了没进池子的东西——**只有把查询本身变得更接近文档的样子**。

**动工前核实的现状**：

| 设想 | 实际是 |
|---|---|
| 检索前已有一次模型调用可复用 | ✅ `QueryRewriter`（指代消解）已在，但它**只输出一句**，产出被当成「唯一正确的检索句」 |
| RRF 只融三路 | ✅ `HybridRetriever.rrfMerge(vector, keyword, graph)` —— 签名写死三路，扩写产生的变体无处可放 |
| 离线重放模式已存在 | ✅ `GroundingFixtures` + `GroundingEvalRunner` 就是「预录真实输出、CI 重放」，本批照此办理 |
| 评测里能测出语义增益 | ❌ `SimpleEmbeddingService` 是 `hashCode` 播种的**伪随机向量**（无任何语义），`RetrievalQualityTest` 因此只测词法路底线 —— **HyDE 的语义增益在 CI 里物理上测不出来**，只能进真实对照实验（需 key），CI 能测的是「多角度改写对词法路的增益」 |

**改法（三层，一处判定）**：

1. **扩写层**（新）：`QueryExpander` 接口 → `QueryExpansions(hypothetical, angles)`。三种实现：
   `LlmQueryExpander`（一次调用同时产出假想答案与多角度改写）、`NoopQueryExpander`（默认降级态，
   行为与改造前逐位相同）、`RecordedQueryExpander`（读预录夹具，CI 与报告页确定性重放）。
2. **融合层**：`HybridRetriever` 接受变体 —— **每一路只吃它擅长的那种变体**：
   假想答案喂向量路（它补的是词汇鸿沟），多角度改写喂词法路（它补的是表述差异），图谱路只认原句。
   全部候选池汇入同一个 RRF，**重排只做一次**（用原句）——每个变体各自重排再合并，等于让每个变体
   各自做一次「不重要的候选就丢掉」的决策，而那个决策恰恰要靠融合才能做。
3. **装配层**：`MultiQueryRetriever` 装饰器包在 retriever 上，开关 `envoymart.rag.query-expansion.enabled`。
   包在这一层而不是对话层，是因为检索有**两个入口**（Agent 主链路的 RAG 与 `KnowledgeSearchTool`
   的 ReAct 再检）——包在外面两条都自动带上，包在任一条里另一条就成了分叉。

**验收（每条都要有证据来源）**：

- **真实对照实验**（`RetrievalComparisonTest`，需 `DASHSCOPE_API_KEY`）：语义档 Hit@3 从 0.625 抬起，
  **字面档不掉**（1.000）
- **CI 防退化**（预录扩写重放）：关键词路全量 Hit@3 不低于现有门槛；另有一条「变体为空时逐位等同旧行为」
  的等价性断言
- **对照实验必须打出扩写降级次数**：扩写失败会退化成「没有扩写」，指标悄悄回到基线——
  不写出来就无法判断这轮数字可不可信（沿用重排降级统计的既有做法）
- 回归：`verify-*` 全绿
- 材料：规划文档 §8.17 + 问答解析 + 背书卡 + 简历

**已知风险**：
- **假想答案是会编的**。它跑偏时引入的是「看起来像」的噪声候选，而 RRF 是名次融合——
  跑偏路的第一名与原句路的第一名同分。先做平等融合并**用数据说话**；若语义档涨而字面档掉，
  再引入权重并说明依据，不预先拍一个系数。
- **每轮多一次模型调用 + 多一次 embedding**。这是检索前的一次性成本，换来候选池从「有」到「有对的」；
  失败一律降级回原句，代价只是回到改造前。
- 预录夹具与真实模型行为会漂移（与 `GroundingFixtures` 同一个已知问题）——夹具记录**采集时间与模型标识**，
  与数字一起展示，不冒充「现在的表现」。

**要解决的问题**：JWT 自证，签发后服务端管不着——禁用只改库的话，旧 Token 还能用满
整个 TTL（7 天）。「禁用了个寂寞」是权限系统最典型的假动作。

**机制**：Redis HASH `envoymart:auth-state`（field = userId，value = `状态|角色`），
**只存被改动过的用户**；网关每次鉴权读一次并覆盖 Token 里的角色快照。
读侧 fail-open（Redis 读不到就按 Token 放行，可用性优先），
**写侧 fail-through**（写失败必须抛，否则「禁用成功」的响应本身就是假的）。
键名与格式在 `common` 的 `AuthState` 里只留一份，写入方（auth）与读取方（gateway）共用。

```
OPEN ──→ PROCESSING ──→ RESOLVED ──→ CLOSED(终态)
  │            │            │
  └────────────┴────────────┘        RESOLVED ──→ PROCESSING（用户重开，唯一的回边）
```

- `OPEN → RESOLVED` 是允许的：有些工单不需要来回（「请帮我取消订单」），
  强行要求先回复一条只是形式主义。
- **`CLOSED` 不可重开**：超时自动关闭会制造一批 CLOSED，若还能重开，
  用户半年后回来重开一条上下文早已散尽的工单，客服手上只有一句「还是不行」。
  新问题开新工单——这是让状态机保持单向所付的最小代价。

**有意为之的不对称（两端关闭的要求不同）**：
用户自行关闭**不需要原因**，由状态区分语义（从 `RESOLVED` 关 = 确认解决，
其余 = 自行撤销，落成 `close_reason` 的两种固定措辞）；
**客服关闭原因必填**，并落一条带操作人的消息。理由：用户关自己的工单不欠谁一个解释，
而**终结别人的诉求时，对方至少要看到是谁、为什么**。

**几条不写进注释就会写错的地方**：
- **消息不驱动状态**。回复、补充说明都只落消息；状态转移只由显式动作发起
  （客服首次回复接手 / 标记解决 / 关闭 / 用户重开）。让「发消息」顺手改状态的话，
  用户补一句「谢谢」会把工单从待处理顶成处理中——而那意味着有人接手了。
- **状态转移走条件更新**（`where id = ? and status = <读到的那个>`），0 行即 409
  「工单状态已变更，请刷新后重试」，而不是把先到的结果覆盖掉。
- **重开时必须清 `resolved_at`**。留着旧值，下一轮超时任务会拿它判定，
  刚重开的工单会被当场扫走。
- **球权列 `last_reply_by`** 跟着最后一条人工消息走，`awaitingAdmin=true`
  对应「最后一条消息来自用户」——客服上班第一件事是捞自己的欠账，而不是从第一页翻到最后。
  系统消息（超时关闭的通知）**不抢球权**，否则工单会看起来在等客服处理。
- **越权返回「工单不存在」而不是「无权查看」**：后者等于确认这条工单存在，
  凭 id 遍历就能数出平台有多少工单。归属条件写在 SQL 的 `where` 里，
  而不是查出来再在内存里比。
- **关联订单必须是自己**：把用户 B 的订单号挂进用户 A 的工单，客服拿着这个线索去查，
  问的是完全不相干的人——而两个用户都不会察觉。
- 用户侧与管理侧**不共用 DTO**：管理侧要看到提交人、要能按用户与球权筛选，
  共用一个类型只会让某一侧多出几个永远为空的字段。

| 12e · 项 5 | **业务码层的重试与诚实降级**：本项目的服务间应答一律是 HTTP 200 + 体里的 `code`，于是工具里那句 `.getData()` 对「查到了 / 查不到 / 下游刚崩了一下」给出同一个 `null`，工具按最常见的那种解释——「没有找到」。改法：读/写分成两个方法（GET 可重发，POST 一律不重发——应答丢了不代表业务没生效），业务码 5xx 退避重试 150/300ms，救不回来就抛「暂时不可用」并挡住模型那句「没有」 | `DownstreamTest` 12 项；`verify-downstream-retry.mjs` **17/17**（把 product-service 停掉换成桩：场景 A 首次回 500 之后回放真实数据、场景 B 一直回 500） |

**12e 端到端实测的两段回答**（同一句提问「帮我推荐几款乳清蛋白粉」，差别只在桩的行为）：

- 场景 A（抖一下）：桩第 1 次回 500、第 2 次回放真实数据 → 工具 `success=true`，输出里带着真实商品的 `SPU3`，回答正常展开
- 场景 B（一直 500）：桩连着回了 3 次（1 次首查 + 2 次重试），工具 `success=false` 且日志标 `transient=true`，回答是
  「**目前商品搜索服务暂时不可用**，我们无法实时为你筛选并展示具体在售的……这部分信息需等服务恢复后才能获取。✅ 你可以稍后重试」
  ——**改造前这里说的是「没有找到相关商品」**，用户会以为商品下架了

**本批修掉的真实缺陷**（按发现顺序）：

1. **MCP 路径上高危工具永远失败**（HIGH，12a）：工具「在册」但协议里没有传 `confirmed` 的位置，
   每一次调用都被第二道防线拒掉，而拒绝文案与「操作失败」无法区分。
2. **业务码 500 被读成「没有」**（HIGH，12e）：`ProductTool` 在下游搜索服务 5xx 时回「没有找到相关商品」、
   `OrderTool` 回「没有找到订单 X」，`InteractionCheckTool` 会把「没查成」渲染成「没有冲突」——
   **都不是文案问题，是工具在编事实**。根因是三种结局共用一个 `null`。
3. **`CancelOrderTool` 在业务拒绝时 NPE**（MID，12e）：409 的响应体 `data` 为 `null`，
   工具紧接着取 `order.getOrderNo()`，模型拿到的是「Cannot invoke … because "order" is null」，
   而下游早就把话说清楚了（「订单已取消，不能重复取消」）。
4. **确认链路的两处绑定缺失**（HIGH，12c）：布尔置位即放行本轮计划里**全部**高危步骤（卡片与真正执行的调用之间没有强制关系）；
   重入要执行什么靠模型从短期记忆里回忆，窗口滑过去、隔久了点、换台设备，卡片还在而订单纹丝不动（**U37 由此关闭**）。
5. **`retrievalQuery` 只影响回答侧**（HIGH，12b）：指代追问时检索侧仍拿「那它和钙片能一起吃吗？」去查，字面上没有实体。
6. **`ToolResult.facts` 无法从 output 反解**（MID，12d）：输出文案改一个字，解析它的正则就悄悄失效，
   而失效的核对器与通过的核对器看起来一模一样——所以事实由工具**声明**，不由上层解析。

**两处刻意留下的边界（被追问时要主动说）**：

- **12e 的重试窗口只有几百毫秒（两次重试、150/300ms 退避），救的是抖动不是宕机**。
  宕机该由熔断与降级管；工具层替用户多等上几秒，换来的是每个提问都慢一截，而结果还是一样。
- **12d 的事实核对只覆盖工具声明过的字段**（当前是订单的状态与应付金额）。
  没声明的事实它一概不管——**"核对通过"是"这两条对得上"，不是"整段回答都对"**。
  漏检上限就写在这里，不吹成「全量事实校验」。

### 8.14 批次 13f（结算页口径统一）的验收证据（2026-10-01）

验收标准原文：**限类目券在结算页显示"不可用"且理由具体，与提交结果一致；一级类目券对子类目商品生效。**

这一批没有新功能，修的是一个反复出现的病根：**同一个语义写在两条路上，迟早分叉**。三处分叉
（券能不能用、要付多少钱、订单页签各有哪些单）是同一件事 —— 同一个判断前端和后端各写了一遍，

| 层 | 做什么 | 证据 |
|---|---|---|
| 后端 · 券可用性只有一个出处 | `CouponServiceImpl.evaluate` 同时服务于「试算预览」与「提交核销」：预览下发的 `usable/unusableReason` 与核销拒绝时抛的 msg **是同一个字符串**（`IllegalStateException` → 409）。前端不参与任何可用性判断 | 类目外商品：预览 `usable=false`「该优惠券不适用于订单中的商品」，真实提交 **409 且 msg 与预览逐字相同**；未达门槛同理（预览「还差 43100 分」＝提交 409 的 msg）。页面上渲染的理由也逐字等于服务端 `unusableReason`（真浏览器断言） |

**缺陷一：类目作用域是等值匹配，配在一级类目上的券永远用不出去。**

### 8.15 批次 13g（收尾）的验收证据（2026-10-01）

验收标准原文：**一条脚本覆盖 13a–13f 的关键断言；材料与代码逐条对齐。**

这一批的初衷只是"写个跨批脚本 + 同步材料"，结果脚本第一次跑就红了一条 —— 而它红得很有价值：
**13a–13f 每一批的验收都是绿的，但每一批绿的都只是"这一批问过的那件事"。两批交界处没有任何一方断言过。**
这一批因此变成了「专门去量接缝」，量出两个 P0（U64、U65）并修掉。

**接缝 A：商品下架不停交易（U64，P0）。**

| 步骤 | 修前 | 修后 |
|---|---|---|
| `PUT /products/admin/spus/1/status?status=0` | 200 | 200 |
| `GET /products/1` | 400「商品不存在」（展示层生效） | 400「商品不存在」 |
| `POST /cart/items` | **200，`available: true`** | **409「商品已下架」** |
| `POST /orders/preview` | **`unavailableCount: 0`** | **`unavailableCount: 1`** |
| `POST /orders/checkout` | **200，下单成功** | **400/409 被拒** |

根因：**"这件商品能不能买"在三个地方各写了一遍，且用的是两套判据** ——
购物车 `toResponse` 与订单 `isUnavailable` 只看 SKU 状态，收藏 `FavoriteServiceImpl` 看 SPU 状态。
关键在于**两级状态是两件事**：下架一个 SPU 是「整个商品停售」，但它下面每个 SKU 行自己的 `status`
不会跟着变，所以只看 SKU 的那两处永远认为商品在售。**和 13f 是同一族病，只是藏在了另一层**
（13f 修的是"前端算一遍、后端算一遍"，这里是"购物车算一遍、订单算一遍、收藏算第三遍"）。

修法：判据提到**共享契约类型**上 `SkuSnapshot.purchasable()`（两级状态都在售才算），
三处调用点全部收口，`ProductServiceImpl.skus()` 补发 `spuStatus`（`spus` map 本来就在手边）。
放在契约上是因为这个判断**跨越了 product-service 与 order-service 的边界** ——
两边各自实现一次，就是给下一次分叉留土壤。顺手删掉两处已无人使用的 `STATUS_ON` 私有常量：
**常量留在原地，下一个人就会再用一次。**

**接缝 B：购物车缓存缓存了一份跨服务的派生结果（U65，P0）。**

判据改完，同一条断言**还是红的** —— 购物车那一行仍是 `available: true`。它读的不是库，
是 Redis 里 `cart:user:<id>` 的**整份 `CartItemResponse` 列表，TTL 72 小时**，
失效只在**用户改动自己的购物车**时触发。但**这份数据里没有一个字段由 order-service 说了算**：
价格、库存、上下架全部来自 product-service，于是商品侧的改动不触发任何失效 ——
管理员改价或下架之后，购物车能对着三天前的快照说「有货、就这个价」，
用户点进结算页被服务端现算的另一个数打脸。**这正是 13f 刚修掉的那件事，被缓存重新引入了。**

> **判据：缓存的失效触发必须覆盖它的全部输入。覆盖不了时，它缓存的是错的答案，不只是慢的答案。**

修法是**删掉这份缓存**而不是缩小 TTL：把 72 小时改成 30 秒只是把「错三天」改成「错三十秒」，
内容与失效条件不匹配这件事一点没变。缓存只能放在**数据所有者**那一侧 ——
product-service 的商品缓存（Caffeine + Redis + 广播失效 + 布隆过滤器 + 空值哨兵 + TTL 抖动
+ 重建互斥 + 熔断降级）**原样留着**，因为它的失效由它自己的上下架与改价驱动；
`CartCacheService` 也随之只剩库存锁，改名 `StockLockService`。

代价是量过的：`GET /cart` 端到端 **29ms**（含网关、鉴权、跨服务），其中跨服务批量取快照 **15ms**。

**接缝 C：领券到提交的金额一致性（这一条本来就是绿的，但断言方式被加固了）。**

| 断言 | 结果 |
|---|---|
| 领券 → 试算抵扣 2000（先钉死券真的生效，否则 `0 == 0` 也是绿的） | ✅ |
| 真实下单：**17800 === 试算 17800** | ✅ |
| 订单详情落库一致（不只是响应回显） | ✅ |
| 券已核销 | ✅ |

**验收脚本自身的缺陷（U67，P2）**：`verify-favorites.mjs` 用 `try/finally` 把 SPU 恢复上架，
但进程**被强杀过一次**，`finally` 没跑到，演示库里那个商品从此停在下架态 ——
后续几批里表现为「这个商品凭空没了」，没有任何地方记得是谁干的。
（而这一批发现 U64，恰恰是因为顺手拿这个漂移的夹具跑了探针。）
修法：**入口先幂等还原一次，再进入断言** —— 两道还原里入口那道才是真兜底，
`finally` 只覆盖"抛异常退出"，覆盖不了 SIGKILL / 超时强杀 / 机器重启。

**另一个差点被误判的"缺陷"**：product-service 启动崩掉的那几分钟里，`/products/1` 回的是
Spring 默认的 500 裸体，看着像「下架商品返回 500」；等它起来一测，回的是
`400 {"msg":"商品不存在"}`。**那个 500 是网关对下游不可用的兜底。**
差一点照着一个不存在的缺陷去改代码。（成因记为 U66：启动期 Redis 握手超 1 秒即进程退出，
`spring.data.redis.timeout: 1s` 是**故意**配的降级速度，但它同时管启动握手 ——
一次偶发不足以定方案，未修。）

**回归口径**：本次改动波及 contract（`SkuSnapshot` 新增字段与判据）、product-service（1 个文件）、
order-service（3 个文件，删 1 个）、前端（2 个验收脚本）。

### 8.16 批次 15（多条件商品推荐）的验收证据（2026-10-01）

| 数据 | 种子库在营养保健域内补 4 个品类与可筛选属性（适用人群 / 剂型 / 是否含乳糖 / 储存条件） | **没有可筛选的属性，多条件就只是个说法**：属性定义按类目维护，所以「适用人群」在每个相关类目下各有一行，检索侧只看名字与取值 |

**ES 索引 v2 → v3（`envoymart_spu_v3`）**，加了两样东西：

- **单字通道 `unigramText`**：二元组（cjk）有固有盲区，实测 `碳酸钙 D3 咀嚼片` 切出来是
  `[碳酸, 酸钙, d3, 咀嚼, 嚼片]`，用户搜「钙片」切出来是 `[钙片]` —— **两边没有任何一个词元重合**，
  于是这个商品搜不到。修法不是换分词器，是让两条通道并存：二元组那条负责精确与打分（行为逐位不变），
  逐字那条要求**查询里的每个字都命中**（`operator=AND`，否则「钙片」会退化成「含钙就行」）。
  项目里商品检索只有 BM25 这一路、没有向量兜底（知识检索那一路有 Milvus，同样的分词缺口被语义通道盖住了），
  所以这个盲区在这里必须是显式补的。
- **结构化属性 `attributes`（Keyword 数组）**：与既有的 `attributeText` 并存不是冗余 ——
  那个给全文检索用（搜「胶囊」能命中），这个给筛选用（「适用人群等于孕妇」要精确）。
  多选属性的一个值一项：整串存 `适用人群:成人,老年人` 的话筛「老年人」就漏了，而那种漏是静默的。
  用 `Keyword` 而非 `Text`，是因为筛选不能经分词器 —— 分过之后「软胶囊」与「胶囊」就没区别了。

**分流判据与 `minimum_should_match` 的那个坑**：加了第二个 `should` 通道之后，
`bool` 里只要还有 `filter`（`status`），`should` 的默认 `minimum_should_match` 就是 0 ——
两条通道会双双退化成「可有可无的加分项」，而 `status` 的 filter 足以让**所有在架商品**全部命中。
症状是**搜索看起来完全正常，只是搜什么都返回全部商品**。所以 `bool.minimumShouldMatch("1")` 不能省，
联想（suggest）那条路同样加了通道、同样要补这一句。

**空结果不再只是一句「没找到」**：工具会**逐个撤掉一个条件再查一次**（最多三次下游调用，毫秒级），
找出把候选清空的那一个，并告诉模型「去掉 X 后能找到商品，可以把这一点告诉用户」。
光说「没找到」，模型只能猜是哪个条件太严，猜错了就给出没用的建议。只撤单个、不试组合 ——
撤掉两个几乎总能查到东西，那种「结论」对用户没有指导意义。

**本批的三个 P0（都是「改完才发现」的，记在这里而不是悄悄修掉）**：

**P0-1 · 种子数据的代理键写死了，而守卫写在自然键上（U69）。**
新增属性取值时给 `spu_attribute_value` 写了显式 id，而那张表的唯一性守卫写在
`(spu_id, attribute_id)` 这个**自然键**上。老库上这些行的 id 还是上一版的行序 ——
守卫按自然键判断「这行不存在」于是放行，而它要占的 id 已经被别人占了：
`Duplicate entry '28' for key 'spu_attribute_value.PRIMARY'`，**服务起不来**，而报错里那个 28
在种子文件里只是「第 28 行」，照着它排查会一头雾水。
判据：**id 有人引用（别的表拿它当外键）时才写死，那是数据的一部分；没人引用的一律交给自增** ——
种子行会随品类扩充整体前移后移，写死 id 就必然撞。
配套的坑：属性定义的**迁移语句必须放在 insert 之前**，反过来在第二次启动时会炸
（迁移走的那一行不存在了 → insert 的守卫放行 → 把它插回来 → 迁移又把它改成已被占用的 id → 撞唯一键）。

**P0-2 · `PageResult` 缺无参构造，整条商品检索炸在解码这一步（U70）。**
`@Data @Builder` 的类**没有无参构造**（`@Data` 在同名注解在场时不补），于是
**序列化正常、反序列化抛异常**：`Cannot construct instance ... no Creators, like default constructor, exist`。
表现是「工具拆参完全正确、下游 HTTP 200、应答是合法 JSON，工具却报『商品服务连不上（DecodeException）』」，
而报错里只有类名、看不出是缺构造器。
`contract` 下的 DTO 全都成对写了 `@NoArgsConstructor @AllArgsConstructor`，`PageResult` 是唯一例外 ——
直到这一批把商品工具从裸 `List` 改成 `Result<PageResult<ProductSummary>>` 才第一次踩到。
**判据：出参只需要 getter，入参需要构造器**；而 HTTP 层脚本（JS 的 `JSON.parse`）对它完全免疫，
所以「七节全绿、模型这一节全红」是可能的 —— 同一份 JSON，两条路一个能读一个读不了。
定位过程一度受阻于**失败路径零堆栈**（`Downstream.invoke` 的 catch 只包了话术、没打堆栈），
补上 `log.warn(..., e)` 之后才从 cause 链里看见真因。

**P0-3 · 检索的默认排序把相关性整个丢掉了（U68）。**
`sortOf` 原先只有一个字段排序、缺省是销量降序，而 **ES 按字段排序时不计算得分** ——
实测搜「乳清蛋白粉」，排第一位的是**维生素 C 咀嚼片**（详情里提过「蛋白」），真正叫这名字的商品排第二。
接口 200、日志正常、没有任何地方报错，**用户和模型都只能看见一串「搜了等于没搜」的结果**。
改法不是「把 sales 换成 `_score`」：销量本身是有效信号，该丢的是「用销量**替代**相关性」——
所以综合排序是两级：`_score` 降序，同分再看销量；`sales` / `price_asc` / `price_desc` / `newest`
四项字段排序保持不变。前端加了「综合排序」并设为默认（后端缺省值同步改为它），
`relevance` 在 MySQL 那条路上落到销量降序（那里没有相关性可言），两条路语义不相反。
验证：`乳清蛋白粉` 综合排序下第一是 `乳清蛋白粉`、销量排序下仍是原来的顺序；无关键词按类目浏览结果不变。

**P0-3 是被一条「措辞断言」牵出来的**：`verify-downstream-retry` 的场景 A 断言
「回答没有把这次抖动说成『没有这个商品』」，红了，报告里给出的匹配是「暂无完全匹配的商品」。
去查回答全文，模型说的是「搜到的三款商品中：SPU20 是维生素C片，不符合品类；SPU3 是乳清蛋白粉但超预算…」
—— 它**拿到了真实数据**，只是在如实转述「这三条里没有同时满足条件的」。
**是那条断言拿模型的措辞判了罪**（U72）：同一个语义它时而说这句、时而说「暂无完全匹配的商品」，
两次的产品行为一模一样。所以断言改锚在**谁造成的**上 —— 场景 A 该守的是
「重试救回来了就不许说这次没查成」（查「不可用/查询失败/服务异常」这类**归因于系统**的说法），
而「把失败读成否定」那条守卫留在场景 B（那里工具确实没查成，任何「没有」都是编事实）。
但顺着这次「红」往上摸，才看见 P0-3 —— **红灯本身是假的那一次，恰恰是它把人带到真问题前面的**。

**同一批里第四件值得记的事：构建产物可能来自一个「编译失败但照样写出了 class」的构建器（U71）。**
改排序时写了 `withSort(sortOf(...).toArray(SortOptions[]::new))`，而这版
`NativeQueryBuilder` 只有 `withSort(List<SortOptions>)` 与 `withSort(SortOptions, SortOptions...)`
—— 这个写法编译不过。但**服务照常起来了、接口照常 200**，应答是
`{"code":500,"msg":"服务暂时不可用"}`，日志里是：

```
java.lang.Error: Unresolved compilation problems:
    The method withSort(List<SortOptions>) ... is not applicable for the arguments (SortOptions[])
    at ...ProductSearchService.search(ProductSearchService.java:182)
```

根因：**VSCode 的 Java 扩展（ECJ）在编译失败时照样往 `target/classes` 写 class，
内容是运行时抛 `Error: Unresolved compilation problems` 的桩**；而 Maven 的增量编译
按时间戳判断「class 比源码新」于是**跳过重编**，直接跑那个坏 class。
这与本批另一处（`@PathVariable` 省略名字依赖 `-parameters` 标志）是同一个环境的两个面：
**`target/classes` 可能被两个构建器写，且其中一个会写出「能加载但不能用」的字节码**。
判据与收口：`@PathVariable` 全仓显式命名（本批收掉最后两处）；遇到「代码明明改了、行为没变」
或「编译不过却没报错」时，先看 `javap -v ... | grep -c MethodParameters`、
再 `mvn clean compile` 强制重编，而不是继续改代码猜。

**与立约的偏差（如实记录）**：

- **没做 `categoryName` 工具参数**。立约里写了「工具签名扩为 …+ `categoryName?`」，
  实际没加：`/products/search` 那一层收的是 `categoryId`（并会展开整棵子树），
  而模型给的是**类目名**，中间要一次名字→id 的解析，解析失败就是**静默筛空** ——
  在没有真实用例之前加它，等于给模型多一个会静默出错的口子。
  （`attributes` 那个参数是有取值清单的、写在工具描述里，模型照着填就不会踩这个坑；
  类目名没有等价的可枚举清单。）**留待有明确需求时再做。**
- **知识图谱没有随新品类扩充**。图谱语料是模型从知识文档里抽的，新加的 4 个品类
  与它们的成分/营养素还没有对应的文档，所以图谱覆盖不到它们。
  这**不影响本批的验收**（图谱那一条判的是「推荐出的商品若在图上，相互作用要查得到且带出处」，
  判据是自洽的，不写「某个商品必须在图上」），但它是一处**真实的缺口**（U73）。

### 8.17 批次 16（查询扩写）的验收证据（2026-10-01）

验收标准原文（§六「批次 16 的立约」）：**真实对照实验里语义档 Hit@3 从 0.625 抬起，字面档不掉；
CI 用预录扩写重放防退化；对照实验必须打出扩写降级次数；回归 `verify-*` 全绿。**

**为什么是这一条**：三档里字面 1.000、口语 0.950、**语义 0.625**——40 条语义鸿沟样本里约 15 条
一次都没召回。这一档的天花板不是「排序不够好」，而是**候选池里根本没有那篇文档**：
查询与文档没有共享词元，向量空间里也离得远。重排、加权、调 topK 都救不了没进池子的东西——
**只有把查询本身变得更接近文档的样子**。

**三层落地（一处判定）**：

| 层 | 改了什么 | 关键取舍 |
|---|---|---|
| 扩写层 | `QueryExpander` → `QueryExpansions(hypothetical, angles)`；`LlmQueryExpander` 一次调用同时产出假想答案与多角度改写 | 两样产出读同一个输入、共享同一段提示词，拆成两次调用等于把同一句话交给模型两次、付两遍延迟，而它们之间没有任何依赖 |
| 融合层 | `HybridRetriever` 接受变体：**每一路只吃它擅长的那种变体** | 假想答案只喂向量路（它补词汇鸿沟），角度改写只喂词法路（它补表述差异），图谱路只认原句 |
| 装配层 | `MultiQueryRetriever` 装饰器 + 开关 `envoymart.rag.query-expansion.enabled` | 包在 retriever 这一层而不是对话层：检索有**两个入口**（Agent 主链路的 RAG 与 `KnowledgeSearchTool` 的 ReAct 再检），包在外面两条都自动带上，包在任一条里另一条就成了分叉 |

**「每一路只吃它擅长的那种变体」是本批的设计要点，也是实测能验证的**：把假想答案
无差别喂给所有路，等于拿一段编出来的长文本按 idf **稀释** BM25 里真正的查询词元。
真实对照里的可加性证明了这个路由是对的 —— 角度改写（进词法路）语义档 +1 条，HyDE（进向量路）
再 +3 条，两条路各补各的洞。

**真实对照完整梯子**（90 篇语料 / 120 条样本 / topK=3，720 次重排调用 **0 次降级**）：

| 混合 + 重排 | 1.000 | 0.950 | 0.625 | 0.858 |

**CI 门禁（关键词路 + 预录夹具，确定性、毫秒级）**：

| 档 | 扩写前 | 扩写后 | 条数 |
|---|---|---|---|

**CI 里测不出 HyDE 的语义增益**：`SimpleEmbeddingService` 是 `Random(text.hashCode())` 播种的
128 维伪随机向量，假想答案送进去只是一段无语义的噪声。CI 能测的是**多角度改写对词法路的增益** ——
而这一半值得单独守，因为它证明了一件反直觉的事：**语义鸿沟档的提升可以完全由词法侧拿到。**
用户说「太贵了」，文档写「定价依据」——这不是向量才能跨的鸿沟，把口语翻译成文档用词就够了，
而翻译恰好是模型的强项。

**门禁的写法**：夹具与样本必须一一对应（样本增删后忘了重采，缺的那条会**静默地按原句检索**，
数字只是偏低、看不出异常，门禁就在测一个越来越小的子集）——`allMatch(covers)` 把「夹具过期」
从沉默变成红灯。增益断言**直接数命中条数**，不从比率反算：比率是浮点数，
`Math.round(hitRate * caseCount)` 会随舍入漂移。覆盖率断言从 `= 100%` 放宽到 `>= 90%`——
90% 能干净地分开「提示词逃逸口回来了（37.5%）」与「个别查询模型没照做（1/120）」两个量级。

**本批最值钱的经验：提示词里的「逃逸口」会被模型滥用。**
第一版提示词写了「若这条查询本身已经足够清晰，输出 `{"hypothetical":"","angles":[]}`」。
实测模型把语义档 40 条里的 **25 条（62.5%）** 判成「无需扩写」，而那 25 条恰恰是最短最口语、
最需要扩写的（"太贵了"、"着急用"、"催一下进度"、"不想要了"、"钱不够"）。
收掉逃逸口后：覆盖率 37.5% → 100%，关键词路语义档 **0.225 → 0.450（翻倍）**，
真实配置语义档 0.675 → **0.725**。

**这个根因是靠一层「归因配置」摸出来的，不是靠盯着指标看出来的。**
第一轮跑完，语义档只从 0.625 涨到 0.675，看着像「HyDE 没用」。加一档
`AnglesOnlyExpander`（只喂角度、丢掉假想答案）才看出：**增益全来自角度改写，HyDE 净效果 ≈ 0**。
一个「净效果约等于零」的组件不会自己暴露原因，只有把它单独摘出来跑一遍才会问出
「它到底是没起作用，还是根本没运行」。答案是后者——模型压根没产出东西。
**判据：当某个组件看起来「没用」时，先证明它真的运行过，再去评价它有没有用。**

**产品缺陷：账本漏在另一条线程上（本批最值得讲的一条）**

- **对账断言怎样抓住它**：usage 的断言是「账本总额 == 该轮日志各次调用之和」。日志侧 17828
  （7 行 `[LLM]` + 2 行 `[Rerank]` + 5 行 `[Embed]`），账本侧 15925，差额 1903。按线程归属一拆就
  定位了：主线程 `exec-10` 的 10 行合计恰好 15925，差额全部来自虚拟线程 `virtual-353` 上的 4 行
  ——查询扩写（LLM 520）+ 向量化（16+85）+ 重排（1282）= 1903，逐项对上。
- **根因**：批次 12 起计划步骤在 `agentExecutor` 的虚拟线程上并行执行（`AgentGraph.invokeBatch`），
  而执行器的包装只做了 `RequestId.inherit`（把日志标识带过去），没有把账本带过去——
  **同一件事「跨线程传播」在两个上下文里各写了一遍，日志传了、账本没有**。
- ⭐ **`TokenLedger` 的类注释早就预言了这个失效形状**：原文写着「哪天有人把某次模型调用挪到
  另一个线程上，那一笔就会静默地不计入——数字偏小、不报错。所以端到端验收里有一条是
  『账本总额必须等于该轮日志里各次调用之和』，而不是只看数字非零」。写下失效形状的判据，
  在 7 个批次之后真的抓住了一次失效——**这就是「验收断言按证伪写」的兑现时刻**。
- **修法**：`TokenLedger.inheriting(Runnable)`（与 `RequestId.inherit` 同一模子：捕获 → set →
  finally 还原；还原而不是清空——池化线程可能正拿着自己那一轮的账），叠加进 `agentExecutor`
  的包装。新增 2 条单测：「包装过的任务把账本带进另一个线程」（钉 agent 实际走过的那条路）与
  「包装执行完还原目标线程原有账本」。
- **验证**：`TokenLedgerTest` 9/9 绿；重启 ai-service 后 `verify-usage` **15 通过 / 0 失败**，
  日志复核虚拟线程上的 1910 tokens 进账（本轮用量 18938 = 17873 + 1065）。

**脚本修复里最值得讲的四条**

- **通用选择器 `.first()` 会被「后来加的元素」截胡**：approval-chain 的定位停在它那一批的页面
  结构上（当时页面上只有聊天一个输入框），改造期加了顶栏搜索框之后，
  `'textarea, input[type="text"]'` 的首个匹配变成了搜索框——fill 填进了搜索框、聊天框仍是空的，
  按钮只因「输入为空」保持 disabled，现场看起来像整个前端卡死。而 chat-ui 脚本一直用
  `.composer textarea`（对业务组件的定位），从来没坏过——**选择器的稳定性不取决于它写得多
  「通用」，取决于它钉的是不是那个元素本身**。
- **验收脚本自己会把断言推出可见精度**：review-loop 每轮往商品 1 提交 3 条真实评价
  （「每轮新注册用户」解决了「我的评价」穿帮，没解决商品页），累积到 33 条 PUBLISHED、
  其中 23 条就是测试文案（`verify-review-loop 差评：包装破损，客服也没人接`——**演示页面上
  挂着的就是这些字**）。池子一大，3 条新评价对均分的推动只有 0.03，而 `statistics.average`
  只回一位小数——3.7 → 3.7，`<` 退化成相等。修法两层：① 断言改走 `distribution` 五格加权
  （全整数、全精度，池子再大也判得动，并钉住同型的「隐藏后均分回升」）；② **收尾自净**——
  评价是**商品的公共资产**，不是订单流水（订单只增不减是业务事实，评价挂在公开页上是污染），
  跑完把测试评价走管理端隐藏（走接口而不是 SQL，因为状态变更要触发重聚合；隐藏而不是删除，
  被隐藏的测试评价与真实审核场景同形）。实测自净清掉 26 条，商品 1 回到 10 条真实种子评价、
  4.3 分，商品侧与评价侧数字同源一致。
- **用列表页定位元素的脚本，都在隐式依赖「数据集规模与排序」**：admin-console 的定位假设
  「候选行在列表第一页」——脚本没写下这个假设，但代码依赖了它。页大小 20 是页面内部约定，
  而验收夹具恰恰是会上涨的那个变量，两者相遇只是时间问题。修法是不依赖位置（走页面自己的
  关键词搜索把集合收窄到一条）。**和上一条合起来是同一句话：脚本的定位要么钉住元素本身，
  要么主动收窄集合，不能赌环境恰好长什么样。**
- **验收脚本之间会通过产品自己的记忆功能互相污染**（本批最值钱的一条）：verify-memory 的三句
  fixture（「学生党，预算 200 以内」「乳糖不耐受」）被记忆抽取器**正常地**抽成画像与长期记忆
  （累计 26 条 Milvus 条目 + Redis `profile:u1003`），而它们挂在 admin 账号上——于是此后每个
  用 admin 的聊天脚本都被「个性化」了：「推荐几款乳清蛋白粉」被画像补上 maxPrice=200 与
  「不含乳糖」属性，商品筛空、trace 标成 noData，打红了读路径完全无辜的 tool-trace；
  downstream-retry 的回答里也混进了与本场景无关的筛选描述。**这不是某处写错了，而是两个正确
  行为的复合**：记忆跨会话生效是产品设计，脚本陈述长期偏好是脚本本分——合起来，「一个脚本的
  正常使用」成了「另一个脚本的环境」。修法与 review-loop 先例一致：聊天类脚本一律每轮注册
  一次性用户，验收夹具不落在共用账号上；已污染的 admin 画像与 26 条条目一并清除。判据：
  **凡是会把数据写进「用户态」的验收（记忆、画像、收藏、订单），都必须用自己的一次性用户**
  ——这些数据的可见面是跨会话的，隔离就必须跨会话。
  诊断过程另有一条方法论：先怀疑「工具描述里的示例值被模型照搬」并加过护栏句，直到发现
  **两次注入的值完全相同（200 / 乳糖 / 成人）**——同一现象反复给出同一组值，指向「有稳定
  来源」（画像），而不是「模型随机编」；证据推翻假设后，护栏句完整回滚（它还会静默压掉

**事故：一笔支付订单的销量在死信队列躺了 24 小时（本批最值得讲的一条）**

- **现场**：评价恢复演练（verify-review-loop 的「隐藏 → 恢复 → 均分回升」）连续两轮
  打红，排查中途顺手看了死信队列——`product.aggregate.dlx.queue` 里躺着一条
  **2026-10-01 的真实支付订单事件**（order 151 的 OrderPaidEvent），与本次演练无关，
  是独立发现。
- **事实链**：order 151 于 10-01 支付；`product_sales_ledger` 无对应行、商品销量少记
  3 件；消息 `x-death` 的 reason=rejected（重试耗尽被拒），而**默认 recoverer 不携带
  异常堆栈**——死信只知道「失败了」，不知道「为什么失败」。product 侧两个死信队列
  此前没有任何消费者，也没有回放机制：**消息死了 24 小时，全程没有任何东西会响**。
- **数据修复**：按原路回放（rabbitmqadmin 直接投递原始报文，带 `__TypeId__` 头让
  Jackson 认类型），台账 +3 行、销量 1319 → 1322，死信清零。回放安全：台账主键是
  **订单行**（order_item_id），重复投递会撞唯一约束被跳过。
- **机制修复**：order 侧原先有一个「只打一行日志就 ACK」的死信消费者——**它把证据
  吃掉了，而那行日志会被下次重启覆盖**（本次取证时第一现场的日志就已被 restart
  覆盖，无日志级确证可用）。删除该监听：死信刻意留在队列里等人看。
- **常驻断言**：verify-cross-batch 新增「全 broker 死信队列必须为空」（16 → 18 条）。
  两个细节都是踩出来的：① 先断言「查到了 ≥3 个死信队列」再断言「没有一条在躺」——
  否则接口挂掉时空集恒真、假绿；② 只看 `messages_ready` 不看 `messages`——后者含
  unacked，正常消费中（毫秒级）的消息也会被算进去，那是在测消费速度而不是测
  「有没有消息死了」。
- ⭐ **可讲：日志会丢（重启覆盖）、监控会漏（没人看），队列才是耐久的证据。**
  一个「有人消费死信」的队列看起来更完整，实际让事故静默；死信的正确姿态是被
  留着、被断言盯住，而不是被吃掉。

**缺陷：本地缓存的回填竞态（读路径把删掉的旧值钉回去）**

- **现象**：评价恢复演练第一次重跑 55/56——「恢复后均分回升」那条红，重跑两次全绿
  （概率性）。第一现场日志已被 restart 覆盖，先按证据排除法收敛。
- **定性**：与全部证据相容的唯一代码缺陷。读路径的顺序是「读到 Redis 旧值 → evict
  已执行（删 Redis、清本地、广播）→ 无条件回填本地」——**已被删掉的旧值又被读路径
  亲手钉回 Caffeine 60 秒**。窗口是 µs 级，但 GC 停顿可以把它放大到几十 ms。
- **修复：失效纪元**。`ProductLocalCache` 增全局 `AtomicLong` 纪元：`invalidate` 在
  锁内「递增纪元 + 删条目」，回填在锁内「校验纪元 + 写入」，同一把锁互斥；读路径
  记下「读 Redis **之前**」的纪元，Redis 回填与 loader 写路径都校验——期间发生过
  失效则**两级都不写**。纪元是全局的不是按 id 的：**宁可误拒（这次不回填），
  不可错回填**。`ProductLocalCacheTest` 补 2 个方向相反的用例。
- **诚实边界**：无日志级确证（首现场日志被覆盖），定性依据是「与全部证据相容的
  唯一代码缺陷」+ 修复后多轮重跑稳定。这条本身可讲：**证据被覆盖时，收敛到
  「唯一相容解释」是次优但可辩护的结论方式——代价是必须说清这个边界**。

**能力：AI 助手的取消语义（「停止生成」是第三种终态）**

- `AgentCancelledException` 继承 `CancellationException`——**取消不是失败**：失败要
  重试、要降级、要说「暂时不可用」；取消是用户主动叫停，正确反应是停止开始新工作、
  把已产生的部分如实收尾。两者混在一起会出两种荒谬：把用户自己按的停止记成系统
  故障（ERROR + 堆栈），或者触发降级话术、服务端继续跑完整个计划——用户已经走了，
  账单还在动。
- 抛出点放在执行链上所有「即将开始新工作」的位置（下一次模型调用、下一批工具、
  下一个已确认操作）；**不打断进行中的工作**（流式调用没有中断句柄，语义是
  「不再开始」不是「中途撕票」）。SSE 断连即取消——用户关页面也能停。
- 半截答复**如实落进历史**（与屏幕一致，服务端不补跑完）；verify-chat-ui 新增
  「停止生成」整节断言（47 → 64 条）。
