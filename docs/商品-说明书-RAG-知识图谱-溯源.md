> 本文只讲**代码里真实存在的那条链路**，不写规划与设想。每条结论都能在源文件里找到落点，关键位置标注了文件路径。

## 1. 全景：一次「上架商品到能回答」到底经过了什么

系统里有**三份东西**，它们的关系是整个设计的核心：

| 角色 | 是什么 | 存在哪 | 谁说了算 |
|------|--------|--------|----------|
| **事实源** | 商品（SPU/SKU）与知识库文档（含原文与切片） | MySQL：`product_*`、`knowledge_document`、`knowledge_chunk` | 管理端的写接口 |
| **派生物** | 向量索引（Milvus）、BM25 快照、知识图谱（Neo4j） | Milvus / 内存 / Neo4j | ai-service 的索引重建 |
| **呈现层** | 回答里的 `[n]` 引用与《文档名》、图谱页的关系与出处、文档页的原文高亮 | 浏览器 | 事实源 + 派生物共同决定 |

一句话概括依赖方向：**事实源 → 派生物 → 呈现**。派生物永远可以从事实源重建，反之不成立。这条单向性决定了后面所有「改了不生效」类问题的排查方向——先问「派生物重建了吗」。

```
                        ┌─────────────── 管理端（人）───────────────┐
                        │ 上架商品 SPU/SKU      上传/编辑说明书      │
                        └───────┬───────────────────────┬──────────┘
                                │                       │
                    POST /products/admin/spus   POST /knowledge/admin/documents
                                │                       │
                                ▼                       ▼
                     ┌──────────────────┐    ┌──────────────────────────────┐
                     │  product-service │    │      knowledge-service        │
                     │  商品/规格/SKU    │    │  ① knowledge_document（原文） │
                     │  商品目录接口     │    │  ② knowledge_chunk（切片）    │
                     │  /internal/catalog│    │  ③ Neo4j 图谱（三元组）        │
                     └────────┬─────────┘    └────────────┬─────────────────┘
                              │  目录（实体链接用）            │ 语料（正文）
                              │                              │
                              ▼                              ▼
                     ┌────────────────────────────────────────────────────────┐
                     │                      ai-service                        │
                     │  重建索引（KnowledgeIndexer）                            │
                     │   ├─ 拉语料 → 结构分层切分 → 向量库 / BM25 快照            │

                     └───────────────────────────┬────────────────────────────┘
                                                 │ 检索三路融合
                                                 ▼
                                  回答 → 引用 [n] → 点回原文（溯源闭环）
```

## 2. 商品与说明书：它们是怎么"绑"在一起的

### 2.1 商品侧的事实源

- 新建商品是**一次事务**写入 SPU + 规格 + SKU + 参数（`ProductAdminController.create`，`POST /products/admin/spus`）。刻意不做"先建商品再逐个加 SKU"的多步接口——中途失败会留下一个界面上看不出坏的商品。
- 商品目录有一个**内部只读接口** `GET /internal/catalog`（`ProductController`），返回 `ProductSummary` 列表，供 ai-service 做实体链接。它挂在 `/internal/` 前缀下，网关直接不放行外部访问。

### 2.2 说明书侧的事实源

说明书就是一篇**知识库文档**，与"退货政策""监管规范"走完全同一条通路。没有单独的"商品说明书表"。

文档写入接口 `POST /knowledge/admin/documents`（`KnowledgeAdminController.upsert`）：

- `docNo` 留空 = 新建（服务端顺延分配编号），填了 = 更新那一篇。
- **更新会重切切片**。正文一变，旧切片的 `charOffset` 就指向了错误的原文位置，而引用正是靠它回跳的。
- 切分用的是与检索侧**同一个实现、同一组参数**：`StructuralSplitter.standard()`（`KnowledgeDocumentServiceImpl` 里的字段注释明确写了这一点）。

文档记录里有几个**不是自由文本**的字段：

| 字段 | 取值 | 为什么受限 |
|------|------|-----------|
| `source` | `manual` / `policy` / `regulation` / `spec` / `guide` | 会被检索侧按来源判断权威度；自由填写会让同一个领域出现三种写法，而筛选是等值匹配 |
| `scope` | `nutrition` / `after_sale` / `logistics` / `payment` / `promotion` / `food_safety` | 检索侧按 scope 做领域筛选 |
| `version` | 如 `v2026.01` | 引用必须指明用的是哪一版；也是"版本较新者取代旧版"判定的输入 |

种子语料（`resources/knowledge/KB-00xx-*.md`）只是**种子，不是事实源**。`CorpusLoader` 在启动时把它们灌进库，目的是"一份新克隆的仓库能直接跑起来"；线上改文档走的是接口，不是改文件重启。

### 2.3 商品和说明书之间，**没有外键**

这是理解整套设计的关键一点，也是最容易被误解的地方：

> **商品和说明书在数据库层面没有任何引用关系。** 它们之间的"绑定"是通过**实体链接**在知识图谱构建时现场建立的。

具体地：

1. 模型从说明书正文里抽出三元组，其中商品一端的 `name` 可能是 `SPU7`，也可能是商品名"鱼油软胶囊"。
2. `KnowledgeGraphBuilder.linkProducts` 把它对齐到 `GET /internal/catalog` 返回的真实目录（键形如 `spu7`，label 是商品名）。
3. **对不上的整条丢弃。** 理由不是洁癖——一个拼错的商品节点在图上是个"真实存在但永远连不上任何东西的孤岛"，查询时表现为"这个商品没有已知相互作用"，**一个不报错的错误答案**。

所以"上架一个新商品，如何把说明书存进 RAG 和知识图谱"，完整答案是：

- **RAG**：说明书作为一篇知识库文档上传 → 重建索引（或单篇增量）→ 切片进向量库与 BM25。这一步**不需要商品存在**，说明书本身就是语料。
- **知识图谱**：重建图谱时，模型从正文抽商品相关的三元组 → 用商品目录做实体链接 → 商品节点才会出现。这一步**必须商品已存在且已启用**，否则链接不到、三元组被丢。
- **两者之间不需要任何手工关联动作**。关联是"目录 + 文档正文"两个事实源在构建期自动对齐的结果。

**当前是否能在管理前端完成**：能，但要分两处操作、按顺序做：

| 步骤 | 界面 | 接口 |
|------|------|------|
| 1. 上架商品 | 管理端 → 商品管理 → 新建商品 | `POST /products/admin/spus` |
| 2. 上传说明书 | 管理端 → 知识库管理 → 新建文档（`source` 选 `manual`，`scope` 选 `nutrition`） | `POST /knowledge/admin/documents` |
| 3. 让这一篇立刻生效 | 保存后管理台**自动**接着调单篇增量重建 | `POST /ai/admin/knowledge/reindex/{docNo}` |
| 4.（可选）整库重来 | 知识库管理 → "重建索引"按钮 | `POST /ai/admin/knowledge/reindex` |

> 顺序要求：**先上架商品，再上传说明书**。反过来的话，这一次的图谱构建会因为链接不到商品而丢掉商品边；等商品上架后需要**再重建一次**才能补上。

## 3. RAG：索引是怎么建的

### 3.1 切分：结构分层，大小只是阈值

`StructuralSplitter`（`agent-core`）的取向是**结构边界优先于大小**：

- 按 章 → 条 → 段 → 句 → 字符 逐级下钻，**大小只作"触发下钻"的阈值**，不是切分目标。
- 生产参数：超过 512 字往下钻一层；低于 40 字与相邻块合并（避免十几字符的碎片白占 topK 名额）。
- 每个切片前面拼上它在文档中的位置，形如 `《深海鱼油软胶囊产品说明书》 > 第二章 > 2.3`，让切片脱离原文后仍能自证语境。

配套改动是**切片级检索融合**（见 3.3）：长文档的多个切片可以各自占据候选位，而不是整篇文档只争一个名额。

> 口径提醒：改造当时线上是 15 篇短文档（每篇恰好一片），切片级融合零收益，切过去只为链路统一；现在线上语料是 **47 篇 / 408 片**，多切片形态真实存在。但 `+11.7pp` 仍是夹具数字，线上没做过 chunk 级 vs 文档级 A/B。

### 3.2 三个检索单元

`KnowledgeIndexer.rebuild()` 做的是"整份重建"：

1. `corpus.reload()` 拉全量语料（来自 knowledge-service，**由 `status=1` 过滤，停用文档不在其中**）。
2. 用 `StructuralSplitter` 切分得到全部切片。
3. `vectorStore.removeAll()` 后 `indexBatch(chunks)` —— **整份清空再写**。
4. `retriever.rebuild(chunks)` 替换 BM25 快照。

为什么向量库是整份清空而不是逐篇删：逐篇删只清得掉"这次语料里有的"那些文档，语料一旦改名或换目录，旧条目就永远留在库里（实测有 15 条早期种子数据躺了几个月，无 title/position、被召回时模型引用不了、用户点开无处可去，还实打实挤占 topK）。整份清空则把"库里恰好等于当前语料"变成重建的性质本身。

单篇增量 `rebuildOne(docNo)` 三段各自取最小改动面：

- **向量库**：`deleteByDocId` + 只编码这一篇，真增量。
- **BM25**：索引是不可变快照，没有按篇增删能力，只能整份重建——但它**纯计算、不调模型、不花钱**，几十毫秒量级，接受。
- **图谱**：写入语义本来就是"按文档整体替换"，所以只重抽这一篇，是天然增量点。

删/停用也走这条路：`docNo` 传进来但语料里已经没有它 → **只删不写**。漏掉这一步的后果就是"停用的文档照样被检索到"。

### 3.3 检索三路与融合

`HybridRetriever` 用 **RRF（互惠排名融合，k=60）** 合并三路：

| 路 | 认什么 | 补谁的盲区 |
|----|--------|-----------|
| BM25（中文二元组 + 单字补充通道） | 词面 | 精确术语、条款编号 |
| 向量 ANN（`text-embedding-v4`，1024 维） | 语义 | 同义改写、口语 |
| **图谱依据**（`GraphEvidenceRetriever`） | **关系** | **实体编号**这类两路都接不上的查询 |

第三路之所以必要，代码里的例子最清楚：语料写着"深海鱼油与华法林合用可能增加出血风险"，用户问"**SPU5** 和华法林冲突吗"——`SPU5` 在任何一篇文档里都不出现，BM25 与向量都无从下手。图谱知道 `spu5 → 深海鱼油`，于是那条风险边捞得回来。

几个关键工程细节：

- **融合的完整流程**（`HybridRetriever.retrieveWithOutcome`）：
  1. 各路按「**语义路 → 词法路 → 图谱路**」的顺序入池。这个顺序有意义：合并用 `putIfAbsent`（先到者胜），同一片被多路召回时留的是先到的那一版。
  2. 语义路入池 **原句 + HyDE 假想答案**两条；词法路入池 **原句 + 各角度改写**条；**图谱路只认原句**——它靠实体编号与实体名定位（`SPU5` 与华法林），而改写恰恰把原句的说法换掉了，改写过的句子在这条路上只会削弱它。
  3. 全部候选汇入同一个 RRF，候选池取 `max(topK × 3, topK)`（`RERANK_CANDIDATES=3`）给重排腾挪。
  4. 重排未配置时是直接截断。
- **图谱路的 key 集合随结果带出**（`RetrievalOutcome.graphKeys`），**不是让下游从截断后的列表反推**。理由：重排会按 topK 截断，图谱切片字面分低，排在 topK 之外就被丢了；下游拿着截断后的列表既看不到它也推不出「它来过」——`EvidenceGate` 的图谱豁免分支正是靠它才有输入。取 key 用与融合同一把尺子（切片级=chunkId，文档级=docId）。
- **扩写结果随 `RetrievalOutcome` 带出**，因为「这回到底用了哪几个查询」是回答为什么对/为什么没查到时最先要问的一件事；不带出去的话，扩写是否生效在链路上完全不可观测，调召回率就成了盲调。
- **按 chunkId 归一**（切片级）。文档级入口则按 docId 归一，避免长文档仅因为切片多而被系统性抬权。
- **第三路可插拔**：`envoymart.rag.graph-recall.enabled` 开关，关掉时传 `null`，行为与只有两路时逐字节一致——留这个开关是为了能当场演示"同一句话，开与关各答一次"。
- **图谱产出与知识库切片同构**：每条边自带 docId / chunkId / 偏移 / 逐字引文，`GraphEvidenceRetriever` 把它拼成**长得和切分器切出来的一样的 `DocumentChunk`**。如果这一路返回的是"图谱说 XX 和 YY 有冲突"这样一句渲染好的文本，那它在回答里就是一段无法追溯的断言——与模型自己编的话在界面上没有区别。
- **图谱失败一律降级为空列表**（增强路不许拖垮主链路），但降级留 warn 日志。

### 3.4 查询扩写（第三路之前的另一处增强）

`MultiQueryRetriever` 包住混合检索，职责是查询改写，两块：

- **HyDE**：让模型先生成一段"假想答案"，用它的向量走**语义路**。
- **角度改写**：把口语问题改写成若干检索角度，走**词法路**。

开关 `envoymart.rag.query-expansion.enabled`，关闭时直接返回 `HybridRetriever` 实例本身（不是"什么都不做"的副本），保证关掉路径与改造前逐位相同。

## 4. 知识图谱：从说明书到三元组到 Neo4j

### 4.1 词表：封闭，且**只有四个关系**

节点类型（`EntityKind`，6 种）：`PRODUCT` 商品 / `INGREDIENT` 成分 / `NUTRIENT` 营养素 / `DRUG` 药物 / `DRUG_CLASS` 药物类别 / `POPULATION` 人群。

关系类型（`GraphRelation`，4 种，且**约束了两端类型**）：

| 关系 | 中文 | 头 → 尾 |
|------|------|---------|
| `CONTAINS` | 含有 | 商品 → 成分 |
| `PROVIDES` | 提供 | 成分 → 营养素 |
| `INTERACTS_WITH` | 相互作用 | 成分/营养素 → 药物/药物类别 |
| `CAUTION_FOR` | 人群禁忌 | 成分/营养素 → 人群 |

为什么是封闭词表：开放式关系名会迅速退化——"增加出血风险""加大出血可能""提升出血倾向"是同一意思的三种写法，每条查询只能捞到一部分，而图上看起来"有数据"。**查询静默漏结果比报错难查得多。**

为什么只有四个：只收语料里真有原文支撑的关系。摄入上限、搭配推荐这类关系在语料里没有任何一句话说过；放进来只会让模型照着关系的名字把答案编出来。

为什么提示词由枚举生成（`GraphRelation.signature()`）而不是手写：手写那版只列了四个名字，模型不知道每条关系对两端类型有约束，于是把"本品与华法林合用可能增加出血风险"抽成了 `PRODUCT -> DRUG`，**实测 KB-0005 七抽七丢、KB-0006 九抽丢七**，丢弃原因全部是"关系不接受这对类型"。从枚举生成后，改约束必然改到提示词，两者不可能再漂移。

> 后果说明写在边的 `effect` 属性上，**不拆成 RISK 节点**："维生素 D + 噻嗪类利尿剂 → 高钙血症风险"里的风险是**组合导致的**，单独一条"维生素 D → 高钙血症"是错的——正常剂量下它不会造成这个结果。拆节点恰好把"谁和谁一起才有事"这个最关键的信息丢掉。

### 4.2 抽取在 ai-service，判真在 knowledge-service

这条分工是刻意的：

- **ai-service 负责"读懂"**：只有它装配了模型（`ChatModel`）。`KnowledgeGraphBuilder` 逐篇文档调模型抽三元组。
- **knowledge-service 负责"判真"**：`GraphService.ingest` 拿**事实源文档**校验。判定"引文是否真的有原文出处"必须比对事实源，而事实源是 `knowledge_document` 表。ai-service 手上只有自己刚发出去的那份文本副本，**用它做判据等于让提交者自己批改**。

### 4.3 抽取侧（`KnowledgeGraphBuilder`）的四条硬约束

1. **只抽原文写了的。** 模型当然知道华法林不能和鱼油乱吃，但图上不该出现一条没有原文出处的边——演示时点开引用会是空的，而空引用比没有这条边更糟。
2. **商品必须落到目录里的真实 SPU**，否则整条丢弃（见 2.3）。
3. **抽取失败不发请求。** 写入语义是"整体替换"，发空列表等于把这篇文档已建好的边全部清空。
4. **解析失败返回 `null` 而非空列表。** 这条是第一版踩过的坑：模型输出被 `max_tokens` 截断一次，这篇文档图上已建好的边就在一次重建里**全部消失**，而报告上失败数是 0、日志只说"抽取 0 条"。窗口期内用户问"这两个能不能一起吃"得到的是"未收录"——**安全场景里的假阴性**。

其它参数与保护：

| 参数 | 值 | 理由 |
|------|-----|------|
| 单篇送模型字符上限 | 12000 | 种子语料最长约 1500 字，这是防意外的护栏 |
| 单篇关系条数上限 | 40 | 防模型跑飞灌几百条 |
| 抽取 `max_tokens` | **4096**（不是对话默认 2048） | 每条三元组都带一段引文，十几条就顶满；顶满的后果不是少几条，而是 **JSON 在字符串中间被截断，整篇归零** |
| 温度 | 0.0 | 抽取要确定性输出 |
| 连续失败熔断 | 3 篇 | 单篇失败是常态；连续失败说明模型/图谱侧整体不可用，再挨个试只会把同一条错误重复十几行、每篇还等满一次超时 |
| 商品目录失败 | **整批不跑** | 拉不到目录 → `linkProducts` 会把所有商品三元组丢光 → 整体替换会把旧商品边删掉，而报告上失败数是 0 |

### 4.4 校验侧（`TripleValidator`）：入库的四道闸

图上的每一条边都会被当成事实回答给用户，所以入库门槛不能是"模型说得像"。四条硬条件：

1. 头尾类型与关系都在封闭词表内，**且关系允许这对类型**；
2. 商品键是 `SPU<数字>` 形状，名字不像一整句话；
3. **两端的名字至少有一个写法出现在这篇文档的正文里**；
4. **模型给出的引文逐字出现在这篇文档的正文里**（忽略空白后匹配，命中后再映射回精确偏移）。

第 3、4 条合起来才挡得住"凭常识补边"：**只有第 4 条时**，模型补出一条"华法林 -INTERACTS_WITH-> 阿司匹林"，再从文档里随便抄一句逐字存在但无关的句子当引文，就能带着一份"看起来有依据"的伪溯源入库——**而这比没有这条边更糟**。

几个容易踩的实现细节，代码里都有注释：

- **端点校验必须判 `label` 非空**。空串被任何字符串包含，少写这个判断这条校验恒为 true，形同不存在。第一版就是这样，"两个端点都是编的"那条照样入库。
- **商品端直接放行**：文档里写"本品"，节点键是 SPU 编号，正文里当然找不到；它与目录的对齐在 ai-service 做，这里只认键的形状。
- **忽略空白匹配**：模型抄原文时经常在中英文之间多一个空格或吞一个换行，逐字匹配会把这类引文判成幻觉——而它其实一字不差。
- **丢弃分五类**（`VOCABULARY` / `SELF_LOOP` / `MALFORMED` / `UNANCHORED` / `UNGROUNDED`），不是合成一个数字。第一版只分"词表/无出处"两类，"无出处"还是事后重算推出来的——于是自环与空名被静默算进"词表"，实测 KB-0005 日志写着"词表 10 / 无出处 0"，**看上去像提示词与枚举对不上，实际一次词表都没查过**。归因错了比不归因更贵：它让人去改一个没坏的地方。
- **失败一律丢弃这一条**，不整批失败。一批几十条里混进一两条幻觉是常态，让整篇文档的图谱因此不建，是把小问题放大成不可用。
- **服务端必须自己校验 `SPU<数字>` 形状**，不能只靠客户端对齐：内部写入接口直连端口就能调，不校验的话谁都能往图上灌任意商品名字符串。

### 4.5 存储（`KnowledgeGraphStore`，Neo4j）

- **单一线型 + 关系名做属性**：`(:Entity)-[:REL {relation:'CONTAINS'}]->(:Entity)`，不引 Spring Data Neo4j。动态类型名要么靠字符串拼接（等于把模型输出拼进 Cypher），要么引 APOC，两条路都比一个普通属性差。属性化之后所有查询都是**参数化**的，"沿几条边走几跳"这类变长路径可以用 `ALL(r IN rels WHERE r.relation IN [...])` 一次表达。
- **节点的键与展示名是两个字段**：`name` 是唯一键（商品为 SPU 编号），`label` 是给人看的名字（如"鱼油软胶囊"）。查询一律按 `name` 匹配、按 `label` 显示——只按 label 匹配的话，商品改名或两种写法（有没有空格）都会让同一条路径忽然断开，而图上看起来只是"多了一组相似节点"。
- **唯一约束必须有**：Neo4j 的 `MERGE` 只有在存在唯一约束时才真正原子，否则两个并发事务各自找不到节点、各自创建一个同名的，而两边都不会报错。后果是图**静默裂开**——查询走到其中一个节点，另一个节点的边全看不见，表现成"这个商品有时查得到相互作用、有时查不到"。**这正是图谱最不该有的失败模式，因为它看起来像模型不稳定。**
- **写入是按文档整体替换**：先删该文档产生的全部边，再写新的（`replaceDocument`）。幂等靠"先删后写"而不是靠 MERGE 去重——重建会重跑抽取，模型每次说法可能有出入，靠 MERGE 会把历次结果越堆越多，图上出现一堆**已经不在文档里的旧边**。
- **读超时与写超时分开**。共用预算真的出过事：`replaceDocument` 原先在一个事务里对每条三元组各发两条语句，11 条的文档就是二十多条挤在同一预算里，实测 KB-0005 撞上超时，**整篇文档的证据一条都没进图**，而调用方只看到"未入库 1 篇"。读在用户请求路径上，超时越短越好；写是后台批量任务，被中途掐断等于白跑。
- **可用性标志必须能被推翻**。`isAvailable()` 只在 ping 里改成 false，而 ping 只在 false 时才重跑——启动探活一旦成功，这个 true 就再也不会变。于是 Neo4j 中途挂掉后，四个读方法各自 catch 住异常返回空列表，接口照样按"图谱可用"渲染，**用户看到的是"没有查到风险"——故障被读成了一个相反的结论。**

## 5. 溯源：从答案的 `[n]` 一路点回原文

溯源不是一个功能点，而是**贯穿全链路的一根线**。每个环节都必须携带字段，断一环整条链就废了。

### 5.1 切片上带了哪些溯源字段

`DocumentChunk` 里专门有一组"溯源用（检索时填充，不参与向量化）"的字段：

| 字段 | 作用 |
|------|------|
| `chunkId` | RRF 归一的键，也是"点引用"的寻址 |
| `docId` / `title` | 显示《文档名》；标题单独存一份，因为检索结果到生成 prompt 之间没有别的地方能拿到它 |
| `source` | `manual` / `policy` / … / **`graph`**。同样是政策，厂商说明书与平台规则的可信度不同 |
| `scope` / `version` | 领域分类 + **引用必须指明是哪一版** |
| `position` | `《文档》 > 第二章 > 2.3`，给人看的落点 |
| `charOffset` | 文档内字符偏移，**给程序定位** |
| `score` / `reranked` | 相关性分，拒答门的输入；**刻意不暴露 RRF 融合分**（量纲是 `1/(60+rank)`，那是名次不是置信度） |

图谱路产出的 `DocumentChunk` 与切分器产出的**结构完全一致**（见 3.3），所以下游渲染、引用标号、点回原文全都不用为它写分支。区别只有一个：`source = graph`，`position` 留空（边只知道自己落在哪一片，不知道那片在文档里的层级路径），渲染时退回《标题》。

### 5.2 三道闸，两前一后

| 闸 | 位置 | 职责 |
|----|------|------|
| **EvidenceGate**（证据门） | 生成**前** | 判定检索到的证据够不够支撑回答 |
| **KnowledgePrompt**（引用规则） | 生成**前** | 把证据渲染进 prompt，并**要求**标注来源编号 |
| **CitationVerifier**（引用校验） | 生成**后** | 逐句核对，把"讲了一条事实却没交代出处"的句子挑出来 |

三道之中只有第三道作用在生成之后，这也是它必须存在的原因：**prompt 是请求，不是保证。** 模型可以标，也可以不标，而它没标的那句话在界面上和标了引用的话长得一模一样。用户看到的是一段排版整齐、引经据典的回答，其中夹着一句凭常识补全的数字——没有任何东西提示他这一句没有出处。

#### EvidenceGate 的几个取舍

- 只看**跨查询可比的分数**（向量余弦相似度或 cross-encoder 重排分），RRF 融合分不在此列。
- **两把尺子两个阈值**：余弦与 cross-encoder 的分布不同，用同一个数字卡两者等于让其中一条路形同虚设。
- **没有分数时放行（fail-open）**：`score` 为 null 只说明这条链路没提供相关性信号，不说明它不相关；因为一个缺失的指标拒绝回答，是把工程缺陷转嫁成用户的损失。
- **图谱依据在场时判定不低于 SUFFICIENT**。这条看着像开后门，其实是在纠正一把用错了的尺子：cross-encoder 量的是 query 与文本的**字面语义距离**，而图谱依据的相关性是由**结构**给的——用户问"SPU7 有什么禁忌"，原文写"出血性疾病患者……应咨询医师"，这两句话本来就不像，任何文本相似度都会给它打低分，**而它恰恰是唯一正确的答案**。实测整轮重排分 0.126–0.157 全在阈值之下，判定成 WEAK，于是模型答对了却要补一句"该条目相关度不足，不能作为权威依据"——**系统明明握着一句原文，却告诉用户别信它。**
- 敢放行的前提是图谱依据的准入门槛不在这一层：能出现在这里的边已经过实体链接、类型过滤，且引文必须逐字出现在**事实源文档**里。

#### CitationVerifier 的判据分寸

判太松（每句都要求引用）会误伤——一轮对话里模型可能既答了政策（该有引用）又答了订单状态（订单号来自工具返回，本来就没有引用可标）；判太严等于没做。取舍是四条：

1. **越界编号无条件摘除。** 正文写着 `[7]` 而本轮只有 3 条证据，这是确定的错误，与"该不该有引用"无关。
2. **先确认这是不是一个知识型回答。** 整篇一个有效引用都没有时不做剔除——那说明这轮压根不在答知识问题，逐句剔会把回答砍碎。
3. **不剔除不等于不报告。** 没有引用也没有工具执行记录的整篇回答，是模型凭自己写出来的，无出处的句子必须报出来。
4. **违规过多则整体放弃剔除**（`MAX_VIOLATION_RATIO`）——一个标了引用却大半没标的回答，更像"模型整体没遵守格式"，全砍比留着更糟。

还有一个必须是"知道就好"的限制：**这道闸对流式是滞后的。** 流式下 delta 已经逐块推给前端了，校验只能改写 done 帧里的完整答案（前端用 done 帧覆盖已渲染文本）。要做成"未校验的字不得到达用户"，唯一办法是先缓冲整个回答再发——那等于放弃流式。

### 5.3 前端呈现：两个页面

**文档页 `KnowledgeDocView`** 是溯源的目的地：

- 路由 `#/knowledge/:docNo?chunk=<chunkId>`，`chunk` 参数即"引用指向的那一片"。
- 正文按 `charOffset` / `charEnd` 切成 head / mark / tail 三段，`mark` 高亮；刷新不丢高亮。
- 左侧切片目录与高亮联动（`aria-current` 跟随）。
- **悬空锚点显式报警**：`danglingChunk`——`chunk` 参数有值但在 `doc.chunks` 里找不到这一片时，页面必须喊出来。它的成因是检索侧与存储侧的切分参数不一致（或文档被删），而那种情况下两边日志都正常，唯一会喊出来的地方就是这里。

**图谱页 `KnowledgeGraphView`** 是知识层的可审计视图：

- 中心实体 + 跳数（1–3），环状布局；节点就是边两端的并集，后端返回边表而不是"节点表 + 边表"。
- 右栏"关系与出处"分两段：**先给中心实体自己的关系**（按关系种类分组），再给其余实体（按实体分组、组内按种类排），风险类关系排在描述性关系之前。
- **同一关系只列一次**：图谱里同一件事常被多篇文档各说一遍（DHA 与阿司匹林相冲，三篇说明书都写了），它们是三条独立的边，但用户眼里是**一件事**。按边逐条列会让用户看到三行一模一样的东西。显示成"1 行 + N 处依据"徽标，展开后逐条给出每处引文与文档链接——**合并不丢证据**。
- 页头有去 AI 助手的入口（`/assistant`）。**图谱是 agent 的检索底座，不是用户自助查询工具**——用户要结论应该去问助手，图谱页存在的意义是"看清知识层长什么样、每条边有没有依据"。

### 5.4 图谱只读接口（`GraphController`，公开前缀 `/knowledge/graph`）

| 接口 | 用途 |
|------|------|
| `GET /entity?name=&depth=` | 实体邻域，供前端画图；`name` 商品传 SPU 编号，其余传中文名 |
| `GET /search?keyword=&limit=` | 实体检索，也给"图谱里到底有没有收录这个词"用 |
| `GET /recall?query=&limit=` | 图谱召回，检索第三路的入口，**不下结论** |
| `GET /interactions?items=` | 「我手上这几样能不能一起吃」，**逐项下结论**（含"没有收录"这种否定回答） |
| `GET /stats` | 图谱规模与各类关系条数 |

两条设计红线：

- **图谱不可用时 `/entity`、`/search`、`/recall` 返回 503，不返回空列表。** 空列表在界面上会渲染成"没有查到相关内容"，而在这个场景里它会被读成"这几样东西没有冲突"——**一个完全相反的结论**。
- **`/interactions` 是例外**：不可用时返回 200，报告体里带 `available=false` 与原因，前端据此显示"未检查"而不是"无冲突"。这是一份"检查没做成"的报告，不是一次请求失败。

## 6. 一次问答里，agent 拿信息的顺序

```
用户问题
   │
   ├─ QueryRewriter：指代消解（"它/这个" → 具体实体）
   │
   ├─ 入口检索（Retriever，含扩写）
   │     └─ BM25 + 向量 + 图谱依据 → RRF 融合 → 重排 → topK
   │
   ├─ EvidenceGate：判定 SUFFICIENT / WEAK / NONE
   │
   ├─ KnowledgePrompt：把证据渲染进 system prompt（三种状态三种指令，
   │                  不足时若注册了再检索工具，会多给一条"先换词再查"的出路）
   │
   ├─ Agent 循环（ReAct / Plan-and-Execute）
   │     ├─ 业务工具：订单、物流、商品、购物车、结算、售后…
   │     ├─ InteractionCheckTool：「这几样能不能一起用」→ 图谱比对
   │     └─ KnowledgeSearchTool：中途再检索一次知识库
   │
   └─ 回答 → CitationVerifier 逐句核对 → done 帧覆盖 → 前端渲染引用
```

关键点：

- **`QueryRewriter`（指代消解）发生在检索侧，不在回答侧，且一次产出三处共用。** 病在「那它呢」「这个和布洛芬能一起吃吗」这类追问字面上没有任何实体，向量化它、BM25 匹配它、拿它召回情节记忆，结果都是噪声。而只有候选池直接吃消息原文的三处看不见历史：**RAG 检索、情节记忆召回、意图路由**。三处各改一次的话，同一个追问会拿到三个略有差异的查询——路由判去了售后流程、检索却在查另一个东西，而两边日志都正常。
- **`QueryRewriter` 条件触发，不是每轮都改**：只有存在历史（非首轮）且模型具备推理能力时才改写（首轮没有可消解的指代，改写是纯浪费；无 Key 的 Mock 路径直接退回原文）。**任何失败都降级回原文**——宁可少改不可改错：一个被改坏的查询会让检索拿到错误证据，而那比拿不到证据更糟（后者会拒答，前者会自信地答错）。**改写结果只进检索侧，不进回答侧**：执行图收到的仍是用户原话。
- **入口检索只发生一次**，所以中途发现有东西要查，得靠 `KnowledgeSearchTool` 再来一次。这个工具补的正是多跳问题的后半跳：先查订单知道买家买的是鱼油，才想起该查"鱼油与华法林的相互作用"；一轮 ReAct 里信息是逐步长出来的，而检索机会只在起点发了一次。
- **`KnowledgeSearchTool` 的段落不带 `[n]` 编号**，要求以《文档名》在句末标出处。**出处形式与编号证据刻意分开**：让模型给工具片段标编号，轻则越界编号被引用校验摘除，重则逼它编一个不存在的编号。
- **`InteractionCheckTool` 输出里最要紧的不是风险条目，是"没查到"和"没收录"的分开表述。** 这两种情况在界面上都表现为"没有风险条目"，而对一个药品营养场景来说它们是相反的两句话：前者是"查过了，没发现"，后者是"系统里根本没这个东西"。一旦模型把后者念成前者，用户就会以为可以放心同服。所以它对 `不可用 / 未收录 / 已收录` 三种状态各给一段不同的措辞和不同的指令。
- **图谱召回与相互作用查询是两条路**：前者是回答侧增强召回，认得出多少实体就给多少依据，认不出返回空，**不承担下结论的责任**；后者是用户明确点了名要查的东西，逐项下结论。

## 7. 图谱与 RAG 的分工

这是最常被问、也最容易回答错的一点。两者不是"两套知识库"，而是**同一批事实源的两种索引**：

| | RAG（向量 + BM25） | 知识图谱 |
|---|---|---|
| 索引的单元 | 文档的**切片**（文字） | 实体与**关系**（结构化） |
| 依据长什么样 | 原文段落 | 三元组 + **逐字引文** |
| 擅长 | 文字里写了、且措辞/语义对得上 | **实体编号、多跳、跨文档组合** |
| 召回不了时 | 问的是 SPU 编号，文档里只有商品名 → 两路都接不上 | 问的实体图上没有 → 返回空 |
| 谁来用 | Agent 主链路的 RAG、`KnowledgeSearchTool` | 检索第三路、`InteractionCheckTool`、图谱页 |
| 事实源 | `knowledge_document` / `knowledge_chunk` | 同一批文档 + 模型抽取 + 校验入库 |

**关系与信息支撑**：图谱的每一条边都以**某篇文档某一片里的逐字引文**为信息支撑，入图前经 `TripleValidator` 校验（端点出自本文 + 引文逐字存在）。所以图谱不是"另一套知识"，而是**对同一批文档做的结构化抽取**——它的价值在于把散落在不同文档里的关系连起来，回答"文本检索够不着"的那类问题。

**溯源的一致性**：因为图谱边保留了 docId/chunkId/偏移/引文，它的依据可以**渲染成和普通切片一模一样的形式**，于是"图谱推导"和"文档原文"在溯源上是同一套机制，用户点任何一条引用都落到同一张原文页面。

## 8. 关键失败模式与设计对策（速查）

| 失败模式 | 症状 | 对策 | 落点 |
|----------|------|------|------|
| 图谱不可用被读成"没有风险" | 故障 → 相反的安全结论 | 读接口返回 503；`/interactions` 回 `available=false` | `GraphController` |
| 抽取 JSON 被截断 | 整篇文档边全丢，报告失败数 0 | `max_tokens=4096`；解析失败返回 `null` 不发请求 | `KnowledgeGraphBuilder` |
| 商品目录拉取失败 | 商品边被整体替换删掉，失败数 0 | 目录为 `null` 则整批不跑 | `KnowledgeGraphBuilder.build` |
| 模型凭常识补边 | 有引用但引用无关 | 端点必须出自本文 + 引文逐字存在 | `TripleValidator` |
| Neo4j `MERGE` 无约束 | 图静默裂开，时好时坏 | 建唯一约束 `:Entity(name)` | `KnowledgeGraphStore` |
| 语料改名/换目录 | 历史孤儿切片占 topK | 向量库整份清空重建 | `KnowledgeIndexer.rebuild` |
| 停用文档仍被检索 | 下架内容照样出现 | 单篇增量走"只删不写" | `KnowledgeIndexer.rebuildOne` |
| 引用指向不存在的切片 | 点开无处可去，两边日志正常 | 文档页显式报警 `danglingChunk` | `KnowledgeDocView` |
| 缩量后模型答对却自我否定 | "相关度不足，不能作为权威依据" | 图谱依据在场时判定不低于 SUFFICIENT | `EvidenceGate` |
| 模型不标引用 | 无出处的断言与有出处的一样好看 | 生成后逐句核对 | `CitationVerifier` |

## 9. 可配置项：三个开关与它们的行为差异

影响这条链路行为的开关只有三个，都支持环境变量覆盖，默认值就是当前线上行为。

| 配置 | 默认 | 行为差异 |
|------|------|----------|
| `envoymart.rag.graph-recall.enabled`（`RAG_GRAPH_RECALL`） | `true` | 关掉时检索退回 **BM25 + 向量两路**，图谱路传 `null`，行为与只有两路时**逐字节一致**，与历史完全一致 |
| `envoymart.rag.query-expansion.enabled`（`RAG_QUERY_EXPANSION`） | `true` | 关掉时每次检索**少一次模型调用**（不产生 HyDE 与角度改写），检索按原句进行；返回的是 `HybridRetriever` 实例本身，不是"什么都不做"的副本 |
| `envoymart.rag.auto-index` | `true` | 关掉时启动不建索引，检索**恒为空**，AI 回答会全部落到"知识库中没有相关依据"。只给测试与"起个空壳排查"用 |

> 前两个开关存在的理由是**可证否**：同一句话，开与关各答一次，这条路的增益必须能被看见或被推翻，而不是靠一段架构描述让人相信它有用。

另外两处与"改了不生效"直接相关的行为：

- 改完知识库文档**不会自动生效**——事实源与派生索引之间需要一次显式重建（管理台保存后会自动触发单篇增量；批量改动才需要点"重建索引"）。
- `POST /knowledge/internal/reseed` 是**开发期**入口：改了 `resources/knowledge/*.md` 不想重启服务时调它一次。线上改文档走管理接口，不是改文件。

## 10. 名词对照（读代码时最容易对不上的几个词）

| 本文用词 | 代码里的落点 | 说明 |
|----------|-------------|------|
| 事实源 | `knowledge_document` / `knowledge_chunk` 表、`product_*` 表 | 唯一权威；派生物都能从它重建 |
| 派生物 | Milvus 向量集合、BM25 快照、Neo4j 图谱 | 由重建产生，不可反向作为事实源 |
| 切片 / 切片级 | `DocumentChunk`、`chunkId` | 检索与融合的**归一粒度**。文档级入口把整篇包成一个切片（`chunkId = docId`） |
| 三元组 | `GraphTriplePayload` / `Triple` | 头实体 + 关系 + 尾实体（+ 可选 effect + 引文） |
| 有出处的三元组 | `GroundedTriple` | 通过校验、且已锚定到原文偏移的那一种 |
| 实体链接 | `KnowledgeGraphBuilder.linkProducts` | 把模型写出的商品名/键对齐到真实 SPU 编号 |
| 证据门 | `EvidenceGate` | SUFFICIENT / WEAK / NONE 三档判定 |
| 拒答门 | `EvidenceGate` 的别名 | 同一个类；"拒答"指的是 NONE 档时不给证据、要求模型明说没查到 |
| 图谱依据 | `SOURCE_GRAPH`、`GraphEvidenceRetriever` | 不是文档原文段落，而是由图上的关系推出来的依据（正文里带逐字引文） |
| 图谱召回 | `GET /knowledge/graph/recall` | 增强召回，不下结论 |
| 相互作用查询 | `GET /knowledge/graph/interactions` | 逐项下结论，包含"没有收录" |

## 11. 想自己核对时，用这些命令

```powershell
# 图谱规模与各类关系条数
curl "http://127.0.0.1:8080/knowledge/graph/stats"

# 某个实体的邻域（商品传 SPU 键，其余传中文名）
curl "http://127.0.0.1:8080/knowledge/graph/entity?name=spu7&depth=1"

# 图谱召回（检索第三路的原始产出）
curl "http://127.0.0.1:8080/knowledge/graph/recall?query=SPU7%20%E5%92%8C%E5%8D%8E%E6%B3%95%E6%9E%97&limit=5"

# 某篇文档的全文 + 切片索引（溯源目的地）
curl "http://127.0.0.1:8080/knowledge/documents/KB-0006"

# 某一片原文（引用回跳的唯一入口）
curl "http://127.0.0.1:8080/knowledge/chunks/KB-0006_0"
```

界面上：

- 图谱：`#/knowledge/graph?root=spu7&depth=1`
- 文档与高亮：`#/knowledge/KB-0006?chunk=KB-0006_0`
- 知识库管理（上传说明书 + 重建索引）：管理端 → 知识库管理
