# 演示数据设计

> 结构与代码保持通用电商形态，**填充数据垂直化到营养健康领域**。
> 这样做的收益是双向的：类目树、SKU、订单、售后等**模型设计讲的是通用方案**，而面试官**看到的数据是他熟悉的领域**——并且营养品的成分→人群→禁忌关系本来就是真实的图结构，知识图谱的必要性无需虚构。

## 一、设计原则

1. **数据必须能支撑演示脚本**——每一个精心设计的案例（多跳推理、拒答、政策判定）都要有对应的数据落位，不能等演示时临时编
2. **边界案例是资产**——刻意设计"知识库里查不到"的问题，让拒答能力可以被演示，而不是只在代码里存在
3. **不用真实品牌与药品名**——商品与品牌虚构，但**成分、营养素、相互作用机制遵循真实营养学**。虚构的是商品，可信的是知识
4. **图谱的边要带证据**——每条相互作用关系回指知识库文档，使图谱推理的每一步也能溯源

## 四、知识库语料（RAG）

约 **30 篇文档**，五类：

| 类型 | 数量 | 示例标题 | 用途 |
|---|---|---|---|
| **产品说明书** | 12 | 《元气元素维生素D3软胶囊 产品说明书》 | 商品参数问答的溯源来源 |
| **成分与营养素说明** | 6 | 《维生素K的生理功能与食物来源》 | 图谱推理的文本依据 |
| **药物-营养素相互作用** | 5 | 《抗凝药物与维生素K的相互作用》 | **演示案例 A 的证据** |
| **人群服用指南** | 4 | 《乳糖不耐受人群的钙补充方案》 | **演示案例 B 的证据** |
| **售后服务政策** | 3 | 《营养保健类商品退换货政策》 | 政策判定 + 溯源 |

### 关键设计：长文档承载切分能力

产品说明书与政策文档**写成真正的长文档**（3000–8000 字，含章、条、段落结构），这样才能演示：

- **结构分层切分**——章 → 条 → 段 → 句逐级下钻，条款不被切断
- **切片级检索**——同一文档内多个切片各自被召回并被 RRF 融合
- **位置前缀溯源**——切片自带 `《文档》 > 章 > 条` 语境，脱离原文仍自证

原实现的 15 篇语料全是短文档（每篇恰好一片），切分改造因此**在线上零收益**——这次要把语料长度做上去，让改造的价值真正可演示。

| 演示案例 | 需要的证据文档 | 关键内容 |

## 五、知识图谱（Neo4j）

### 节点类型

| 标签 | 属性 | 示例 |
|---|---|---|
| `Supplement` | 名称、类目、形态 | 维生素K2软胶囊 |
| `Ingredient` | 名称、别名 | 维生素K2 / 甲萘醌 |
| `Nutrient` | 名称、推荐摄入量、单位 | 维生素K、钙、维生素D |
| `Drug` | 名称、药物类别 | 华法林 |
| `Population` | 名称 | 孕妇、乳糖不耐受人群、老年人、儿童 |
| `Condition` | 名称 | 糖尿病、高血压、骨质疏松 |
| `Purpose` | 功效诉求 | 补钙、助眠、增强免疫、骨骼健康 |
| `Policy` | 政策名称、文档编号 | 营养保健类商品退换货政策 |

### 关系类型

| 关系 | 方向 | 属性 |
|---|---|---|
| `CONTAINS` | Supplement → Ingredient | 含量、单位 |
| `PROVIDES` | Ingredient → Nutrient | |
| `INTERACTS_WITH` | Ingredient → Drug | **严重程度**、机制说明、**doc_ref** |
| `CONTRAINDICATED_FOR` | Supplement → Population | 原因、**doc_ref** |
| `SUITABLE_FOR` | Supplement → Population | |
| `ADDRESSES` | Supplement → Purpose | 证据强度 |
| `DEPLETES` | Drug → Nutrient | 机制 |
| `SUBSTITUTE_OF` | Supplement → Supplement | 替代理由 |
| `GOVERNED_BY` | Supplement / Category → Policy | |

**每条关系带 `doc_ref` 回指知识库文档编号**——图谱给出的结论同样可溯源，这是"知识图谱 + 强溯源"的结合点。

### 关键数据（演示案例 A 的完整推理链）

```
(本草纪维生素K2软胶囊)-[:CONTAINS]->(维生素K2)
(维生素K2)-[:PROVIDES]->(维生素K)
(维生素K)-[:INTERACTS_WITH {severity:"HIGH", 
     mechanism:"维生素K是华法林的作用靶点，外源补充可拮抗其抗凝效果",
     doc_ref:"KB-0007"}]->(华法林)
(华法林)-[:DEPLETES]->(维生素K)
```

**查询"我在吃华法林，能吃维生素K2吗"的推理路径**（4 跳）：

```
Question → [实体识别] → 维生素K2 + 华法林
  → (维生素K2)-[:CONTAINS]->(维生素K)          第 1 跳
  → (维生素K)-[:INTERACTS_WITH]->(华法林)       第 2 跳  ← 关键
  → 取 severity + mechanism + doc_ref          第 3 跳
  → [doc_ref] → 知识库检索 → 引用原文           第 4 跳
```

**这条链证明了什么**：知识库里**没有任何一段文本同时提到"本草纪维生素K2软胶囊"和"华法林"**——向量检索无论怎么调，都召不回这条结论。**知识藏在关系里，不在文本里。** 这是知识图谱必要性的实证，而不仅仅是论证。

## 六、拒答案例（必须刻意设计）

拒答能力要能在面试现场演示，就必须**预先准备好明知查不到的问题**：

| 问题 | 为什么库里没有 |
|---|---|
| "这个鱼油对阿尔茨海默病有没有预防作用" | 知识库只收录产品说明与营养学基础，不含疾病治疗研究 |
| "孕妇能不能吃这个辅酶Q10" | 未收录该人群的服用指南（厂商说明书也未涉及） |
| "这个益生菌和我吃的某个处方药会不会冲突" | 未收录该药物对应用户的相互作用数据 |
| "我能用这个蛋白粉替代透析病人的营养方案吗" | 属医疗行为，知识库明确不覆盖 |

**期望行为**：系统回答"**知识库中没有检索到支持该结论的依据**"，并提示咨询医生或药师——**而不是给出一个听起来合理的答案**。

同时准备**反例**（库里有的相似问题），用于对比演示：

| 对照 | 问 | 期望 |
|---|---|---|
| 有依据 | "孕妇能不能吃这个维生素D3" | 答"可以"，引用说明书中适用人群条目 |
| 无依据 | "孕妇能不能吃这个辅酶Q10" | 拒答，说明未收录该人群数据 |

**这一组对比是整场演示里最有说服力的一段**——同一类问题，一个有答案一个有边界，直接证明拒答不是"什么都不敢答"。

## 七、演示脚本

按这个顺序走一遍，覆盖全部能力点：

| 步 | 操作 | 展示的能力 |
|---|---|---|
| 1 | 登录 → 首页浏览营养保健类目树 | 类目树、布局 |
| 2 | 搜索"孕妇 补钙"→ 按价格/品牌筛选排序 | ES 多字段检索、筛选聚合 |
| 3 | 进商品详情 → 选规格（多 SKU）→ 加购 | SPU/SKU、属性展示 |
| 4 | 购物车 → 下单 → 支付 | 完整交易链路 |
| 5 | 问"我乳糖不耐受，能吃这个碳酸钙片吗" | **人群禁忌判定 → 推荐替代品** |
| 6 | 点击回答中的引用 → 跳政策/说明书原文并高亮 | **强溯源** |
| 7 | 问"我在吃华法林，能吃维生素 K2 吗" | **图谱 4 跳推理 + 风险提示 + 溯源** |
| 8 | 问"这个鱼油对阿尔茨海默病有用吗" | **拒答（有边界）** |
| 9 | 申请退货 → 政策引擎判定拆封商品不可退 | **规则判定 + 引用政策条文** |
| 10 | 打开知识库台 → 图谱可视化 → 查看评测报告 | **知识层与量化指标** |

**第 5–9 步是主秀**：它们共同证明这个系统**不是一个会说话的搜索引擎**——它有知识、有边界、每一步都能指回原文。
