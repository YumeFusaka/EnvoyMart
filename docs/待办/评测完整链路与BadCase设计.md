# 评测完整链路与 Bad Case 设计

> 状态：未实现，作为下一会话的实现依据。
> 更新日期：2026-10-08

## 目标

补齐两类能力：

1. 检索质量评测和回答质量评测的每条样本都展示可核验的真实执行链路，能够回答“这一条结果是怎样产生的”。
2. 智能助手支持针对单条助手回答的点踩反馈，把用户明确标记的问题保存为真实 Bad Case，供后续排查、评测集治理和面试演示使用。

本项完成后，评测页面只读已保存快照；检索和回答评测各只允许人工明确触发一次真实重测，避免页面刷新或验收重复消耗模型额度。

## 当前代码事实

- 智能助手已有回答、引用、工具轨迹、检索查询、扩写、用量和请求 ID 的响应字段，历史消息也会保存 `ChatResponse` 快照到 Redis。
- 当前没有消息级点踩接口、反馈原因模型或 Bad Case 独立存储。
- 检索评测后端 `CaseReport` 已保存 `RetrievalTrace`、扩写和最终 evidence，但检索页只展示最终文档和命中状态，没有把这些字段按阶段展开。
- 回答评测后端 `CaseResult` 已保存 evidence、retrievalQuery、expansion、toolExecutions 和 retrievalTrace，但页面只展示回答、依据和判定，缺少完整链路视图；当前快照没有的字段必须显示“未记录”，不能用当前运行数据补历史。
- 评测快照位于 `backend/ai-service/data/eval/`，属于运行期产物，不提交到仓库。

## 范围

### 包含

- 检索评测逐条链路展开。
- 回答评测逐条链路展开。
- 智能助手消息级点踩、原因选择、关联消息选择、可选说明、幂等提交和撤销。
- Bad Case 独立持久化、归属校验、脱敏和结构化日志。
- 相关后端单测、前端类型检查和目标 UI 验收脚本。
- 代码验证通过后，检索与回答评测各进行一次真实重测。

### 不包含

- 不保存整个长会话作为一个 Bad Case。
- 本项不实现管理端 Bad Case 列表、导出或人工标注页面；先保证数据契约可供后续治理。
- 不在页面访问或 UI 验收脚本中自动触发计费模型。
- 不调整检索参数、提示词策略或评测口径来刷指标。

## Bad Case 设计

### 反馈对象

反馈绑定 `assistantMessageId`，而不是只绑定 `sessionId`。用户点踩的是当前回答，长会话中的其他轮次默认不进入样本。

前端打开反馈面板后：

- 默认勾选当前用户问题和被评价的助手回答；
- 展示当前回答附近的消息列表，用户可额外勾选真正相关的上下文片段；
- 支持多选固定原因：事实错误、没有回答问题、依据不相关、工具执行错误、回答难懂/过长、其他；
- 支持可选文字说明；
- 保存前明确显示将被记录的消息数量和回答摘要。

### 保存内容

Bad Case 记录至少包含：

| 字段 | 说明 |
|------|------|
| `badCaseId` | 服务端生成的稳定标识 |
| `userId` | 归属键，仅用于权限隔离，不展示给其他用户 |
| `sessionId` | 来源会话 |
| `assistantMessageId` | 被评价的助手消息，幂等键的一部分 |
| `userMessageId` | 与回答直接对应的用户问题 |
| `selectedMessageIds` | 用户明确勾选的上下文消息 ID，不能自动扩展为整会话 |
| `reasonCodes` | 固定原因枚举，多选 |
| `comment` | 可选补充说明，限制长度并脱敏展示 |
| `question` | 当前问题快照 |
| `answer` | 当前回答快照 |
| `responseSnapshot` | 完整 `ChatResponse` 快照：工具、依据、扩写、检索、用量、requestId 等 |
| `createdAt` / `updatedAt` | 创建和更新时刻 |
| `status` | `ACTIVE` 或 `REVOKED` |

不得保存 Authorization、Cookie、令牌、原始请求头或内部密钥。工具入参和返回值沿用现有脱敏规则；失败日志只记录 user/session/message 的摘要和错误类型。

### 持久化与接口

复用 `ChatHistoryStore` 的 Redis 基础设施，但使用独立 key 前缀，不能把反馈写回聊天历史列表。TTL 与会话历史保持一致，避免产生永久个人数据。

建议接口：

- `PUT /ai/sessions/{sessionId}/messages/{messageId}/bad-case`：创建或幂等更新当前用户对该回答的反馈；服务端从消息历史读取权威 `ChatResponse`，客户端只提交原因、说明和选择的消息 ID。
- `GET /ai/sessions/{sessionId}/messages/{messageId}/bad-case`：读取当前用户自己的反馈状态，用于刷新页面后恢复按钮状态。
- `DELETE /ai/sessions/{sessionId}/messages/{messageId}/bad-case`：撤销反馈，保留记录并改为 `REVOKED`，不物理删除。

服务端必须校验：会话归属、助手消息归属、用户问题归属、所选消息 ID 属于同一会话且在允许的历史窗口内。重复提交覆盖同一记录，不能生成重复 Bad Case。

## 评测完整链路

### 检索质量页

逐条明细默认折叠，展开后按以下顺序展示：

1. 输入：原始 query、stratum、caseId、期望文档；
2. 查询处理：最终检索 query、HyDE 假想答案、角度改写及 `applied` 状态；
3. 三路候选：向量、BM25、图谱候选数量；如果某一路没有执行或历史快照没记录，分别显示对应状态；
4. 融合与重排：fusedCandidates、rerankedCandidates、rerankQuery、是否实际执行 rerank；
5. 依据：最终进入 prompt 的切片、标题、章节、来源、graphBacked 和顺序；
6. 结果：最终文档排名、命中位次、图谱路径命中、失败原因；
7. 元数据：采集时间、链路描述、耗时、索引/模型版本（只有快照真实保存时才展示）。

不能把最终 `retrievedDocIds` 改名成“候选链路”。缺少中间字段时必须显示“该快照未记录”。

### 回答质量页

逐条明细默认折叠，展开后按以下顺序展示：

1. 输入和输出：caseId、问题、完整回答、延迟和错误状态；
2. 工具轨迹：工具名、脱敏入参、成功/无数据/失败、耗时、结构化输出摘要；
3. 检索链路：retrievalQuery、向量/BM25/图谱候选计数、融合数、重排数、重排状态；
4. 扩写：HyDE、角度改写、是否实际生效；
5. 依据：证据切片、标题、位置、来源和引用角标跳转；
6. 判定：证据门级别与理由、未支撑句、错引、越界引用、过拒/漏拒、多跳结果和根因；
7. 元数据：requestId、promptVersion、pipelineVersion、模型用量和快照时间。

页面必须区分“真实执行为空”“执行后无结果”“历史快照未记录”三种状态。旧快照只按已有字段展示，不能请求当前 Agent 重新补齐。

## 前端交互要求

- 点踩按钮只出现在助手消息上，具有明确 `aria-label`、聚焦态和提交中/失败可重试状态。
- 已提交状态在重新加载会话后保持；再次点击可进入编辑或撤销流程，不能无提示重复写入。
- 反馈面板不遮挡回答链路，长文本和多条消息可滚动，移动窗口可用。
- 评测链路用原生 `details` 或等价可访问折叠控件；默认折叠，展开后不改变指标数字。

## 测试与验收

### 后端

- Bad Case 保存单测：创建、幂等更新、撤销、用户隔离、消息选择范围、快照脱敏。
- 评测快照兼容单测：新字段序列化、旧快照缺字段不报错。

### 前端

- `vue-tsc --build` 和 `pnpm build`。
- 智能助手 UI：点踩入口、原因选择、消息勾选、保存状态、撤销/重试。
- 检索评测 UI：每条可展开，链路阶段和缺失字段提示存在。
- 回答评测 UI：工具、检索、扩写、依据、判定和元数据均可展开查看。

### 一次性真实重测

所有代码和 UI 验证通过后：

1. 人工触发一次检索质量评测，等待完成并保存快照；
2. 人工触发一次回答质量评测，等待完成并保存快照；
3. 记录两次运行时间、样本数、失败数、链路版本和最终指标；
4. 页面验收只读取快照，不再次触发模型。

## 完成标准

- 用户可以对单条回答点踩并保存真实 Bad Case，刷新后状态仍在，且不会混入整段会话。
- 两个评测页的每条样本都能从结果回溯到工具、检索、扩写、依据和判定。
- 缺失历史字段有明确提示，页面不编造执行链路。
- 相关确定性测试和 UI 验收通过后，才进行唯一一轮真实重测。
