## 〇、总原则（用户 2026-10-06 拍板，冲突时以它为准）

1. **评测页必须展示真实链路下的效果**。真实链路 = 用户输入 → query 改写（口语改写 + 扩写 + HyDE）
   → 三路并行（向量 + BM25 + 知识图谱）→ RRF → rerank → 写入 prompt。
   **展示出来的如果不是现在真正给用户用的那条链路，这页就没有意义。**
2. **不要重跑**。重跑既增加开销又没有意义；**把真正实测跑出来的那一次结果固化成快照展示**。
3. **测试集就是生产环境本身**：用真正在跑的文档、知识图谱、向量库作为评测语料；
   **数量不够就扩充文档**（扩充是真实扩充知识库，不是造评测专用夹具）。
4. 本阶段只做**效果展示**，不借改造之机调检索参数（调参需要先有基线，基线正是本阶段的产出）。

## 一、为什么会有这份清单：现状与真实链路的偏离

### 1.1 真实链路（已逐环节核实源码，2026-10-06）

| 环节 | 生产实现 | 位置 |
|------|----------|------|
| 口语改写 / 指代消解 | `QueryRewriter` → 四个消费方共用同一份改写句 | 检索是其中之一 |
| 扩写：HyDE 假想答案 | **只走语义路**（`vectorStore.search(ex.hypothetical())`） | `HybridRetriever.retrieveWithOutcome` |
| 扩写：角度改写 | **只走词法路**（`bm25Search(angle)`） | 同上 |
| 路 ① 向量 | `vectorStore.search(query, topK*2)` | 同上 |
| 路 ② BM25 | `bm25Search(query)` | 同上 |
| 路 ③ 知识图谱 | `GraphEvidenceRetriever`，打**线上 Neo4j**，**只认原句**（不吃改写） | `AiAgentConfig.hybridRetriever` |
| RRF 融合 | `rrfMerge(ranked, graphChunks, topK * RERANK_CANDIDATES)`，k=60，三路**平等**入池 | `HybridRetriever` |
| Rerank | `DashScopeReranker`（百炼 `gte-rerank-v2`），无 Key 降级 `Reranker.NOOP` | `AiAgentConfig.dashScopeReranker` |
| 写入 prompt | `RetrievalOutcome(kept, graphKeys, graphBacked, expansions)` → `SimpleRAGEngine` | `ai-service` |

装配：`AiAgentConfig.hybridRetriever` → `Retriever retriever(...)` 包 `MultiQueryRetriever`（扩写装饰器，
两个检索入口都覆盖）。图谱路有开关 `envoymart.rag.graph-recall.enabled`。

### 1.2 检索页 `/knowledge/eval` 实际跑的东西（**偏离**）

`RetrievalEvalRunner.run()`：

    new HybridRetriever(new InMemoryVectorStore(new SimpleEmbeddingService()), EvalFixtures.DOCS)
    Retriever expanded = new MultiQueryRetriever(base, new RecordedQueryExpander())

逐项对照：

| 真实链路的环节 | 检索页实际 | 缺什么 |
|----------------|-----------|--------|
| 真实 embedding | `SimpleEmbeddingService`（**伪随机哈希向量**） | 真实向量未接 |
| 知识图谱路 | 无 | **第三路缺失** |
| RRF 多路融合 | 只有向量 + BM25 两路 | 融合不完整 |
| Rerank | 无（未构造 `Reranker`） | **重排未跑** |
| HyDE | `RecordedQueryExpander` 预录夹具，只有角度改写 | **HyDE 不生效** |

**结论：这页测的是一条不存在的链路。** 语义档 35% 不是「系统水平」，是「无真实向量、无重排」时的下限。

### 1.3 回答页 `/knowledge/eval/answer`（**链路正确，主次颠倒**）

- 「线上真跑」栏：`GroundingLiveEvalService` 注入真实 `Agent`，`runCase` 直接 `agent.chat(...)`
  → **就是用户用的那条链路**（真实模型 + 真实知识库 + 真实图谱 + 完整检索）。
- 「离线重放」栏：喂冻结快照，测判定逻辑有没有退化，**进 CI**。
- 问题不在链路，在**排序**：`Report(offline, live)` 里 offline 在前，页面也先展示离线。
  读者会把「某次采集时的模型」读成「当前系统」。

### 1.4 评测基准与生产语料分离

| | 评测夹具 | 生产环境 |
|---|---------|---------|
| 文档 | `EvalFixtures` 90 篇短文档（30~51 字/篇，每篇恰好一片） | **47 篇成篇文档 / 408 片**（KB-0001~KB-0047） |
| 图谱 | 无（夹具不在图里） | **Neo4j 5.26**（`bolt://127.0.0.1:7687`），157 实体 / 261 关系 |
| 向量库 | `InMemoryVectorStore` | **Milvus**（`SPRING_PROFILES_ACTIVE=milvus`） |
| 标注 | 120 条（对应那 90 篇） | **无** |

`EvalFixtures` 类注释自己写了：「与线上知识库是两套独立数据…不可互相推算」。
后果：**图谱路在离线评测上永远空跑**，完整链路在离线集上无法真正跑通。

## 三、讨论中已确认的关键事实（避免重复论证）

1. **真实链路形状**：用户输入 → 口语改写 + 扩写（HyDE / 角度）→ 三路并行 → RRF → rerank → prompt。
   **已逐环节对到源码**，与用户的设计完全对应。
2. **HyDE 与角度改写各走一路**：HyDE 只喂向量路，角度只喂 BM25。它们不是同一个入口，
   这解释了 P2-3「两半各自单独看都接近噪声、合起来才有增益」。
3. **图谱路只认原句**：它靠实体编号与实体名定位，改写会削弱它（代码注释写明）。
4. **图谱用的是线上真实存储**：Neo4j 5.26 容器，语料是 knowledge-service 的 47 篇真实文档。
5. **「加进去会污染」的准确表述**：不是污染数据，是**混了两套语料**——线上图谱与向量库都是
   线上服务在用的，灌评测文档会让真实检索捞到它们。**所以应该反过来：评测用生产语料。**
6. **回答页的真跑已经是真实链路**，不需要改造链路，只需要调主次。
7. **生产检索只读、不写**：评测读 Milvus 与 Neo4j，不写入，安全。
