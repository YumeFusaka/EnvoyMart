## 一、审阅结论

当前“一次性收口计划”覆盖了三类用户反馈和一部分 Agent 能力建设，但没有覆盖待优化清单中的全部工程问题。因此它不能直接作为“全量问题收口”计划执行。

必须先补入计划的高风险问题：

1. O44 短期记忆键缺少 `userId`，存在跨用户读取风险。
2. O1 高危工具的幂等前提没有落到工具契约和启动期校验。
3. O4 同一会话的并发消息、审批和断点没有互斥语义。
4. O13 `$N.field` 引用没有自动补齐 `dependsOn`，O14 没有执行前参数 schema 校验。
5. O15 `evaluate` 只能判断“是否有数据”，不能判断“数据是否回答了原问题”。
6. O26 PII 脱敏只有方向，没有日志、历史、上下文和前端轨迹的验收断言。

计划还存在以下事实和范围问题：

- 现有材料写的是 11 个 Agent 工具、4 个高危工具；计划任务 3 将新增优惠券、工单等工具，完成后必须同步工具数量、能力表、MCP instructions 和面试材料。
- 计划写“售后预览/申请/审核链路”，但当前没有 `after_sale_preview` 工具，实际是 `after_sale_apply` 加确定性售后流程。必须先确定“预览”是服务 API、流程节点还是新增工具。
- 计划任务 1/6/7 的复杂场景和回放不能替代意图评测、会话并发、拒答服从性、Bad Case 回流等专门契约。
- 计划收尾重复列出 `EnvoyMart/docs/待办/待办总表.md`，遗漏根目录深挖问答、待优化清单、简历等材料同步项。

## 四、必须优先实施的契约改动

### 4.1 身份、会话和数据隔离

**问题**

- STM 当前键只有 `stm:{sessionId}`，同一个 sessionId 被另一个用户复用时可能读到前一用户内容。
- 同一会话的两个请求可能同时读改写 sessionContext、澄清状态、审批状态或断点。
- 删除会话只清短期记忆，现场和断点仍可能继续生效。

**改动方案**

1. STM 键改为 `stm:{userId}:{sessionId}`，读取时再校验条目归属。
2. 以 `(userId, sessionId)` 建立会话级互斥；优先使用 Redis 锁或版本号 CAS，锁必须有 TTL、续期和释放失败日志。
3. 新增 `SessionLifecycle` 统一处理会话删除：先删断点，再删现场，最后删 STM 和历史墓碑；所有清理按用户和会话双重约束。
4. 断点增加 `schemaVersion`；版本不兼容时安全丢弃并记录原因，不静默降级成普通空会话。

**验收证据**

- 同 sessionId 换 userId 不能读取、复述或删除另一用户内容。
- 同一会话并发发送两条消息，状态不能出现后写覆盖先写；并发审批不能重复执行。
- 删除会话后，STM、session context、checkpoint 均不可再恢复。
- Redis 锁超时、竞争失败和释放异常都有可检索指标或日志。

### 4.2 高危工具幂等和审批令牌

**问题**

- 现有确认令牌默认允许有效期内重复提交。
- `ApprovalTokens` 的幂等工具登记不是所有高危工具的统一契约。
- `operationId` 只有进入计划的说法，没有明确跨重规划、确认重试和下游落库的生命周期。

**改动方案**

1. 扩展 `ToolDefinition`，显式声明 `requiresConfirmation`、幂等策略、幂等键来源和是否允许令牌重放。
2. `ToolRegistry` 启动时校验：高危工具未声明幂等策略则启动失败。
3. 幂等工具使用稳定 `operationId = userId + sessionId + planId + stepId`，重规划不能为同一业务动作生成新 operationId。
4. 下游写服务使用唯一约束或幂等记录裁决重复请求，不能只在 Agent 入口去重。
5. 非幂等高危操作使用 Redis/数据库一次性消费记录；不能通过注释承诺“工具幂等”。
6. 令牌校验仍强制绑定用户、动作、参数和有效期；跨 MCP 入口放宽会话绑定时必须单独标记并测试。

**验收证据**

- 双击确认、网络重试、重规划重复提交、跨入口重复提交均只有一次副作用。
- 新增一个未声明幂等语义的高危工具时，应用启动失败。
- 同一 operationId 的重复执行返回第一次结果或明确的已完成状态。
- 非幂等工具令牌第二次提交被拒绝，且无下游调用。

### 4.3 计划引用、依赖和参数契约

**问题**

- 当前执行器支持 `$N.field`，但模型仍需要手写 `dependsOn`。
- 列表引用未带下标时会默认取第一个元素；多商品写操作可能因此绑定错商品。
- 参数错误要到工具内部才暴露，重规划上下文离根因较远。

**改动方案**

1. 计划归一化时扫描全部参数引用，自动补齐引用步骤到当前步骤的 `dependsOn`，与模型声明取并集。
2. 引用自身或未来步骤直接判定为非法计划，不能进入执行。
3. 写操作引用列表必须显式下标；多元素列表使用 `$0[0].skuId`、`$0[1].skuId` 等形式；不带下标时阻断并要求澄清/重规划。
4. 明确 optional 前置步骤失败语义：被引用的 optional 步骤失败时，引用方判阻塞，不允许把占位串传入写工具。
5. plan 阶段校验字面参数；act 阶段解析引用后再次校验类型、必填项、数组形状和未知字段。
6. 工具输出中必须包含后续写操作所需的结构化 ID、规格和状态，正文只作展示。

**验收证据**

- 漏写 `dependsOn` 仍按数据依赖串行执行；无关步骤保持并发。
- 双商品计划最终绑定两个不同 SKU，每个只执行一次，不能默认取第一个。
- 引用步骤失败时不会生成带占位符的确认卡，也不会调用写工具。
- 未知参数、缺必填、类型和数组形状错误在执行前被结构化指出。

### 4.4 Agent 能力和售后语义

**改动方案**

1. 覆盖矩阵把能力分为 `UI_ONLY`、`API_ONLY`、`AGENT_READ`、`AGENT_WRITE_CONFIRM`、`UNAVAILABLE`。
2. 新增优惠券领取、购物车增删改、工单提交等工具时，统一接入确认、身份注入、幂等和权威结果复核。
3. 明确售后“预览”的真实边界：若是服务端预览 API，工具描述写 API 语义；若是确定性流程节点，不把它伪装成独立工具；只有确有用户交互价值时才新增工具。
4. 没有工具或接口支撑的能力必须返回不可执行，不允许模型用自然语言声称完成。

**验收证据**

- 每个工具至少有一条确定性契约测试和一条真实副作用验收。
- 工具清单、MCP instructions、能力矩阵、问答材料中的工具数量一致。
- 售后预览、申请、审核的接口、工具和页面名称完全一致。

### 4.5 普通回答的动作事实和 PII

**改动方案**

1. 对“已下单、已取消、已加购、已提交”等完成态动词，与当轮成功写工具和权威返回结果做确定性对账；没有成功执行就删除或改写完成态。
2. 响应增加 `source`/执行来源标识，确认轮显示“已确认执行”等可核验状态。
3. 功能路径保留真实地址和手机号；日志、trace、工具输出、前端轨迹按统一脱敏器处理。
4. 日志保留手机号尾号和地址区划即可；完整地址只允许进入用户自己的业务路径，不进入普通 INFO/DEBUG 日志。

**验收证据**

- 伪造“已完成”文本但没有成功写工具时，响应不出现完成态。
- 日志、trace、前端轨迹扫描不到完整手机号和完整地址。
- 真实结算仍能使用完整地址，不能因脱敏误伤功能路径。

### 5.3 评测快照和图谱诊断

- 使用专用稳定 DTO，不直接持久化 `DocumentChunk` 等内部对象。
- 快照使用临时文件加原子替换；区分 `NEVER_RUN`、`RUNNING`、`COMPLETED`、`SNAPSHOT_CORRUPTED`、`VERSION_INCOMPATIBLE`。
- 保留当前可用快照和带 `runId` 的历史副本；磁盘满、写中断、旧字段缺失和版本不兼容必须有确定性语义。
- 图谱拒绝记录保存原始候选、规范化前后字段、quote、阶段、原因码、批次和可重试性；统计按批次隔离，详情可追溯到原文。

## 十一、深挖问答 Q1–Q42 逐题问题覆盖

下面登记的是问答正文中“当前实现已经存在的缺陷、明确承认的不足、生产级差距和触发条件”。纯概念解释、已经验证通过且没有遗留风险的实现，不重复列为问题。

### Q1：Agent 适用边界和整体能力

- 工具仍是编译期手工注册；没有 MCP 消费端动态发现，也没有按角色限制工具可见性（对应 O9/O41）。
- 只有事后 `TokenLedger`，没有用户/会话级事前预算墙和语义缓存（O8）。
- 在线质量只有埋点，没有任务完成率、转人工率、每轮成本和在线 A/B 看板（O7/O43）。
- 没有向量语义记忆、遗忘和衰减策略（O10）。
- 当前单进程单图没有多 Agent/子图复用；这是明确的产品和架构边界，不是待办。电商导购、售后问答和受约束交易操作共享商品、订单、知识和权限上下文，引入多 Agent 只会增加 handoff、状态一致性、预算和排障成本。

### Q2：自研编排、evaluate、guardrail、recovery

- `evaluate` 只判断成功/无数据，不能判断工具结果是否真正回答了原问题（O15）。
- 工具、计划和会话预算静态硬编码，未按任务复杂度和租户配额动态化（O8）。
- 同一会话没有并发互斥，读改写、审批和断点都可能发生覆盖或竞态（O4）。
- 确认令牌可在有效期内重复提交，高危工具幂等只是注释假设，没有契约校验（O1）。
- recovery 没有命中率、恢复成功率、确认放弃率等指标（O7/O21）。
- 项目总览仍有旧的 `approved=true` 机制描述，材料和代码存在漂移（O41）。

### Q3：意图判断、切换和指代

- 推荐候选从回答正文正则推导，未把 `recommendedProducts` 结构化字段作为唯一事实来源（O2）。
- 领域关键词表会把“买过的东西还没到”误判为商品检索；需要同义扩展或确定性 embedding 领域相似度（O5）。
- 改写、路由、规划存在重复模型调用，路由没有规则预筛，改写与路由没有合并（O6）。
- 路由、切换、澄清、drift 没有标注集、回流和指标（O3/O21）。
- 澄清没有硬性轮次上限，用户一直改口时可能持续消耗调用（补充 S21）。
- 会话上下文是单槽，插问后原任务只能依赖历史恢复；话题栈是产品驱动的未实现能力（O12）。

### Q4：复杂任务拆分和计划执行

- 引用没有自动补 `dependsOn`，依赖正确性仍依赖模型记忆（O13）。
- 计划阶段没有参数 schema 预校验，错误在工具内部才暴露（O14）。
- 计划是静态对象，执行中只能整环重规划，不能安全动态插步；审批载荷和幂等语义尚未覆盖动态计划（补充 S01）。
- 同批虚拟线程没有按下游设置显式并发上限或舱壁，可能集中冲击同一服务（补充 S07）。
- evaluate 看不到已消耗的 token 和成本，不能做预算感知的继续/收尾判断（O8/O22）。
- 多个写操作没有跨服务补偿事务；当前只有确认、幂等和结果回传，没有 Saga/补偿语义（补充 S01）。

### Q5：长短期记忆设计

- STM 键缺少 `userId`，同 sessionId 可跨用户复述（O44，应升 P0/P1）。
- 感知记忆没有生产写入方；`MemoryTrace` 已下发但前端和脚本没有消费（O19，补充 S19）。
- `importance` 在生产沉淀链路没有写入，显式重要性分支实际上不生效（O18）。
- 情节记忆无时间衰减，事实性问题也可能无条件注入个人偏好（O10）。
- 记忆来源只有 `previousValue`，缺少 source message、时间和原文锚点，无法完成“我没说过”的举证和定点删除（补充 S02）。
- 记忆只有功能性存取测试，没有召回准确率、错误记忆率和开关对照实验（补充 S03）。
- `turnCounters` 未按用户和会话完整隔离，当前仅因单租户语义暂时可接受（补充 S19）。

### Q6：记忆压缩

- 历史窗口外的原文直接丢弃，没有归档层，无法纠错、审计或重新抽取（O20）。
- 结构化抽取没有保真评测，否定词、限定词和过度泛化可能静默进入记忆（O20/S03）。
- token 估算刻意高估，但没有“估算值与模型实际 usage”的偏差对账（补充 S04）。
- 截断按字符/消息 FIFO，没有按句子、段落和结构边界做语义化降级（补充 S04）。
- `importance` 尚未有生产写入，不能直接把淘汰策略升级成重要性排序（O18）。

### Q7：反思

- critique 只服务当次重规划，失败分类没有聚合指标和改进闭环（O21）。
- 已证伪的检索路径没有结构化传递到下一轮，模型可能重复走已经失败的路径（补充 S01）。
- 没有 Reflexion 式跨轮反思记忆；当前不做答案自评是确定性设计选择，不应包装成已有能力。

### Q8：上下文工程

- 七个分段预算没有总账本，无法知道本轮总 token、各段占比和谁触发了裁剪（O22）。
- 上下文组装没有脱敏 debug 出口，bad case 排查只能依赖零散日志（补充 S04）。
- 观测和知识段存在字符截断，未按结构边界降级（补充 S04）。
- 提示词是代码常量，没有统一 PromptRegistry、自动版本 diff 和结果关联（补充 S05）。

### Q9：多轮状态、中断和恢复

- 删除会话只清 STM，不清 session context 和 checkpoint，旧任务可能在 TTL 内复活（O23）。
- 同会话并发恢复没有互斥，可能同时消费同一现场（O4）。
- checkpoint 缺少 schema 版本演进策略，字段变化可能被 Jackson 静默忽略（补充 S02）。
- recovery 命中、保存失败、恢复成功率没有指标（O7/O21）。

### Q10：评测、Trace、Guardrail、AI Eval

- 24 条离线夹具样本量小，置信区间宽；模型、语料和判定链变化后没有自动重采/重校准触发（O28）。
- 规则评测抓不住“引用存在但语义转述失真”，需要人审或独立参考轨，不应把模型自评当门禁（补充 S03）。
- 各道 guardrail 没有拦截率、误杀率和覆盖率指标（补充 S06）。
- Bad Case 追加集已能导出但离线/在线评测不消费（O29）。
- 评测页面重构后旧脚本仍断言已删除的选择器和数字（O27）。

### Q11：循环、重复和震荡

- LoopGuard 预算静态，单步任务过宽、复杂多跳过窄（O8）。
- 签名主要是规范化 JSON，语义相同但字面略变的调用仍可能绕过重复判定（补充 S01）。
- MCP 护栏是进程内固定窗口，多实例会放大配额且无法跨实例识别震荡，状态也无淘汰（O24）。

### Q12：延迟和 Trace

- AgentGraph 没有 plan/retrieve/act/evaluate/replan/answer 节点级 Observation，无法直接看到节点耗时瀑布（补充 S06）。
- 没有 P95/P99、首 token、节点耗时和降级率 SLO 告警（O43/S06）。
- 出站依赖没有统一的超时、重试、熔断和舱壁策略；LLM 侧无熔断（补充 S07/S22）。
- 60 秒整体超时只能硬杀，无法区分首 token 超时和整体超时，也没有长尾渐进展示和成本止损（补充 S06）。

### Q13：任务幻觉

- 普通轮仍需要把“已下单/已取消/已加购”等完成态与成功写工具对账（O25）。
- 响应缺少明确的 `source`/执行来源标识，用户无法区分确认执行、模型生成和 fallback（O25）。
- 后置核对以删句为主，可能连同句子中的正确部分一起丢失；需要标记/折叠等更细的呈现策略（补充 S18）。

### Q14：数据库、越权和敏感信息

- PII 会进入原始消息日志、工具输出日志、模型上下文、历史和前端轨迹，缺少分路径脱敏验收（O26）。
- 内部端点依赖“网关 404 + 端口够不着”，直连服务端口时可能无凭证调用；静态共享 token 无轮换（O30）。
- 数据库使用单一高权限账号，没有运行账号/迁移账号/读写副本分层（补充 S08）。
- 行级权限依赖每处手写 `user_id` 条件，没有结构性拦截忘记租户条件的查询（补充 S08）。
- 当轮用户输入和工具输出没有统一的注入检测/数据声明（O40）。

### Q15：文档存储和切分

- 当前 Markdown/front-matter 形态的切分链没有 PDF、扫描件和表格版面解析能力，上传能力不开放（Q34/S13）。
- 切分参数、切片质量和切片级/文档级收益缺少持续校准触发条件（O28/S15）。

### Q16：向量数据库和性能

- 索引类型和度量依赖 SDK 默认值，缺启动时生效配置和升级回归（O32）。
- embedding 重建逐片调用，语料增长后耗时线性放大，没有批量和断点语义（O31）。
- 没有检索缓存、高频问题会重复支付扩写和重排成本（O8）。
- 没有切片数到延迟的容量曲线，也没有多知识库/多租户隔离方案（O32/S11）。
- 一致性等级没有按知识集合和记忆集合区分，写后读与吞吐取舍尚未量化（补充 S11）。

### Q17：RAG 工作流

- `needRetrieval` 没有独立评测，误判跳过会被总指标稀释（O33）。
- 三路检索串行，缺节点级耗时和并行结果一致性验证（O31/S06）。
- “不要声称没有依据”主要依赖模型遵守，没有生成后确定性对账（O35/S12）。
- 没有 Self-RAG 式多轮复检；当前一轮检索定终局，补检索依赖工具路径（O34，属于明确取舍但必须写清）。

### Q18：Query Rewrite 和 Expansion

- 相同查询重复扩写，缺语义缓存（O8）。
- 扩写有覆盖率测试，但没有独立判断角度是否落在正确主题上的评测（补充 S15）。
- 角度数量和 HyDE 长度固定，缺动态成本/收益依据（补充 S15）。
- 领域说明写死在代码，多知识域部署需要配置和版本化（补充 S05）。

### Q19：多路召回和融合

- 三路召回串行，缺并行性能优化（O31）。
- BM25 权重、EvidenceGate 阈值和融合参数虽有局部实验，但没有统一参数来源表和再校准触发（O28/S15）。
- 图谱召回有字段但没有覆盖率阈值告警，图谱失效可能被误认为“图谱本来就没价值”（O43）。
- 加权 RRF、学习排序和跨路证据合并尚未实现；当前等权是样本量驱动的保守取舍（补充 S20）。

### Q20：RAG 范式

- Corrective RAG 只有 WEAK/NONE 分级和提示词，没有代码级补检索、候选丢弃或硬拒答（O34/O35）。
- Adaptive RAG 只有 `needRetrieval` 布尔判断，没有复杂度分类器和成本收益证据（O33）。
- Self-RAG 不属于当前能力；如果未来加入，必须先解决评测和生成自评可信度问题（明确非目标）。

### Q21：幻觉和 RAG 评测

- 门判定拒答但最终回答仍下结论时，没有确定性抗命率检测（O35）。
- 夹具模型与线上模型已经发生代际漂移，旧数字不能直接作为当前质量结论（O28）。
- 删句式校验可能丢掉同句中的正确信息（补充 S18）。
- 缺少 answer relevancy 维度；RAGAS/LLM judge 只能作为参考轨，不能替代确定性门禁（补充 S03/S18）。

### Q22：知识库动态更新

- 更新和重建依赖显式 HTTP 调用，没有 MQ 事件传导和事实源/索引版本对账；漏调用无法自动发现（补充 S09）。
- 全量重建 `removeAll → indexBatch` 期间会暴露不完整语料，没有双集合切换或版本指针（补充 S09）。
- 没有索引滞后度 gauge、文档版本对账和单文档增量重建策略（O43/S09）。
- 异步 pending 去重存在忙时丢请求风险，必须把丢弃变成可重试状态而不是静默返回（补充 S09）。

### Q23：知识冲突和时效

- 没有 `valid_from/valid_until`，过期只能靠人工停用或替换（O37）。
- `SourceAuthority.dominates()` 已定义但没有生产调用，不同权威度冲突仍交给模型（补充 S10）。
- 种子导入和管理上传的元数据校验不一致，存在越界 source（O36）。
- 工具再检索证据缺少权威度字段，冲突裁决输入不完整（O38）。
- 冲突人工确认后没有自动学习/回写机制，这是刻意防止模型判断变成事实源，但需要保留人工闭环（补充 S10）。

### Q24：知识图谱设计

- 实体链接目前主要靠名称和变体包含匹配，图规模扩大后误匹配和性能会成为首个瓶颈（补充 S11）。
- 图谱与知识库都没有时效模型（O37）。
- 类型和关系词表是封闭的，词表新增需要同步抽取提示词、校验器和材料，缺少版本化治理（补充 S05/S11）。

### Q25：图谱参与 RAG 和多跳

- 图谱多跳固定为单条 Cypher、最多 3 跳，没有迭代式多跳、hop 权重或开放关系支持；这是当前域约束下的非目标，但必须记录触发条件。
- 图谱 RAG 依赖实体链接和建边覆盖，当前只有命中字段，没有低覆盖率告警（O43）。
- 图谱与文本证据只并列入池，没有跨路证据合并（补充 S20）。
- 图谱不可用和空结果已区分，但所有图谱降级路径的长期比例仍需要指标消费（O43）。

### Q26：Function Calling、MCP、Skill 概念边界

- 当前只有 MCP server 出口，没有消费外部 MCP 工具的 client 能力（补充 S16）。
- MCP 工具全量发布、授权级别单一，不能按调用方/角色限制能力（O9）。
- 对外描述已存在工具数量、幽灵工具和项目总览三处漂移（O41）。

### Q27：项目中的 FC、MCP、Skill 分层

- 工具注册表是单一事实源，但 instructions 仍有手写副本，缺自动渲染和一致性测试（O41/S16）。
- MCP 外部真实调用方主要是验收脚本，尚未形成生产级消费链路（补充 S16）。
- `ToolCall.confirmed` 仍是裸布尔，缺少编译期限制，新增调用方理论上可能绕过审批（补充 S16）。

### Q28：为什么暂不用 Skill

- 当前不引入 Skill 的立场合理，但触发条件、生成式单一来源和版本治理必须落文档。
- 若未来新增 Skill，必须从工具注册表/流程注册表生成，不能形成第三份手写描述（O41/S16）。

### Q29：Tool Routing、结果结构和超时

- 11 个工具每轮全量下发，工具表 token 成本尚未量化；约 20–30 个工具或 token 成本成为瓶颈时才引入两阶段路由，并保留全量兜底（O42）。
- 单条工具输出和总观测量有上限，但没有按工具重要性差异化预算（补充 S07）。
- LLM 侧无熔断，重试预算统一，缺少首 token/整体超时分离（补充 S06/S22）。
- `ToolResult` 三态已建立，但仍需确保所有下游和前端不把 `noData`、业务失败、传输失败压成二态（O25/S12）。

### Q30：非法调用、参数错误、超时和恢复

- 参数 schema 目前主要校验必填，类型、取值和数组形状要到工具内部才发现（O14）。
- 传输层重试、业务码重试和写操作不重试的分层正确，但重试次数未按工具重要性差异化（补充 S22）。
- LLM 侧缺熔断；下游断路器覆盖不完整（补充 S22）。
- 高危写工具只有部分 requestId 幂等，新增非幂等写操作仍可能被令牌重放（O1）。

### Q31：Bad Case、反馈和追踪

- Bad Case 和聊天历史只有 7 天 TTL，评测快照覆盖式落盘，没有审计级长期留档（O20/补充 S14）。
- 追加集能导出但不自动回流离线/在线评测（O29）。
- OTel 探针就位但默认没有 trace 导出后端，不是完整 Jaeger/Langfuse 链路（补充 S14）。
- 点踩缺少更复杂的刷反馈风控；当前只校验用户会话和消息归属（补充 S14）。

### Q32：Prompt 和模型调优

- Prompt 没有统一注册、自动 diff 和快照强绑定，版本依赖人工维护（补充 S05）。
- 评测集同时用于开发、调参和门禁，没有留出集，存在过拟合风险（O28/S05）。
- 夹具模型换代没有自动阻断，模型元信息目前只是记录（O28）。
- 扩写/HyDE 的“有没有运行”和“有没有收益”虽已能分别观测，但其他 Prompt 组件也需要同样的执行证据（补充 S15）。

### Q33：检索参数和消融实验

- 参数来源分散，文献默认、约束推导和实测值没有统一登记表（补充 S15）。
- 没有参数自动搜索，参数交互（如 topK×阈值）没有联合实验；当前样本量不足以支持自动搜索，应明确为非目标。
- 重排线上仍有 5 秒超时导致静默降级风险，缺少基于 P99 的稳定性参数校准和告警（O43/S06）。

### Q34：PDF、扫描件和文档解析

- 当前没有 PDF、扫描件、OCR、表格结构还原链路，也没有用户上传入口。
- 若开放上传，必须同时实现版面结构还原、OCR 置信度、低置信内容隔离、解析质量评测和上传内容注入防线（补充 S13）。
- 解析器必须保持“异常显式失败、禁止静默产出坏语料”的契约。

### Q35：提示词注入和工具安全

- 工具输出回填没有统一“资料不是指令”声明，当轮用户输入没有独立检测层（O40）。
- `confirmed` 裸布尔依赖“全仓只有一个构造点”的约定，没有编译期保证（补充 S16）。
- 权限判定不应读取记忆，工具参数中的 userId 必须由服务端注入；该原则需要继续用权限回归固定。
- 不应引入“让模型检测注入”作为唯一防线，确定性过滤、存储隔离和服务端权限仍是主防线。

### Q36：并发和扩容

- 模型侧没有并发上限、排队和舱壁；网关 5 QPS 不能约束一次会话内部的多轮模型调用和工具扇出（补充 S07）。
- 对话主链路没有并发压测，只有重排压力脚本（补充 S07）。
- 虚拟线程上下文传递、SSE 断开后的取消传播需要专门回归；否则客户端断开仍可能继续消耗模型 token（补充 S06）。
- 同一会话并发互斥仍缺失（O4）。

### Q37：线上可观测性

- 有健康位和计数素材，但没有告警动作、滞后度 gauge、评测趋势和 MCP 拒绝计数指标（O43）。
- 没有生产级 logback 滚动和 JSON 结构化日志；当前主要依赖控制台和正则解析（补充 S14）。
- 没有独立 readyz，启动自检和流量就绪语义未统一（补充 S14）。
- requestId 能串日志，但 OTel 没有默认导出，节点级 trace 仍缺（Q12/S06）。

### Q38：Deep Research

- 当前没有异步长任务、检索扇出、来源管理和大纲式综合写作能力。
- 本阶段纳入实现：复用证据门/引用核验，补齐异步任务状态、进度、取消、恢复、预算、来源管理、检索扇出和研究质量评测（补充 S17）。

### Q39：LATS、ToT、GoT

- 当前没有多候选计划、价值函数、树搜索、回溯剪枝或 Reflexion 记忆。
- 本阶段纳入受控推理增强：先实现 2–3 个候选计划、确定性约束过滤和轻量评分，再加入受预算限制的回溯；不引入 Multi-Agent，也不允许树搜索绕过审批、权限和证据门（补充 S17）。

### Q40：Agent 记忆系统

- 重复确认 Q5 的核心缺陷：STM 跨用户隔离、感知记忆无写入、长期记忆无用户可见/纠错入口、无衰减、无质量指标（O10/O16/O19/O44/S02/S03/S19）。
- 情节记忆没有自动淘汰 TTL，Milvus 旧事实可能长期存在；必须先定义时间衰减和用户删除语义（O10/O16）。
- 记忆失败语义已分级，但降级率和错误记忆率没有看板（O7/O21/S03）。

### Q41：多路召回融合

- RRF `k=60` 使用文献默认，未做本地调优；参数交互也未评估（O28/S15）。
- 图谱路与文本路等权，没有独立权重实验；跨路只去重和并列，没有证据合并（补充 S20）。
- RRF 分数不能作为置信度，证据门必须继续使用原生相似度/重排分；需要防回归断言（O35/S15）。

### Q42：Multi-Agent

- 当前是单图单 Agent，没有多 Agent 协作、子图复用和 supervisor。
- 这不是待补能力，而是明确不做的项目边界：电商 Agent 的导购、售后和交易操作共享用户身份、商品/订单状态、知识证据和审批链路，拆成多个 Agent 会增加 handoff 信息损失、状态一致性、全局预算、追踪和评测归因成本，却没有对应业务收益。
- 面试口径固定为：本项目选择单 Agent 显式状态图，把复杂度投入到工具契约、证据溯源、审批和确定性护栏；不为展示多 Agent 概念而引入它。

## 十三、收口计划八项任务的补充要求

### 任务 1：覆盖矩阵和数据契约

必须从“48 条复杂对话”扩展为 Q1–Q42/O1–O44/S01–S19 的覆盖矩阵。每条用例必须标注来源问题、初始数据、工具 DAG、权限、参数来源、确认点、最终状态、日志/指标断言和是否依赖真实模型。

### 任务 2：消息 ID、点踩和完整会话选择

除统一 `assistantMessageId` 外，还必须验证：流式完成事件、历史加载、重新生成、点踩、撤销、管理审核和追加测试集都使用同一个权威消息 ID；点踩选择范围覆盖整个当前会话，并有跨用户、越权、刷新恢复和状态冲突验收。

### 任务 3：Agent 平台能力

必须先完成 O1/O2/O13/O14/O25/O26 和 S12/S16，再新增优惠券、工单、购物车和售后工具。每个新增工具必须明确读取/写入/确认/幂等/权限/最终状态，不允许只增加模型描述。

### 任务 4：评测快照和页面语义

除 DTO、原子写入、重启读取和损坏状态外，还必须加入模型/语料/判定链版本、历史保留、Bad Case 追加集独立入口、基础集与追加集分母隔离，以及当前页面对应的脚本断言。

### 任务 5：图谱诊断

必须补齐批次隔离、原始候选、规范化字段、quote、原因码、可重试性、分页和权限；同时明确索引重建事件、滞后度和真实重建顺序，避免诊断页完成但生产链路仍不可解释。

### 任务 6：全平台验收脚本

脚本必须同时覆盖 UI/API/Agent 三种入口，且以权威状态为最终判据；新增跨用户 STM、并发会话、幂等重放、PII 扫描、拒答抗命、索引滞后、Bad Case 回流和图谱批次统计场景。

### 任务 7：确定性复杂对话回放和后端契约

固定计划回放不能只验证“计划能执行”，还必须验证自动依赖补边、optional 失败语义、schema 预校验、operationId 稳定性、重复确认、取消、补偿边界、会话互斥和最终副作用。

### 任务 8：真实模型和评测收尾

真实评测只能在确定性门禁通过后人工触发；结果必须保存 runId、模型/语料/prompt/pipeline 版本、请求轨迹、失败阶段、token 用量和最终状态。页面刷新、脚本验收和历史查询不能自动再次调用模型。

## 十四、最终完整性判据

只有同时满足以下条件，才能说“三个文档的问题全部覆盖”：

1. Q1–Q42 每题都有本清单中的问题登记或明确“这是非目标，不是当前缺陷”的边界说明。
2. O1–O44 每项都有问题、改动方向、状态和验收证据。
3. S01–S19 每项都有对应实现方案或明确触发条件。
4. 收口计划任务 1–8 的目标、依赖、测试和真实模型运行条件都能映射到上述条目。
5. 代码、验收脚本、运行证据和材料同步后，才能把对应条目标记为 `☑`。
