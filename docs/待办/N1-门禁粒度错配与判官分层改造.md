## 一、结论先行

用户反馈的三类现象，**根因不是「规则写得不够细」，而是「判定粒度放错了层」**：

1. **判官早已存在，但它不是最终裁决。** `SemanticGroundingVerifier` 就是模型判官（独立 LLM 调用、`temperature=0`、四档 JSON 判定），接线在 `Agent.java:1527`（semanticReview）与 `:1845`（判官本体调用），覆盖全篇句子。**同一句要活下来必须同时过判官与 `MedicalEvidenceVerifier`（54KB 纯正则），后者在后且删除优先级更高。**
   **但要注意：判官自己也会误杀**——图二那句元陈述就是判官删的（见 2.6）。所以「换判官」不是银弹，判官的判定档位同样需要设计正确。
2. **规则在管语义，模型在管硬约束——两者放反了。** 规则只能枚举「错误长什么样」，枚举不了「正确长什么样」，而自然语言的正例空间是开放的。现状是判官里塞着「CONVERSATIONAL 但含医学事实就降级」这类硬约束，而路由/豁免/证据门这些语义判断全用词表与句式穷举。
3. **三张图落在三个不同的错配点，不是同一个 bug。** 但共同后果一致：**答对的内容被删、被降级、被判成拒答**。
4. **会话记录扫描又挖出 5 类评测集未覆盖的问题**（§2.11），其中两类（空白气泡、元指令泄漏）**已经在生产会话里对用户可见**，另一类（模型自我否认并撤回正确答案）**用户信任成本高于直接答错**。
5. **逐轮对照「回答 ↔ 执行链路」后，发现更靠下的一层：动作层与自述层完全没有校验**（§2.12）。四道门禁全部作用在**文本层**——判「每句话有没有出处」；而**「系统做的是不是用户要的那几件事、做了几件」（动作层）与「模型对自身行为的陈述是否属实」（自述层）没有任何校验**。已确证的后果：多动作请求只执行一半、续作轮把同一件商品加购两次、确认卡片上的商品名与真实 SKU 不是同一件——**而这一切在 36 题评测里永远是绿的**，因为评测集只考「问答正确性」，没有一道题检验动作条数与内容。

**改造方向：把规则从「裁判」降为「哨兵」，并把校验从文本层扩到动作层与自述层。** 判官负责语义判断，规则只保留确定性硬约束（数量单位、主体归属、极性方向），证据门恢复集合级判定；**同时补齐「平台自写文案不进校验」「工具输出字段分离」「审批断点引用解析」「重新生成历史一致」四条结构性缺口，以及「动作条数对账」「阶段与待办同源」「自述事实供给」三条新缺口**。

### 2.4 真因：`enforceUnknownInteractionRefusal` 的事后降级

`Agent.java:1766` / `:1802`：

```java
// 边界拒答与证据门必须说的是同一件事：输出都声明"无法判断具体相互作用"了，
// 同一轮就不能再记账为"证据充分到可以作答"
if (response.getEvidenceLevel() == EvidenceGate.Level.SUFFICIENT) {
    response.setEvidenceLevel(EvidenceGate.Level.WEAK);
}
```

而评测侧 `GroundingEvaluator.java:274` 的判据是：

```java
boolean gateRefused = sample.evidenceLevel() != EvidenceGate.Level.SUFFICIENT;
```

**因果链**：`interaction_check` 工具对用户口语称呼（「深海鱼油」「DHA 藻油」「乳清蛋白粉」）返回「本次图谱检查未收录该称呼」→ 该函数追加一段边界拒答 → **顺手把整轮 level 从 SUFFICIENT 降为 WEAK** → 评测把整题记成过拒。

日志实证（`logs/logs-local/ai-service.log`）：

```
[Agent] 医学确定性边界 mode=PARTIAL_OR_TEXT_BACKED_INTERACTION_UNKNOWN 证据=WEAK 未收录项=1
```

G-16 的答案正文里，**正确的鱼油-抗凝药出血风险部分完整保留**，末尾才追加那段边界话术。用户看到的是「答对了 + 一段自我否定」，评测看到的是「拒答」。

**这条降级本身有其历史理由**（避免「输出说无法判断、记账却说证据充分」），但它把「图谱未收录某个口语别名」这一条**局部**事实，升级成了对**整轮**作答能力的否定。

### 2.6 图二：元陈述句被**判官**剔除（非规则）

「以上是知识库中与满减直接相关的全部内容」是**关于检索本身的元陈述**，没有也不该有出处。

**这里必须先纠正一个直觉归因**：最初的判断是「`CitationVerifier` 的句式豁免枚举不全」。**实测推翻了它**——用规则层直接跑这句（探针：`CitationVerifier.verify(meta, 3, false, ...)`，5 种变体）：

```
unsupported=0  stripped=false  factSentences=0
```

原因：该句不命中 `FACT_SIGNAL`（`CitationVerifier.java:96` 的「数字/规定/政策/条款/标准/上限/…」），`needsCitation` 因此返回 false。**规则层根本不会删它。**

**真凶在会话记录里**（`chat:hist:u1003:u1003-1791874549403`，用户实测原始响应）：

```json
"unsupportedClaims": ["以上是知识库中与满减直接相关的全部内容。"],
"unsupportedStripped": true
```

这条 `unsupportedClaims` 是 `SemanticGroundingVerifier` 判官（`SEMANTIC_REVIEW` 阶段）的产物——**判官把「关于检索本身的元陈述」判成了 `UNSUPPORTED`**。

**所以图二的根因不是「规则太严」，而是「判官缺少『元陈述不属于断言』这一档」。** 判官的四档（`SUPPORTED`/`CONVERSATIONAL`/`UNSUPPORTED`/`CONFLICTED`）里，`CONVERSATIONAL` 的定义是「纯承接或解释对话上下文」，而「以上是知识库中…全部内容」是在**说明检索范围**，现有提示词没有覆盖这一类，判官只能往 `UNSUPPORTED` 归。

**改造点因此从「加豁免句式」变为「补判官的判定口径」**——后者才是开放集的解法。

### 2.7 图三：证据门的粒度错配

`MedicalEvidenceVerifier.java:419` 对**每个引用切片单独**重跑证据门并要求全部达标：

```java
boolean allUsable = refs.stream().allMatch(ref ->
        EvidenceGate.evaluate(List.of(chunk), thresholds, ...).isSufficient());
```

而 `EvidenceGate` 的设计是**集合级**判定（类注释：「判定这一轮检索到的证据够不够支撑一个回答」）。KG-04 引用的 `KB-0022_7` 得 0.1907、差 0.009，就毁掉整句。

**同一批证据，集合判 SUFFICIENT、逐片重判却全否——两把尺子量同一件事。**

### 2.8 第 4 类机制：标题外提后主体丢失（KG-04 实证）

KG-04「维生素 K2 和华法林之间是什么关系」的完整阶段轨迹（日志 `520aff7a401f4da9`）：

```
GENERATED        factCount=4 rejectedCount=0
TITLE_LOCATED    factCount=4 rejectedCount=0
SEMANTIC_REVIEW  factCount=4 rejectedCount=1
MEDICAL_REVIEW   factCount=3 rejectedCount=3
PUBLICATION_REVIEW factCount=0
FINAL            factCount=0        ← 发布时已无事实句
医学完整性结算 beforeFacts=4 finalFacts=0
```

生成的原文（`GENERATED` 阶段）本来是**正确且有主体**的：

```
《维生素 K2 软胶囊产品说明书》第四章写明：维生素 K 可拮抗华法林等维生素 K 拮抗剂类
抗凝药物的作用，正在服用华法林者禁用本品，或必须在医师指导下使用并监测凝血指标。
```

`TITLE_LOCATED` 把《文档名》外提成编号后，句子变成：

```
[1]第四章写明：维生素 K 可拮抗华法林等…，正在服用华法林者禁用本品，…监测凝血指标 [1]。
```

于是 `MEDICAL_REVIEW` 判：

```
reason=同一引用切片未支撑：本品临床事实没有声明引用来源所属商品
```

**机制**：`MedicalEvidenceVerifier.java:473` 的判据是「句中出现『本品』时必须声明商品归属」，而归属来源是 `productOwner(chunk.getTitle())`（`:549`）——它要求**标题原文出现在句子里**（`:153-155` 的 `declaredOwners`）。标题被 `numberTitles` 换成 `[1]` 之后，句子不再含商品名，归属判定失败。

**探针实证**（同一批证据、同一句话）：

```
PROBE withTitle unsupported=[]        ← 保留标题时通过
PROBE numbered  unsupported=[该句]    ← 标题换编号后被拒
PROBE numbered  reasons={…=本品临床事实没有声明引用来源所属商品}
```

**这是「引用编号化」与「主体归属判定」之间的冲突**：为了让前端能点击回原文，标题被换成编号；而归属判定却依赖标题原文。**两个都正确的设计，合起来是错的。**

### 2.11 五类新发现（均为评测集未覆盖，P0 级）

#### 发现 A：审批确认话术曾被校验器删光 → 用户看到**空白气泡**（已在后续提交修复，留作回归）

证据：`chat:hist:u1001:u1001-1791442326988` 两轮、`chat:hist:u1003:u1003-1791710154819` 一轮（**2026-10-08 的会话**），`content` 长度 = **0**，而 `pendingActions` 正常下发（`cart_add(skuId=10)` / `cart_checkout(...)`）。

```json
"unsupportedClaims": ["这个操作不可撤销，需要你确认后才会执行。", "确认无误请点击「确认执行」，或直接回复这四个字。"],
"unsupportedStripped": true,
```

**当前代码已不复现**（探针实测，2026-10-14）：用 `Agent` 完整构造 + `PendingGraph` 复现审批中断轮，五组输入（含 `结算`、`益生菌粉60袋装加入购物车后如何结算`、`推荐一款维生素D补充剂`）全部得到 `replyLen=44`、`unsupportedClaims=null`。`CitationVerifier.verify()` 对该话术的判定也是 `unsupported=[] stripped=false`（八种 evidence/toolEvidence 组合全覆盖）。

**为什么当初会被删（历史归因）**：现场 `level=NONE` + `knowledge=0` 指向医学链；`finalizeMedicalReply`（`Agent.java:1637`，2026-10-12 新增）在 `earlierFactsRemoved=true` 且当前文本 `factSentences` 为空时会 `break` 并返回 `insufficientMedicalReply` 兜底句——**探针已证实这条路径会把审批话术整体替换掉**。10-08 的现场没有这个函数，剔除者应是当时的 `groundResponse` 链（版本已不可考，`git log -S` 显示确认话术自 `3394566` 引入后未改，剔除逻辑在其后大改过）。

**为什么仍然写进本文**：它不是「已修复所以无关」，而是**同类风险仍在**——`finalizeMedicalReply` 现在对「`factSentences` 为空且 `earlierFactsRemoved=true`」的文本仍会替换成兜底拒答（探针实测：`PROBE earlierFactsRemoved=true -> reply=[当前检索证据不足以支持该医学问题的结论…]`）。只要某条路径上「平台自写常量」被标成 `earlierFactsRemoved`，同样的空白就会重现。

**讽刺之处**：审批轮的正文是**平台自己写的常量**，不是模型生成的，却要过「防模型幻觉」的闸门。`Agent.java:1504` 有一处 `toolBacked` 特判（`"flow".equals(source) || "approval".equals(source)`），但 `executeApproved` 返回的 `source="approved"`，不在特判集合里。**这个缺口仍在。**

**用户可见后果（历史）**：前端渲染出一个空的助手气泡，只有一张确认卡片孤零零挂着——**用户不知道为什么要点确认**。当前代码已不复现，但 R7（校验范围按来源分流）仍要落地，否则 `source="approved"` 这个缺口会在别的路径上以别的形态重现。

```
- 订单已创建：单号 YS2026100715580262243E72D，应付 267.00 元。当前状态是待支付——务必提醒用户还要完成支付，否则订单会超时关闭。
```

**根因**：`AddToCartTool.java:96` 与 `CheckoutTool.java:108` 把**给模型的指令**写进了工具返回的 `output`：

```java
.output("已加入购物车：" + item.getName() + "……"
        + "提醒用户：加入购物车还没有下单，需要结算并支付才算买到。")
```

而这两条工具属于**写操作**，回复路径是 `renderApproved`（`Agent.java:718`）——**直接把 `execution.getOutput()` 拼进给用户的正文**，不经模型转述。于是「提醒用户：」这个祈使句成了商品描述的一部分。

**这是一处「工具输出的双重身份」缺陷**：`output` 同时被当作（a）模型读的观察结果、（b）用户读的正文。两种读者的语言约定不同——对模型说「务必提醒用户」，对用户应当直接说「还需完成支付」。**同一条字符串不可能同时满足两种读者。**

#### 发现 D：模型自我否认 + 编造「更正」（最严重）
**当前状态：未修复（2026-10-14 核实）**。`regenerate` 标志只用于 `recordTurn`，不传给 agent-core；`Agent.java:487` 的 `rememberMessage` 无条件追加。

证据：`chat:hist:u1003:u1003-1791618493018`。同一会话里，**同一个问题被问了两次**（相隔 1.6 秒，来自 `verify-chat-ui.mjs` 的「重新生成」步骤）：

| 轮次 | 结果 |
|---|---|
| 第 1 次 | `level=SUFFICIENT`、`knowledge=7`、回答**完整正确**（满减档位、门槛、退货扣回、券叠加全对） |
| 第 2 次（重新生成） | `level=NONE`、`tools=[]`、`knowledge=0`，回答：「**我上一轮的回答有问题，需要更正：我并没有真正检索到这些条款**……那是我凭通用印象编的，不是平台的说法」 |

**第 2 次的说法是假的**：知识库**确实有**满减规则（`KB-0014-promotion.md`，同一时期 5 个其他会话都成功检索到 5 条知识并给出正确答案）。模型没有编造条款——它编造了**「我编造了条款」这个忏悔**。

**机制**（三因叠加，**已用 Redis 数据证实**）：

1. **重新生成时旧答案仍在短期记忆里，而且变成「两条」**。`AiAssistantServiceImpl.java:179` 走 `history.recordAnswer` 就地改写 `chat:hist:`，但 `Agent.java:487` 的 `rememberMessage` 是**另一条写入路径**、每轮无条件 `LPUSH` 进 `stm:`。实测该会话 `stm:u1003|u1003-1791618493018` 的 6 条消息，**同一个问题出现两次、带两条不同的答案**（正确版在前、自我否认版在后）。模型看到的上下文里，两个「自己」说了相反的话。
2. **用户消息里带着 `（mv23e4ds）`**。这是 `verify-chat-ui.mjs:175` 为去重注入的 `RUN_TAG`，模型把它读成了**「依据编号」**（用户消息原文就是「请……标注依据编号（mv23e4ds）」），于是试图在自己的输出里找这个编号、找不到 → 推断「我上一轮没真检索」。
3. **`tools=[]`**：这一轮**没有调用任何工具**（`level=NONE` 也印证），模型完全凭上下文自我推断，没有去知识库核实一遍。

**「知识库没有收录」这一句的判据缺口**：`KnowledgePrompt` 已有两条口径——「不得用你自己的常识、训练数据或通用经验把答案补全」（`:160`）、「说『没有』时不要越过资料的边界」（`:189`）——但它们约束的是**编造内容**，没有约束**「声称自己没检索过」**这种**关于自身行为的陈述**。模型可以诚实地遵守前两条、同时说出一句关于自己检索史的假话。

**同一模式的第二个实例**：`chat:hist:u1003:u1003-1791631564939` 的 `level=NONE`，回答开头同样是「我需要先说明一点：我还没有真正检索过……」，但这一轮**调了 2 次 `knowledge_search`、拿到 7 条知识**，于是它接着说「现在我去查一下」，然后**给出了正确答案**——同一段自白，一半是假的。

**为什么这条最严重**：它不是「答得不够好」，是**把正确答案主动撤回并道歉**。用户看到的是一个「诚实」的助手，实际拿到的是被自我怀疑毁掉的答案。**这类错误的用户信任成本高于直接答错。**

### 2.12 「回答 ↔ 执行链路」一致性专项（第三层扫描：逐轮对照回复与工具轨迹）

§2.10–2.11 看的是**回复文本里有什么**（元指令、空白、否认）。本节换一个判据：**把每一轮的回复与同一轮的工具轨迹、审批载荷、任务状态逐条对照**，回答一个问题——**模型对用户说的，与系统实际做的，是不是同一件事**。

方法：解析 44 个会话 / 125 轮的完整 `response`（`toolCalls` / `pendingActions` / `pendingActionDetails` / `stage` / `taskState` / `reply`），按 10 条判据跑确定性检测（脚本 `frontend/.evidence/n1-probe/consistency.cjs` + `detect2.cjs` + `detect3.cjs`）。

#### 发现 F：多动作计划在审批断点只保留 1 条，其余**静默丢失**（P0，新）

证据：`chat:hist:u1001:u1001-1791529067350`（2026-10-09）第 7–12 轮。

用户说「**那两个商品我都来一个吧，原版来 120 片版本的**」——两个不同 SPU 各加购一件。同轮 `taskState.core_intent` 明确写着**四项**待办：

```

```

同轮 `toolCalls` 有**两次成功的 `product_search`**（`SPU29` 与 `SPU20`），说明检索侧拿到了两个候选。但落地的审批载荷只有**一条**：

```json
"pendingActions": ["cart_add(quantity=1, skuId=39)"],
"pendingActionDetails": [{"tool":"cart_add","arguments":{"skuId":39,...,"productName":"维生素 C 咀嚼片"}}]
```

**免疫配方版（SPU20 → SKU29）的那条 `cart_add` 从未出现在确认卡片上。** 用户点确认，执行的是原版 120 片；他以为「两种各一份」已经批准。

**更糟的是下一步**：执行成功后，系统**又弹了一次同一个审批**（第 10 轮 `stage=DONE` + `pendingActions=["cart_add(quantity=1, skuId=39)"]` + `approvalStatus=CONFIRMED`），用户再点一次「确认执行」→ 同一 SKU 被加购**第二次**（`× 2`）。

用户的第 13 轮是这条链的判决书：

> **「我不是说两种商品各来一份吗，你怎么把同一个商品给我两次」**

助手这一轮才查购物车并承认：「抱歉，是我操作错了——把原版 120 片的加了两份，免疫配方那款反而没加进去。」

**三个独立缺陷叠在一条链上（归因已用探针校正，非推测）**：

1. **规划器漏了一条动作**（不是执行器丢的）。已用一次性探针（四条步骤：两次 `product_search` + 两条 `cart_add` 各自 `dependsOn` 自己的检索）验证：`executePlan` 的 `risky` 收集**不丢条目**——`pending.count=2`、两条 `cart_add`（`skuId=39`/`skuId=29`）都在卡片上、`writes=0`。所以「只剩一条」发生在**计划生成**：模型自己只写了一条 `cart_add`。同轮 `taskState.core_intent` 写了四项待办、`toolCalls` 只有两次 `product_search`，与「计划里只有一条加购」一致。
   - **探针已删**（临时文件不留在仓库）。R12 落地时它应转为**正式回归测试**：构造上述四步计划，断言 `pendingActions` 恒为 2 条且 SKU 不同。
2. **续作轮的参数填错，而没有任何校验发现**。第 9 轮的 `taskState.core_intent` 已经变成「**把免疫配方版**维生素C咀嚼片加入购物车（原版120片已加购成功，不重复）」——续作机制正确识别了剩余任务；但落地的 `pendingActions` 仍是 `cart_add(quantity=1, skuId=39)`，**`skuId=39` 是上一批那条原版**，免疫配方版是 `SKU29`。于是「续作」把同一个 SKU 加购了第二次（第 11 轮 `× 2`）。
   **缺口**：续作轮**没有任何断言**核对「模型填的参数是否对得上它自己声明的意图」。`core_intent` 说 A、`arguments` 填 B，两者都在同一份响应里，却从不互相校验。
3. **「两种各一份」这类并列请求的条数，全链路无校验**。用户要求 2 项、实际落地 1 项（第 8 轮）与 2 项落地但同一件（第 11 轮），**系统两次都没有发现自己答错了**——是用户第 13 轮亲自质问才暴露。这是**计数级的一致性缺口**：它不像事实错误那样有出处可核，任何按句校验的门禁都看不见它。

**附带发现（探针副产物，P2）**：当同一批里两条高危步骤的引用都解析失败时（`unresolved` 非空且 `preparation` 为空），`executePlan` 会**整份计划阻断**并交出 `当前计划无法安全执行…` 作为答案。保守方向正确（宁可不做），但用户拿到的是一句**没有可操作性的错误**：既没说他能做什么，也没说这一步为什么失败。

**另需注意**：`stage=DONE` 与 `pendingActions` 同时出现这一形态，在 `u1001-1791442326988`、`u1001-1791359634411`、`u1001-1791665225779` 等 **7 处**复现（`pendingNotWaiting` 检测项），说明它不是这一条链的偶然。它由 `ChatHistoryStore.updateApprovalMessage` 的 `response.put("stage", "CONFIRMED".equals(status) ? "DONE" : "WAITING_USER")` 与 `pendingActions` 各自写入、互不约束造成——**「阶段」与「待办」是两个字段，没有任何东西保证它们语义一致**。

#### 发现 G：确认卡片上的商品名与将要执行的 SKU **不是同一件商品**（P0，新）

证据：`chat:hist:u1001:u1001-1791422651547`（2026-10-08）第 5–6 轮。

用户说「**把这两个商品都帮我加入购物车吧，我各买一瓶**」（上下文是叶黄素酯软胶囊 158 元 与 越橘叶黄素片 138 元）。落地的审批载荷是**两条** `cart_add`（`skuId=27`、`skuId=28`），但两条的 `productName` **都写成「越橘叶黄素片」**：

```json
{"tool":"cart_add","arguments":{"skuId":27,"quantity":1,
  "productName":"越橘叶黄素片（北欧越橘提取物与叶黄素复合配方）",
  "specification":"规格：SKU27 158.00 元 有货"}},
{"tool":"cart_add","arguments":{"skuId":28,"quantity":1,
  "productName":"越橘叶黄素片（北欧越橘提取物与叶黄素复合配方）",
  "specification":"规格：SKU28 138.00 元 有货"}}
```

**权威数据核对**（`GET /products/skus?ids=27,28`，2026-10-14 实测）：

```
id=27 → spuName=叶黄素酯软胶囊    price=15800  stock=220
id=28 → spuName=越橘叶黄素片      price=13800  stock=240
```

`skuId=27` 确实是**叶黄素酯软胶囊**（158 元），卡片却写着「越橘叶黄素片」。用户看到的确认卡片是**错的**：他以为在批准「叶黄素酯软胶囊 ×1」，卡片告诉他那是「越橘叶黄素片」。

**根因：当时用「同一段文本里出现」代替了「真实的 SKU→SPU 归属」**。这条会话（10-08 01:26）跑的是 `aface99`（10-07 16:39）那版代码，其 `Agent.enrichCartAdd` 从**工具输出文本里正则抽商品名**：

```java
if (!output.contains(skuToken)) continue;                       // 这段输出里出现过 SKU27
Matcher product = Pattern.compile("- 编号\\s+SPU\\d+：(.+?)(?:，价格|，类目|，品牌|\\n)").matcher(output);
if (product.find()) arguments.put("productName", product.group(1).trim());   // 抽的是「第一个」SPU
```

检索输出里「- 编号 SPUxx：」的**第一条不是 skuId 所属的那个 SPU**（`product_search` 返回按相关性排序的列表）。正则 `find()` 只取第一个匹配，于是 `SKU27`（叶黄素酯软胶囊）拿到了列表首位的名字「越橘叶黄素片」。`specification` 那行带 `Pattern.quote(skuToken)`，所以规格抽对了——**同一份载荷里两个字段一个对一个错**，正是这个不对称造成的。

**判据错在哪**：「这个 SKU 属于哪个 SPU」是**数据关系**（`SkuSnapshot.spuId`/`spuName`），当时却用「两个字符串出现在同一段文本里」来推断。文本里的相邻性不等于实体间的归属关系。

**当前版本已修**：`CommerceCardAssembler.enrichApproval` 改为先 `arguments.remove("productName")` 再用权威 `SkuSnapshot.spuName` 覆盖，取不到就 `confirmable=false` + `displayNotice`（**不给模型自称的名字留位置**）。`enrichCartAdd` 那段正则已从 `Agent.java` 移除（`grep` 无命中）。已有测试覆盖：`CommerceCardAssemblerTest` 的「跨轮加购无需本轮搜索输出也能批量补齐多个真实商品」「商品服务失败时保留原执行参数并明确不能盲签」。

**仍存的两个残留**：
1. **补全失败时仍回退到原载荷**（`sku == null` 分支返回未改写的 `detail`）。因为 `productName` 已被 `remove`，模型自称的名字不会外泄——但 `pendingActionDetails` 会缺商品名，前端只能渲染裸 `skuId`。这是**降级**而非错误，可接受，但用户看到的是「SKU27」这种内部编号。
2. **历史回放不修正**（`historical=true` 且载荷「完整」时原样返回）。这是刻意的设计（「不改原记录」），但意味着**旧卡片上的错误名字会随历史长期存在**，不会随商品目录修正。用户回翻旧会话时看到的仍是错的。

**用户可见后果**：这是「确认卡片存在的全部意义」被击穿的形态——**用户批准的东西和他以为在批准的东西不是同一个**。§2.11 发现 B（工具输出被逐字拼接）是**格式**问题，这条是**内容**问题，危害高一档。

#### 发现 L：同一轮内工具失败，回复仍以「已按你的确认执行」开头（P2，形态问题）

语义上没错（确认确实被执行了、执行失败），但**「已按你的确认执行」这半句会被快速阅读的用户读成成功**，而失败信息在后面。同一轮 `order_cancel:false` 的失败原因还是**原始异常文本**：

```

```

`For input string` 是 `NumberFormatException` 的原文，**没有翻译成用户能懂的话**。这与发现 B 是同一层（工具输出直接进正文），但方向相反：B 是**内部指令泄漏**，L 是**内部异常泄漏**。

#### 本节小结：一致性缺口的三个层次

| 层 | 判据 | 现有校验能否发现 | 发现编号 |
|---|---|---|---|
| **文本级** | 回复里的每句话有没有出处 | ✅ 有（引用/事实/语义/医学四道） | — |
| **动作级** | 系统做的是不是用户要的那几件事、做了几件 | ❌ **完全没有** | F、G、I |
| **自述级** | 模型对自身行为的陈述是否属实 | ❌ **完全没有**（判官无此档） | D、K |

**这是本文件最重要的结构性发现**：现有四道门禁全部作用在**文本层**，而**动作层与自述层没有任何校验**。评测集 36 题也全是「问答正确性」，没有一道题检验「动作条数与内容是否符合请求」——所以这四类缺陷**在评测里永远是绿的**。

- **发现 J（`stage=null` 的半句）撤回**：它是 `verify-chat-ui.mjs` 的取消测试产生的**正常行为**，不是缺陷。详见该条。
- **发现 L（「已按你的确认执行」开头）降级为 P2 形态问题**：语义上正确（确认确实执行了、执行失败），且失败原因已由 `Downstream` 包装成人话（「订单服务暂时不可用」）。但**失败原因仍有一处是原始异常文本**（`For input string: "YS..."`），见 §四 R9。

**两条归因教训（本轮实际发生）**：

1. **`stage=null` + `kn=0` 有两种成因**（被取消 / 收尾失败），只凭字段形状分不出来——必须回到产生它的那条路径。
2. **`unsupportedStripped=true` 不代表「话被删了」**：它只说明「有句子被判为未支撑」，而 `reply` 可能完好。发现 H 的第一版归因就是被这个字段误导的（探针实测四种组合全部 `unsupported=[]`）。


### 2.13 第四层扫描：逐句核对「生成表述 ↔ 校验判据」（2026-10-14，零 API 成本）

§2.10–2.12 看的是「回复里有什么」与「回复和执行链路是否对得上」。本节换第三个判据：**把每一轮的回复拆成句子，逐句问「这句话被判未支撑的判据，是否真的成立」**——即**校验判据自身的准确率**。

方法：新写 6 个只读脚本（`n2-*.cjs`，落在 `frontend/.evidence/n1-probe/`），对 44 会话 / 122 轮跑 24 条新判据（截断、内部标识泄漏、数字幻觉、虚构用户前提、承诺悬空、括号不配平、条数不符、重复动作…），再对**所有剔除轮次**做逐句复核。

```
第 2 次 order_cancel(orderId=YS2026...)   → 失败：同一参数原样重试
第 3 次 order_query(orderId=YS2026...)    → 失败：同一个转换问题
第 4 次 order_cancel(orderId=$0.id)       → 失败：$0.id 未被解析，字面量进了工具
```

**三处独立缺陷叠在一条链上**：
1. **失败的写操作不产生「失败记忆」**：第 2 次与第 1 次的参数**逐字相同**，系统没有任何机制阻止重发。
2. **`$0.id` 字面量穿到了工具**：`resolveBatch` 对**解析不出来的引用保持原样**（设计如此，为了让报错带上下文），但**高危步骤的未解析引用没有在此拦截**——`unresolvedRisky` 只在「本批同时有可执行的非高危步骤」时才拦（`:644`），当准备步骤本身也失败时，含 `$0.id` 的取消请求照样生成了确认卡。用户点「确认执行」，系统执行一个参数是 `$0.id` 的取消。
3. **原始异常进正文**：`For input string: "YS…"` 是 `NumberFormatException` 原文（§2.12 发现 L 已记，此处补上它的上游成因）。

**注意**：`order_cancel` 的参数契约**已经修过**（现在同时接受数字 ID 与 YS 订单号，见 §4.2 R9），所以第 1–3 次的报错在当前版本不复现；**但第 4 条的形态（未解析引用 + 高危 + 仍出确认卡）在当前代码里仍然存在**——`unresolvedRisky` 的拦截条件是 `preparation.isEmpty()` 才返回空，若本批有别的可执行步骤，含未解析引用的高危步骤会被**推迟**而不是**拒绝**。

#### 本节小结：校验层的「判据准确率」

前三层扫描（文本 / 动作 / 自述）问的是「回复对不对」。本节问的是**更上游的问题：判它对错的那些判据，自己准不准**。

| 判据 | 命中规模 | 后果 |
|---|---|---|
| 剂量断言要求句内主体 | **4/12 轮整篇被兜底**（同问题） | 用户拿不到已检索到的正确内容 |
| 长期记忆与当前上下文不加区分 | ≥4 轮 | 用户被问一个他没说过的前提 |
| 高危步骤未解析引用不拒绝只推迟 | 1 轮（链路级） | 用户批准注定失败的操作 |
| 计数词不随剔除更新 | ≥5 轮 | 用户看到「三档」却只有两档 |

**方法论教训（第三条）**：**`unsupportedClaims` 非空不等于「删错了」**——本节 38 个有剔除的轮次里，绝大多数删的是**真正多余的推断句**（如「三份资料一致，可以放心」这类原文没有的结论）。**只有逐句对照「这句话的判据是否成立」，才能把「判对了」与「判错了」分开**；只看 `unsupportedStripped=true` 会得出「门禁太严」的错误结论，只看 `unsupported=0` 又会漏掉本节全部四条。

用户反馈的「商品信息被误拦截」在库里是**可复现的稳定形态**，不是偶发：

- 同形态在 `CA-011`/`CA-022`/`CA-034`/`CA-012` 等 14 个轮次重复出现。

**根因链（三处叠加，每一处单独看都「有道理」）：**

1. **路由**：`isMedicalQuestion` 是词表判定（`MEDICAL_TERMS` 含「维生素D」「钙片」「益生菌」…）。用户问的是**买哪个商品**，词表只看到「维生素D」→ 判成医学问题 → 走严格链。这正是 R1 要修的项，**尚未落地**。
2. **改写放大**：`Agent.java:447` 把判定写成 `isMedicalQuestion(message) || isMedicalQuestion(retrievalQuery)`，而 `retrievalQuery` 是指代消解/扩写后的句子。实测 **38 轮**出现「用户原话不命中医学词表、改写后命中」——例如用户说「取消刚才的操作，不执行加购」，改写后变成「取消将**益生菌粉**（SPU5）…」，于是**一次取消操作被拖进医学严格链**，回复被替换成医学兜底句。**改写是为了让检索更准，却让路由判定跟着漂移**——判据的输入不该是被改写过的那一份。
3. **兜底替换**：`finalizeMedicalReply` 的兜底分支不区分「正文里还有平台自己的商品列表」，把整段替换成拒答。`ProductCandidateList` 是**平台自己拼的**（`ProductCandidateList.render`），与模型的医学断言无关，却一起被吃掉。

**为什么这条比 §2.5 更严重**：§2.5 说的是「商品咨询被拖进医学链」，本轮证实它**同时在 14 个轮次上发生，且改写路径是放大器**。用户看到的是「你问我推荐维生素D，我告诉你请咨询医师」。

## 三、根因统一表述

> **粒度错配。** 信息放在块级，核验器按句级要它；证据门按集合判 SUFFICIENT，逐句核验却对每个引用切片单独重判；路由按词表判语义类别；主体归属判定依赖已被改写掉的标题原文。

**四类现象、四个不同的错配点，一个共同结构：判据所在的层，与事实所在的层不一致。**

| # | 现象 | 判据所在层 | 事实所在层 | 错配形式 |
|---|---|---|---|---|
| 1 | 商品咨询被拖进医学链 | 词表（`MEDICAL_TERMS`） | 语义意图 | 词表命中 ≠ 医学意图 |
| 2 | 元陈述句被删 | 判官（缺「元陈述」档） | 检索自述 | 判定档位不覆盖 |
| 3 | 答对却判相关度不足 | 逐片重判 + 事后降级 | 集合级证据 | 粒度 + 记账越界 |
| 4 | 标题外提后主体丢失 | 标题原文（已被编号替换） | 切片元数据 | 改写与判据竞争 |
| 5 | 平台自写的审批话术被删成空白气泡 | 通用后置校验（对所有回复） | 平台常量文案 | 校验范围未按来源分流 |
| 6 | 工具返回的元指令被原样展示 | 工具 `output` 字段（双重身份） | 模型观察 vs 用户正文 | 一个字段服务两种读者 |
| 7 | 多步任务在审批断点丢失后半段 | 同批引用解析（`$0.id`） | 跨审批轮的执行结果 | 中断切断引用依赖链 |
| 8 | 模型自我否认并编造「更正」 | 短期记忆里的旧答案 + 用户消息噪声 | 知识库真实存在的内容 | 无工具调用的自我推断 |

### 3.1 第二类根因：校验层的**覆盖面**错配（§2.12 专项）

上表八类都在「**同一个事实、判据放错了层**」这一族里。§2.12 挖出的七类不同——它们的共同点是**该有校验的地方根本没有校验**：

| # | 现象 | 谁的账 | 现状 |
|---|---|---|---|
| 9 | 多动作请求只落地一部分 | 用户要几件事 vs 系统做几件事 | **无任何校验**（文本层门禁看不见条数） |
| 10 | 续作轮把同一 SKU 加购两次 | 续作声明的意图 vs 实际填的参数 | **无任何校验**（两者在同一份响应里，从不互校） |
| 11 | 确认卡片商品名与真实 SKU 不符 | SKU→SPU 归属关系 | 已改用权威 `SkuSnapshot`（历史回放仍存错） |
| 12 | 审批轮 `ungrounded` 误报 | 回复来源（平台常量 vs 模型生成） | `toolBacked` 集合漏 `approved`/`approval-recovery` |
| 13 | `stage` 与 `pendingActions` 互相矛盾 | 同一件事写在两个字段 | 两个独立 `put`，无一致性约束 |
| 14 | 模型自述与事实相反 | 本轮实际工具调用 | 模型自述，**无事实供给也无校验** |

**两类根因合起来才是完整结论**：

- **第一类（3.0）**：判据的**粒度**与事实所在的层不匹配 → 修法是**换判据的层**。
- **第二类（3.1）**：校验的**覆盖面**根本没到那一层 → 修法是**把账立起来**。

**这两类修法毫无共同点**：前者是「判错了」，后者是「没人判」。把它们混在一起谈，就会得到「再加几条规则」这种既修不好第一类、也修不了第二类的方案。

**这十四类不是同一个 bug 的十四个面，而是十四个独立的错配点。** 修复必须逐点对应，不能用一条补丁覆盖——但它们的**共同后果一致**：答对的内容被删、被降级、被判成拒答、被模型自己撤回，或者系统做了与承诺不同的事而无人知晓。

### 3.2 一个反直觉的发现：判官不是「太松」，而是「档位不够」

第 2 类（图二）最初被归因为「规则句式枚举不全」，**探针实测推翻了它**：规则层根本不删那句（`unsupported=0 / stripped=false`）。真凶是判官——它的四档里没有「关于检索本身的元陈述」这一档，只能归到 `UNSUPPORTED`。

**这说明「换成模型判官」本身不自动解决问题**：判官的判定档位与提示词口径同样是人工设计的，覆盖不全时会以另一种形式产生同样的误杀。**换判官解决的是「枚举正例」的不可行性，不解决「判定档位要设计得对」。**

## 四、改造方案

### 4.1 总原则：规则从裁判降为哨兵

| 判定类型 | 改后归属 | 理由 |
|---|---|---|
| 「是不是医学问题」 | **判官** + 确定性硬触发 | 语义分类是开放集 |
| 「这句话有没有依据」 | **判官为主** | 同上 |
| 「这句话的出处对不对」 | 规则（保留） | 确定性可验证 |
| 「数量/单位/主体/极性对不对」 | **规则（硬约束，保留）** | 「每日1粒→2粒」一个字的差别必须确定性抓 |
| 「这一轮证据够不够」 | 规则，**集合级** | 粒度错配要修回集合级 |
| 「元陈述/边界提醒」 | **判官** | 句式枚举不完 |
| 「这条回复要不要校验」 | 规则，**按来源分流** | 平台常量文案无幻觉风险 |
| 「工具输出给谁看」 | 规则，**字段分离** | 一个字段不能服务两种读者 |

**硬约束为什么不能交给判官**：剂量、主体归属、否定极性属于**安全性断言**，一次误放就是医学事故。判官是概率系统，与「必须确定性」的要求本质冲突。这一条不因成本或便利让步。

### 4.2 十一项改造（R1–R11，对应 §2.1–2.11）

#### R1 路由层：医学问题判定改由判官 + 硬触发

- **保留**：剂量/相互作用/症状的确定性硬触发（`isMedicalQuestion` 后半段的正则，`:248-251`）。
- **移除**：`MEDICAL_TERMS` 词表命中即判医学（`:246`）。
- **新增**：判官判定「这个用户在问医学结论，还是在挑商品/问价格/问规格」。
- **兜底**：判官不可用（无 Key / Mock / 超时）时，**退回现有词表**——保持改造前行为，不因新能力缺失而放宽。

**验收**：`isMedicalQuestion("推荐一款维生素D补充剂")` 为 false；`isMedicalQuestion("维生素D每日上限是多少")` 为 true。

#### R2 判官档位：补「元陈述 / 检索自述」档

**纠正**：这一项原计划是「把三处句式豁免交给判官」，但实测表明元陈述**已经在判官手里**，问题是判官**没有对应档位**。因此改法是**扩档**，不是搬移：

- 在判官判定口径中显式增加「关于本次检索范围/来源的自述」一类，归入保留侧。
  典型形态：「以上是知识库中与X相关的全部内容」「以上内容来自平台知识库」「本次检索没有查到…」。
- **判据**：这句话陈述的是**检索行为本身**，不是关于世界的事实——它的依据是检索过程，不是切片。
- **保留**：`ECHO_LEAD`、`ABSENCE_SIGNAL`、`boundaryReminder` 的确定性豁免不动（它们是同一件事的确定性兜底，双保险）。
- **保留**：越界编号摘除（确定性）。
- 判官不可用时退回现有句式（同上）。

#### R3 证据门粒度：恢复集合级

- `MedicalEvidenceVerifier.java:419` 的 `refs.stream().allMatch(单片判定)` 改为**按整轮证据集合判定一次**，句子只需引用集合内成员。
- 图谱触达（`graphChunkIds`）的语义在集合级天然成立，不再需要逐片拼装。

**验收**：KG-04 场景（引 0.1907 切片 + 同轮有强片）不再因单片低分拒句。

#### R4 边界降级：从「整轮降级」改为「范围记账」

`Agent.java:1802` 的 `setEvidenceLevel(WEAK)` 是 2.4 的直接成因。改为：

- **不改整轮 level**；边界话术的适用范围写在它自己的输出里（已经是这么写的：「仅依据本次图谱检查，无法判断X与Y」）。
- 若必须表达「某个子问题未覆盖」，用**结构化字段**（该轮已覆盖哪些、未覆盖哪些），不用全局 level 承载。

**验收**：G-16 / KG-08 / KG-11 在答对的前提下 `gateRefused` 为 false。

#### R5 主体归属：判据改用切片元数据，不依赖标题原文

第 4 类错配的修法。`MedicalEvidenceVerifier.java:153-155` 现在从**句子文本里找商品名**来建立归属；而标题已被 `numberTitles` 换成编号。

- **改后**：归属判定用**引用切片自身的元数据**（`chunk.getTitle()` / `productOwner`）——这条信息一直都在，不需要句子复述它。
- 判据从「句子里有没有商品名」变为「**引用的那片是不是这个商品的说明书**」。
- **保留**：`productOwner` 的提取规则、`本品` 必须绑定归属的要求（安全性判据不动）。
- 同理检查 `ownerContext`（`:134`）与 `declaredOwners`（`:153`）的其他消费点。

**验收**：KG-04 那句在 `TITLE_LOCATED` 之后仍被保留（探针已构造出该用例：`withTitle` 通过 / `numbered` 被拒，改后两者都通过）。

#### R6 判官层级：判官在后、规则在前（顺序对调）

- **现在**：判官放行 → 规则照样删。
- **改后**：规则只做**硬约束否决**（数量/主体/极性/越界编号），硬约束不触发时**以判官结论为准**。

#### R7 校验范围：`toolBacked` 的枚举补齐（只修 `ungrounded` 误报）

发现 H 的修法**之一**。与 R13 是**两件事**，边界必须分清：

- **R7 管「标记」**：`Agent.java:1504` 的 `toolBacked` 集合漏了 `source="approved"` 与 `"approval-recovery"`，导致确认轮被判 `ungrounded=true`、前端渲染「本轮没有平台依据」提示条（而这一轮刚执行完用户批准的操作）。**改后**：集合补齐这两项。
- **R13 管「删除」**：`finalizeMedicalReply` 的替换分支会吃掉平台常量。**那是另一条路径**，补 `toolBacked` 修不了它。

**为什么分开写**：把两者合成一条「平台常量不进校验」会掩盖一个事实——**同一个缺口在两处代码里各自成立**，只修一处仍有另一个症状。探针（四种组合全部 `unsupported=[]`）已经证明 `CitationVerifier` 本身不删话术，所以 `toolBacked` 只影响标记；**误把「补集合」当成「防空白气泡」的修法，会在下次复现时找不到原因。**

**验收**：审批轮 `ungrounded=false`（当前恒为 true）。

#### R8 工具输出：拆成「给模型」与「给用户」两个字段

发现 B 的修法。`ToolResult.output` 当前承担两种读者，这是缺陷本身。

- **改后**：`ToolResult` 增加 `userFacingText`（或让 `renderApproved` 只取工具返回的**事实部分**，不含祈使句）。
- **取舍**：优先做**最小改动**——把 `AddToCartTool` / `CheckoutTool` 里那句祈使语从 `output` 中移除，改由 `renderApproved` 统一追加提醒（提醒文案是**平台策略**，不该由每个工具各写一遍）。
- **验收**：`renderApproved` 的产物中不含「提醒用户：」「务必提醒用户」等祈使句；提醒语义仍完整表达。

#### R9 审批中断点：引用必须在本批内解析完，或降级为「先查再问」

发现 C 的修法。三个子问题分别处理：

- **`$0.id` 进卡片 —— 已修（10-08 17:32，`66c2cce`）**。会话现场（10-08 08:28）当时版本还没有这道拦截；`unresolvedRisky` 分支（`AgentGraph.java:633-650`）加入后，含未解析引用的高危步骤**不会生成确认卡**，而是先执行本批非高危准备步骤、下一轮重新解析。**保留本条是为了防回归**：修法是「拦」，不是「渲染可读描述」——拦比渲染更保守（宁可让用户多等一轮，也不让他在看不懂的卡片上点确认）。
- **`order_cancel` 参数契约 —— 已修**。`CancelOrderTool` 的 `orderId` 现在**同时接受数字 ID 与用户可见的 YS 订单号**（工具描述明写「也兼容用户看到的 YS 开头订单号」），内部按形态分流到 `cancelOrderReceipt` / `cancelOrderByNoReceipt`，回执校验也按形态分支。这正是「要求模型做两次转换，不如让接口只要求一次」的落地——**当时现场那句 `order_cancel 需要订单内部数字 ID；请先查询订单并使用结果中的 id` 本身就是把接口的不足转嫁给了模型和用户。**
- **失败重试无增量 —— ✅ 已落地（2026-10-14）**。新增快照键 `SNAPSHOT_LAST_FAILURE`：每轮结束时把**最后一个失败的写调用**压成一条事实（`tool` / `input` / `error`，各截断 200 字），成功即从快照移除；下一轮经 `lastFailureHint(SessionContext)` 注入 prompt（与 `pendingHint` 同一处——同一类信息：「上一轮在这里停过」，一个是等人点头、一个是没能做成）。提示给的是**事实与出路**而不是禁令：直接写「不得重发」会挡住「换个参数就能成」的正常重试（下游抖动、参数该换形态），所以写「同一参数原样重发会得到同一个结果；请先处理这个原因（换参数形态、先补齐缺失信息、或如实告诉用户暂时做不了），不要直接重试」。**验收**：`AgentFailureMemoryTest` 5 项（失败留痕 / 成功不留痕 / 只读失败不算 / 提示含工具·参数·原因·出路 / 无失败不产生提示）。现场证据：`u1001-1791359634411` 第 25 与第 27 轮两次完全相同的 `order_cancel(orderId=YS2026...)`。

#### R10 重新生成：历史一致性 + 自我否认抑制

发现 D 的修法，分两层：

- **一致性**：重新生成时**同步清除/改写短期记忆里的旧答案**（当前只改 `chat:hist:`，不改 `stm:`）——否则模型看到「自己说过的话」与「历史里的话」不一致。
- **抑制自我否认**：在 prompt 中明确「你无法核实历史中自己是否检索过；**若本轮没有调用工具，不得断言知识库有无某内容**」。这一条与 2.6 的元陈述档位是同一族问题：**关于「检索到了什么」的陈述，必须有本轮的检索动作背书。**
- **验收**：重新生成路径不再产生「我上一轮答错了」类自白；`level=NONE` 时不得出现「知识库没有收录 X」的断言（除非本轮确实检索过）。

#### R11 评测脚本的注入标记：不得混入用户消息语义

发现 D 的第二因。`verify-chat-ui.mjs` 把 `RUN_TAG` 写进用户消息正文（`（mv23e4ds）`），模型会把它当作**内容**解读。

- **改后**：去重标记改为**不在用户可见消息里的机制**（如 `sessionId` 维度、或独立的 `runTag` 字段），或使用模型不会误读为语义的形态。
- **注**：这是**评测装置缺陷**，不是产品缺陷；但它污染了真实数据，且掩盖了真实行为。**装置自己也要遵守「不制造误导性输入」的原则。**

### 4.3 本轮新增改造（R12–R19，对应 §2.12–2.13）

#### R12 动作级一致性：把「用户要几件事」变成可核对的账

发现 F / I 的修法。**这是本文最重要的结构性缺口**——现有四道门禁全在文本层，动作层无人看管。

三层各补一件事，缺一层都不完整：

1. **规划期：请求条数 → 计划条数**。`core_intent` 已经写出了用户要的几件事（「查 A…查 B…加购 A…加购 B」），但没有任何东西拿它对账 `plan`。加一条**确定性断言**：意图里声明的动作项与计划中的对应工具步骤数不一致时，**补一轮规划**（复用已有的 `compileAndRepairPlan` 修复通道，把差异写进 `hint`）。
   - **判据要保守**：只对**明确并列的同类动作**（「两个都加」「各来一份」+ 两个不同 SKU）报警，不做通用语义比对——否则会退化成又一次「用规则判语义」。
2. **执行期：同批动作不得折叠**。已探针证实 `executePlan` 现在不丢条目（`pending.count=2`）。**补一条回归测试锁住它**，防止将来某次「优化」把 `distinct()` 或分组合并加回来。
3. **续作期：参数与声明意图对账**。发现 F 第 2 点的直接修法。续作轮的 `taskState.core_intent` 说「把免疫配方版加入购物车」，而 `arguments.skuId` 是上一批的 SKU——**两者在同一份响应里**。加一条校验：续作轮的高危步骤，其关键参数（SKU/订单 ID）**不得与本批已执行过的相同**；命中时**拒绝生成确认卡**并把冲突交给模型重规划。
   - 这条同时能拦住「确认后又点一次确认」造成的重复加购（`× 2`）。
   - **落点**：`AgentGraph` 已经把已执行步骤注入了重规划上下文（`traceOf(steps)`，`:543` 的「不得重复已完成的写操作」）——但它只是**给模型的一句话**，模型可以不听。这里要的是**确定性校验**：把「已执行的写操作指纹（工具名 + 关键参数）」与「待确认批次」求交，非空即拒。**「告诉模型别重复」和「让系统拒绝重复」是两件事，前者已经做了、后者还没有。**

**验收**：新增用例——「两个商品各来一份」的计划必须产出 2 条 `cart_add` 且 SKU 不同；续作轮填回已执行 SKU 时必须被拦下。既有 `WriteToolConfirmationTest` / `AgentComplexDagReplayTest` 全绿。

#### R13 平台自写文案：不进模型输出校验链

发现 H 的修法。`finalizeMedicalReply` 会在 `earlierFactsRemoved=true` 且 `factSentences` 为空时把整段文本替换成兜底拒答——**这个判据对「平台自己写的常量」不成立**，因为常量本来就不含「事实句」。

- **改后**：`groundResponse` 增加一个**来源白名单**：`source` ∈ {`approval`, `approved`, `approval-recovery`, `flow`} 的回复，**跳过「句子级事实校验与替换」这一类关**（`SemanticGroundingVerifier` / `MedicalEvidenceVerifier` / `finalizeMedicalReply` 的替换分支），但**保留** `ToolFactVerifier`（数字核对）与 `CitationVerifier` 的越界编号摘除（纯确定性、无误伤）。**`fallback` 不在白名单内**——它的正文出自模型，见下方落地记录。
- **为什么不是再加白名单句式**：句式枚举是「错误长什么样」，而平台常量的集合是**封闭的、由代码定义的**——用来源判定是**穷举正确**，用句式判定是**穷举错误**。这一条正是 §4.1「规则从裁判降为哨兵」在文本层之外的实例。
- **验收**：审批轮 / 恢复轮 / 降级轮 / 确定性流程轮的 `reply` 恒非空，且 `unsupportedStripped=false`。
- **✅ 已落地（2026-10-14）**。`Agent.PLATFORM_AUTHORED_SOURCES = {flow, approval, approved, approval-recovery}`，在 `groundResponse` 里由 `platformAuthored` 与 `medicalStrict = medicalQuestion && !platformAuthored` 两处消费。**注意实际集合不含 `fallback`**：`fallback` 的正文出自模型（降级轮里模型仍可能写事实句），把它算成平台自写等于给幻觉开后门——这是与本文初稿的一处偏差，以代码为准。**验收**：`PlatformAuthoredReplyTest` 8 项（四种来源认定 / 模型来源不在集合 / 审批话术不被剔除 / 平台来源不标无依据 / 模型来源无工具记录仍按无依据 / 有工具记录即认定 / 用户可读版本回退）。

#### R14 「阶段」与「待办」不得各写各的

发现 F 副产物的修法。`ChatHistoryStore.updateApprovalMessage` 里 `stage` 与 `pendingActions` 是两个独立 `put`，7 处现场证明它们会互相矛盾（`DONE` + 有待办）。

- **改后**：把两者的关系**收敛成一个判定**——`stage` 由 `pendingActions` 是否为空**派生**，或反过来。**一处判定，另一处只负责显示**（与 13f 收口的原则同源）。
- **验收**：全量会话里不再出现 `stage=DONE` 且 `pendingActions` 非空；已有 `pendingNotWaiting` 检测项作为回归判据。
- **✅ 已落地（2026-10-14）**。`ChatHistoryStore` 新增 `stageOf(approvalStatus)`（`:650`）：只有 `PENDING` / `IN_FLIGHT` 报 `WAITING_USER`，其余（已确认 / 已取消 / 结果未知 / 被拒）都是这一轮已收尾。**扫描到的 7 处「`DONE` + 有待办」全部落在确认成功之后**——那不是矛盾，而是「已提交确认的操作」这张历史卡该有的样子（卡片留着当记录）。但「碰巧一致」与「保证一致」是两件事：新增一种审批状态时，落点只有 `stageOf` 一处。

#### R15 关于「系统自身行为」的陈述，必须由系统事实回答

发现 K 的修法（与 R10 的自我否认是同一族，但这条是**结构**修法而非 prompt 修法）。模型对以下事实**没有可靠的知情权**：本轮有没有检索、上一轮说了什么、历史里那句话是不是自己说的。

- **改后**：把「本轮实际调用了哪些工具、检索到几条」作为**结构化事实注入** prompt（已有 `taskState.context_snapshot` 一类载体），并在 prompt 中明确「这些是权威事实，不得凭记忆否认或补充」。
- **与 R2 的关系**：R2 是**判官档位**（让元陈述不被误杀），R15 是**事实供给**（让元陈述有据可依）。两条都要，方向相反、互不替代。
- **验收**：`claimsKnowledgeNoSearch` 检测项中「无检索却声称检索过」的轮次降为 0（「无检索且诚实声明无依据」保留）。

#### R16 主体继承：标题与引导句声明的实体必须可被正文继承

发现 M 的修法。当前剂量断言只从「同一句」或「上一句已支撑的剂量句」继承主体，标题行解析出的 `headingSubjects` **只服务于 `MONITORING` 分支**。

- **改后**：把 `headingSubjects` 提升为**与 `previousSubjects` 同级的继承来源**——标题行/引导句声明的实体，对其后**同层级**的正文句有效（层级由列表缩进与空行界定，换段即失效）。
- **保守边界（不能放宽的部分）**：继承只在**同一章节块内**成立；跨标题不继承；`本品` 的归属声明要求不变（`numberedSourceFrame` 那条精确形态继续保留）；主体继承来的断言仍要过 `数值 / 人群 / 角色 / 约束` 四项逐项核对——**只补主体，不补数值**。
- **验收**：`MedicalSubjectInheritanceTest` 6 项全绿——标题声明、引导句声明、句内声明三组正例放行；「本品未声明来源」「数值不一致」「人群不一致」「引导句自身含量值」四组反例仍拒。
- **风险对冲**：主体继承会把「本来判无主体」的句子放行，**放行的边界就是安全性边界**。因此这条改动的验收必须**同时**包含正例与反例，且反例优先——参照 R5 第一版改太宽打回 KG-02/KG-11 的教训。
- **✅ 已落地（2026-10-14）**。两处改动：① `headingSubjects` 从「只服务 `MONITORING` 分支」提升为**主体继承的第三来源**（就近优先：句内 > 上一句 > 标题/引导句）；② 新增 `isSubjectLeadIn`，把「短句 + 冒号结尾 + 无量值 + 非列表项 + 自身非医学事实句」的引导句记为主体声明。
  - **第一版判据太宽，被 3 条 KG-04 用例打回**：图谱关系父项（`- **华法林**：…相互作用记录：`）也以冒号结尾，被当成引导句后**父项与整棵子树一并放行**。收窄为「非列表项 + 自身非医学事实句」后 KG-04 三条转绿。**这是「放宽判据必须先想清它同时放行了什么」的第二次实证**（第一次是 R5）。

#### R17 记忆来源标注：长期记忆的事实与「本轮用户说的」必须可区分

发现 N 的修法。`memoryTrace` 已经记录了 `profileSlots` / `recalled` / `byType` / `itemIds`，但**注入 prompt 时没有标注来源**，模型一律用「你之前说」复述。

- **改后**：注入上下文时给每条记忆打**来源标记**（如「【长期记忆·2026-10-04】BUDGET=200 元以内」），并在 prompt 中明确「引用长期记忆时必须说明这是更早会话里记录的偏好，不得表述为『你刚才说』」。
- **判据**：`memoryTrace.recalled > 0` 而该会话用户消息中不含该前提时，回复不得出现「你之前说 / 你刚才说 / 你提过」这类**当前会话口径**的措辞。
- **验收**：新增检测项「记忆前提用当前会话口径复述」的命中数降为 0。

#### R18 未解析引用的高危步骤：拒绝，不推迟

发现 O 的修法。**第一版诊断指错了落点；纠正过程本身是本次改造最有价值的一条经验。**

- **第一版诊断（错）**：以为 `AgentGraph` 里 `unresolvedRisky`（`:644`）那条「推迟」分支放行了含 `$0.id` 的取消请求。
- **纠正后的真相**：那条分支**是不可达死代码**——走到它时 `unresolved` 必为空（上游 `:613` 的分支已经处理了所有含未解析引用的 ready 步骤并 `continue`/`return`），而高危步骤是 ready 的子集，所以 `unresolvedRisky` 永远为空。**它读起来像一道防线、实际一次都不会执行**，后来的人会以为「推迟机制」存在，从而把真正的缺口留给别处。已删除并留不变式说明注释。
- **真缺口在 ReAct 路径**：`LangChain4jLLMProvider.executeToolRequests`（`:396` 起）对高危工具**零引用检查**，而 system prompt 又确实教了模型 `$N[i]` 语法（多步任务示例写着 `cart_add` 用 `"$0[0].skuId"`）→ 模型在 ReAct 轮里照写，`$0.id` 字面量一路穿进确认卡。计划路径有 `resolveBatch` 逐参数填值，ReAct 没有「计划」可以预先解析。
- **改后**：在 `requiresConfirmation(request.name())` 分支内，若 `StepReferences.hasUnresolved(arguments)` 则**不生成载荷**、回填可执行纠正（「先用查询工具取得真实编号，再用真实值重新调用 X」）后 `continue`。**与「用户还没批准」的中断不同**——那一种模型修不了（只能中断循环，转一圈它只会换个说法再要一次，每一圈都是真实计费调用），这一种模型自己修得了（只是缺一次查询），所以退回的是可执行纠正而不是死胡同。
- **语法收敛到单一来源**：新增 `StepReferences`（`REF` / `MARKER` / `PATH_TOKEN` 三个 Pattern + `hasUnresolved(Object)` 递归判据），`AgentGraph` 与 `LangChain4jLLMProvider` 共同引用。此前「什么算引用」有两个定义，一处认、一处不认，症状是某个形态的引用从其中一条路径静默漏过去。
- **验收**：`ReactToolLoopTest` 新增用例——参数含 `$0.id` 的 `order_cancel` 不得产生 `pendingActions`，且退回后模型改用真实值（第二轮）必须能拿到正确载荷（`requests == 2`）。**只断言「第一次被拒」的话，一个把模型逼进死胡同的实现同样能通过。**

#### R19 计数词与剔除联动（并入 R12）

发现 P。R12 已经建立「动作级一致性对账」，本条是它在**文本层**的对应物：剔除句子后，若正文里出现「这两款 / 三档 / N 种」而实际条目数不符，**要么补全条目、要么改掉计数词**。

- 这一条**不做通用语义比对**（会退化成又一次「用规则判语义」）：只在**同一段落内**出现计数词且**紧邻列表项数**可数时触发。
- **验收**：`stripDangling` 检测项的命中数显著下降；`u1003-1791680700402` 这类「说三档列两档」不再出现。
- **✅ 已落地（2026-10-14）**。新增 `CountReconciliation.reconcile(reply)`，接线在 `Agent.java` 的 `response.setReply(finalReply)` 之前（全部剔除之后）。**判据三条**（缺一不可）：① 同段落内只有一个连续列表块；② 计数词出现在列表块**之后**；③ 计数词后紧跟**谓词性成分**（`都|均|全|是|在|正|可`）——即它是主语，不是定语。
- **反例清单（四种一律不动）**：计数词作定语（「三种支付方式都可以」——数的是支付方式，与列表行数无关）；两个列表块（配对关系不确定，猜错会把一处错误换成另一处错误）；列表之前的计数词（「以下三档」指代对象可能是别处）；读不出的数（「十几」）。**「改模型写的话」的改动，反例比正例重要**——判据放宽就会把正确的话改错，且改完同样通顺、看不出发生过什么。
- **改计数词，不补条目**：补条目要凭空造内容（被剔除的那条正是因为无依据），而计数词是模型自己写的修饰，改它不引入任何新事实。
- **验收**：`CountReconciliationTest` 8 项（正例 2 + 反例 5 + 无列表 1）。落点：`agent-core/.../rag/CountReconciliation.java`。
### 4.4 第五层扫描新增改造（R20–R23，对应 §2.14）

#### R20 医学路由：判据只认用户原话，且「问商品」优先于「含医学词」

发现 T/V 的修法，**与 R1 是同一件事的两半，必须一起做**。

- **R1 管「谁来判」**：词表 → 判官。
- **R20 管「拿哪一份文本去判」**：`Agent.java:447` 的
  `isMedicalQuestion(message) || isMedicalQuestion(retrievalQuery)` —— **后者必须去掉**。
  改写句是给检索用的，它把指代补全、把商品名展开，恰恰是「用户原话里没有的医学词」的来源。
  实测 38 轮里 3 轮因此把**取消加购**判成医学问题并整篇兜底。
- **判据方向**：`retrievalQuery` 只能用于**检索**，不得回流到**路由**。若确实需要「改写后才发现是医学问题」的能力，那也应该由判官在**读完用户原话 + 对话历史**后决定，而不是靠一个给检索器用的字符串。
- **验收**：`isMedicalQuestion("取消刚才的操作，不执行加购。")` 为 false（当前因改写而 true）；`CA-022` 第 3 轮、`u1003-1791874549403` 第 2 轮的 `reply` 不再是医学兜底句。

#### R21 商品行的放行判据改为「与工具回执逐字段核对」

发现 U 的修法。`supportedProductRow` 当前是**先按排除词表否决、再要求结构化匹配**；排除词表（`含有|成分|适用|每日|…`）会把最正常的商品描述挡在门外。

- **改后**：把顺序反过来——**先看能不能与 `product_search` 回执逐字段对上**（SPU/SKU 编号、规格文本、价格），能对上就放行；对不上才回到医学证据链。
- **理由**：商品行的数据来源是**工具回执**，不是知识切片。要求它引用切片是把两套来源混成一套。
- **保守边界（不能放宽的部分）**：一旦句子含**医学断言**（剂量/相互作用/风险/疗效——即 `isMedicalFact` 成立），**仍走医学链**，不得因「能对上商品回执」而放行。**商品事实与医学结论是两种句子，不能因为前者可核对就放过后者。**
- **验收**：新增用例——`| 1 | 孕妇钙片 | 柠檬酸钙 500mg + 维生素 D3 400IU，孕期哺乳期适用 · SKU34 | 129.00 元 |` 在有对应 `product_search` 回执时放行；同一句若改成「孕期每天需补钙 1000mg」，仍被拒。

#### R22 平台自写段落不参与「整篇替换」

发现 T 第 3 点的修法。`finalizeMedicalReply` 在判「整篇无依据」时，会把**平台自己拼的商品候选列表**一起替换掉。

- **改后**：兜底替换只作用于**模型生成的那一段**；`ProductCandidateList.render` 拼出的段落（以及审批话术、流程回执）在替换时**原样保留**。
- **与 R13 的关系**：R13 是「按 `source` 跳过校验」，R22 是「替换时保住平台段落」。**R13 管入口、R22 管出口**——即使某一轮没被 R13 判成平台来源（例如计划路径的正文确实是模型写的），商品列表段落也必须在替换中被保住。
- **验收**：新增用例——模型正文全被判无依据时，`reply` 里仍含完整商品候选列表；且医学兜底句与商品列表**不混排**（要么是纯兜底，要么是兜底 + 平台段落，不得是「兜底句 + 模型残留半句」）。

#### R23 判定输入的「来源纯度」：路由只看原话，核验只看本轮

发现 V 的**结构性**修法（R20 是它的一个实例）。把「哪一份文本可以喂给哪一道判据」写成一条明确规则：

| 判据 | 输入 | 不得使用 |
|---|---|---|
| 路由（是不是医学问题） | 用户本轮原话 + 对话历史 | **改写后的检索句** |
| 检索 | 改写后的检索句 | — |
| 引用/证据核验 | 模型正文 + 本轮证据 | 上一轮的证据、历史里的引用编号 |
| 记忆前提 | 长期记忆（带来源标注） | 当前会话口径（R17） |

- **理由**：**改写的目的是让检索更准，它的输出是「检索用的查询」，不是「用户的意图」。**把中间产物当意图用，等于让一个为召回率优化的变换去决定业务路由。
- **验收**：`Agent.java` 中不存在把 `retrievalQuery` 喂给路由判据的调用点（当前 `:447` 有一处）；新增断言锁定「路由判据只读 `message`」。

### 11.11 面试可讲经验（本轮四条）

- **一次只读探测改写了状态**——`enforceUnknownInteractionRefusal(response, "", true)` 本意是问「边界文本在不在」，副作用却把整轮证据门从 SUFFICIENT 降成 WEAK，4 例过拒由此产生。**纯查询不得有副作用**；判据的写入点必须留痕，否则只能靠「入口 SUFFICIENT、出口 WEAK」两行日志反推。
- **判据在追一个自己刚擦掉的证据**——`numberTitles` 把标题换成 `[1]`，下游却要求「句子必须声明来源商品名」。同一份信息换了载体，判据没跟着换。
- **探针参数写错会把结论整个带偏**——G-14 第一版探针传空 `verifiedSubjects`，等于关掉主体继承，得出「误杀」的错结论。**验证工具本身要先自证。**
- **「放宽判据」不是唯一出路**——同一个现象（答对了却被拦），可能是门禁问题，也可能是生成精度问题。分不清就会去改一个没坏的地方。


### 11.12 4.1 缺口的修复与 alice 真实复测（`6583073e`，2026-10-15 05:02）

**现场（alice `u1001-batch-dup-1792006692964`）**：用户「把越橘叶黄素片加入购物车」→ 拿到确认卡片 → 点确认执行成功 → **紧接着又回一句「确认执行」** → 系统重新生成一张一模一样的卡片。用户再点一次就是同一件商品加两遍，而购物车没有删减入口。

**根因（生产数据取证，非推断）**：确认轮 `executeApproved` 在 `doChat` 里**提前 return、不走常规收尾**，于是会话现场永远停在「执行之前」的样子。Redis 实证：

```
agent:session-context:u1001:u1001-batch-dup-1792006692964
  pendingTools: ["cart_add(quantity=1, skuId=28)"]   ← 执行成功后仍然挂着
```

下一轮 prompt 里那段「还有待确认的操作」照实注入，模型据此把同一件商品重新出了一张卡片——**它看到的现场就是错的，重出一张是它对那份现场的正确反应**。这与 R14（stage 与 pending 不同源）是同一族缺陷的另一半：同一事实在「响应」与「现场」两处各算一遍，且只有一处被更新。

**两处修法（全部确定性，不进模型、不花 API 费用）**：

1. **现场对齐**（`syncPendingAfterApproval`）：确认轮结束后把会话现场的 `pendingTools` 对齐到本轮真实载荷——一处判定（响应），另一处只负责读（现场）。失败只记日志：现场是增强项，一次存储抖动不该让一次已执行完的确认轮变成报错。
2. **协议出口**（`isBareConfirmPhrase` + `APPROVAL_IDLE_REPLY`）：平台自己教过「直接回复「确认执行」」这四个字，用户照做而**现场没有可确认载荷**时，由平台直接答，不再交给模型猜——那次猜测正是重复卡片的来源。判据收得很紧：整句就是 `确认执行` / `确认`（允许尾随标点），且 `pendingHint == null` 且 `sessionContext.pendingTools().isEmpty()`。**刻意不包含**「确定」「是」「好的」：它们更可能是一句普通回应，在没有对象时放宽会让别的话题里一句「好的」收到「没有执行任何操作」。

**为什么不是把账本搬到会话级**：曾评估把写操作指纹搬进 `SessionContext`（7 天 TTL），但那样会让「30 分钟内再买一件同款」被自己的历史拦下——**误拦合法操作比多问一次更糟**。这条缺口不是安全缺陷（无令牌路径永不执行写操作，只多出一张需要重新批准的卡），所以修的是「现场如实 + 口令由平台接住」，不是加一道更严的门禁。

**测试锁定**（先红后绿）：`AgentConfirmWithoutPayloadTest` 3 项——①执行完再回口令不长出第二张卡（且不进图、不产生第二次副作用、来源是平台自写）；②卡片还挂着时不带令牌的口令仍走正常链路；③口令混在句子里（「帮我确认执行一下退款流程」）仍交给模型。红测证据：断言失败信息正是生产现场那句 `cart_add(quantity=1, skuId=28)`。
