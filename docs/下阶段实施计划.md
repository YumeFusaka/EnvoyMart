## 〇、总原则（不可协商，冲突时以它为准）

1. **能查到就必须给**：商品库 / RAG / 图谱任一路径能捞到相关内容，agent 必须结合用户提问做评估，给出推荐 + 为什么推荐 + 有什么作用。
2. **拿不准就先问**：信息不足（"肠道不好"可能是便秘/腹泻/腹胀）时先澄清再检索，不拿模糊输入硬查、拿不相关结果凑答案。
3. **只有真的没有，才说没有**：RAG 与图谱都找不到相关商品时，说的是**"知识库里没有"**，不是**"你不能吃"**。这是平台资料覆盖度的陈述，不是医学结论。
4. **存储质量是上游**：回答质量依赖检索质量，检索质量依赖存储质量。**"有商品但没资料"本身是一个应当被发现的缺陷**，不是可以接受的终态。
5. **拒答门不推翻**：`EvidenceGate` 防的是"模型拿常识编造平台事实"，防的是**编造**，不是**话题敏感**。
6. **安全边界照资料办**：资料里写着禁忌/就医提示的（如"肠梗阻、肠道狭窄者禁用"），照着说并建议就医；判据是**资料里有没有写**，不是话题敏不敏感。

## 批次 A · 修 P0-A（商品被引用校验误剔除）

### 问题定义

用户看到"空商品表格"（只剩表头）。**不是渲染 bug**，是 `CitationVerifier` 把商品行整句剔除：

- `cited` 只计 `[n]` 角标与《文档名》，商品表的出处是 **`product_search` 工具返回**，两者都不算 → 判为"讲事实没出处"
- `cited = 4 > 0` 使 `knowledgeAnswer = true`，`withinBudget` 成立 → 执行剔除
- 结果：表格行被逐句删掉，**表头留在原地**，渲染成一张空表

### 根因

`CitationVerifier` 的"可引用出处"只有两态：**prompt 证据的 `[n]`** 与**工具输出"出处："行里的《文档名》**。
**"工具返回过的商品/订单实体名"这一态缺失**——它同样是平台自己声明过的事实，且识别面天然收窄（收窄到"工具真的返回过"）。

### 改法

1. **新增"工具声明实体"作为第三类可引用依据**
   - `ProductTool` 在 `ToolResult.facts` 里声明本轮返回的商品（如 `商品:SPU5 益生菌粉`）——**沿用已有的 `facts` 通道**，不新造平行机制：`ToolFactVerifier` 已经在用同一份数据做数值核对，商品名同属"工具自己声明的事实"
   - `Agent` 收集 `ToolExecution.facts` 里声明的实体名，与 `citableTitles` 同层传给 `CitationVerifier`
   - `CitationVerifier.hasValidCitation` 增加第三判据：句子命中了"工具声明过的实体"也算有出处

2. **识别面必须收窄**（关键，否则闸门失效）
   - 只认**工具真的返回过**的实体名，逐字比对 + 忽略空白，不做模糊匹配
   - 不接受模型自述的实体列表（`ProductSearchService` 的词表不参与）

3. **剔除粒度修正**
   - 表格行被拆开后表头残留比整段消失更困惑：**剔除时若删掉的是表格行（以 `|` 开头），一并处理表头与分隔行**——若该表已无有效数据行，整表一起删

### 改动落点

- `agent-core/.../rag/CitationVerifier.java`：新增工具实体集合参数、第三判据、表格感知剔除
- `agent-core/.../core/Agent.java`：收集 `execution.getFacts()` 里的实体名并传入
- `ai-service/.../tool/ProductTool.java`：`ToolResult.facts` 声明商品名与编号
- 单测：`CitationVerifierTest` 补"工具实体算出处""编造商品仍剔除""表格行剔除不留空表头"

### 验收证据

| 验收标准 | 证据来源 |
|----------|----------|
| alice 三个会话的商品表还在，商品名/价格与工具返回逐字一致 | 重跑 `u1001-1791252142046` / `-1791252238126` / `-1791252059073`，比对响应体表格与 `product_search` 的 output |
| 模型编造的商品名**仍被剔除** | 构造样本：编一个不在工具返回里的商品名，断言进入 `unsupportedClaims` 且被剔除 |
| 表格不再出现"只剩表头" | 同第一行的真实会话，断言正文不含孤立表头 |
| 不误伤订单/物流类回答 | 跑 `verify-chat-ui`、`verify-cross-batch` 相邻断言 |

### 回滚点

单文件级：还原 `CitationVerifier` + `Agent` 的收集逻辑即可，无数据/契约改动。

## 批次 A / A2 · 完成记录（2026-10-06）

### 做了什么

**A · 商品被引用校验误剔除**
- `ToolResult` / `ToolExecution` 新增 `entities` 通道（**与 `facts` 分开**：`facts` 是「标签→取值」的取值核对，`entities` 是「本轮存在过什么」的存在性核对。合成一个字段会让校验器分不清「写错取值」与「编造实体」）
- `ProductTool` 声明本轮返回过的商品编号、商品名、副标题、规格编号
- `CitationVerifier` 新增第三类出处：命中「工具返回过的值」也算有出处
- 两条出口都要带：`Agent`（计划路径）与 `LangChain4jLLMProvider`（ReAct 路径）——**只补一处会漏**，实测就是漏了 ReAct 那处

**A2 · 症状类提问必须检索商品**
- `Agent.buildSystemPrompt` 新增症状/健康类规则：**必须先调 `product_search` 再回答**，写进 system prompt 而不是工具描述（失效发生在模型决定不调工具的那一刻，工具描述那时根本没被读到）
- `KnowledgePrompt.none()` 补上「知识库没有依据 ≠ 平台没有相关商品」
- 新增 `HealthQueryCoverage`（观测，只记日志不拦截）：症状类提问若本轮没有 `product_search` 执行记录，`log.warn` 报警。按「能查到就必须给」这条原则，把「它到底查没查」变成日志里能读出来的事实

### 实测证据（真实链路，alice u1001）

| 场景 | 修复前 | 修复后 |
|------|--------|--------|
| 「最近肠道不好，应该吃什么药」 | `product_search` 0 次；回答「知识库没有用药依据」；商品表被删空 | `product_search` 2 次 + `knowledge_search` 2 次；`stripped=false`；给出商品表 + 作用说明 + 澄清问题（便秘/腹泻/腹胀） |

| 「发烧了应该吃什么药」 | — | 检索 3 次（退烧药/布洛芬/对乙酰氨基酚）**确实没有** → 才说「没有查到」，并解释药品不该由助手推荐 |

## 批次 B · 存储质量把关 + 覆盖率可观测

### 问题定义

用户追加判据："**如果存在相符的商品，但它对应的资料不全面，导致没能到达可以推荐给用户的阈值，就算是有问题了**。"
现状：管理台只能**逐个**商品看"被哪些文档支持"，**无法回答"多少在售商品有资料、多少没有"**。

### 改法

1. **覆盖率读数接口**（知识服务）
   - `GET /knowledge/admin/coverage`：返回 `{ totalSpu, coveredSpu, uncoveredSpu: [{spuKey, name, reason}] }`
   - 口径：商品 → 图谱一跳 `CONTAINS` 关系（与 P0-1 的 `documentsOfProduct` 同一判据，**不另立口径**）
   - `reason` 区分"图谱无此节点"（从未构建）与"有节点但无文档边"（说明书没入库）——两者的修法不同

2. **管理台可把关**
   - 商品列表页（或知识库页）显示覆盖率数字 + "未覆盖商品"清单，可点进商品编辑页直接上传说明书
   - 空态要给出**下一步动作**，不是只报一个数字

3. **上架流程提示**
   - 商品编辑页已有"说明书与知识依据"面板 → 无资料时给出**明确的待办提示**（不是错误，是欠账）

### 改动落点

- `knowledge-service/.../graph/GraphService.java`：`coverage()` 聚合查询
- `knowledge-service/.../controller/KnowledgeAdminController.java`：新增接口
- `frontend/src/api/admin/knowledge.ts` + 管理台页面：覆盖率卡片与未覆盖清单
- 单测：`GraphServiceRecallTest` 补覆盖率用例（有节点无文档、无节点、正常覆盖三态）

### 验收证据

| 验收标准 | 证据来源 |
|----------|----------|
| 覆盖率数字与图谱真实状态一致 | 对拍：接口数字 vs `GraphService.documentsOfProduct` 逐个抽查 5 个 SPU |
| 未覆盖清单能区分两种原因 | 构造样本：一个未构建节点、一个已构建无文档边 |
| 前端能看到数字与清单、能点进商品 | 管理台截图 + 点击跳转确认 |
| 无 token 返回 401 | curl 断言 |

### 回滚点

新增接口与页面区块，删掉即可，不影响既有链路。

## 批次 C · P0-B 澄清优先 + 症状类查询评估

### 问题定义

alice 三个会话都是"症状 → 商品"：用户说症状，语料写成分与适应症。当前 agent 直接硬查、拿不相关结果凑答案，或退回泛泛免责声明。

### 改法（三条可执行规则）

1. **澄清优先**
   - `EvidenceGate` / 提示词层增加"信息不足先问"的判据：症状类查询（含"不舒服/不好/疼/胀/发烧"等无明确指向词）**在检索前**先产出澄清问题
   - 澄清问题必须**能缩小结果集**（"是便秘还是腹泻？"），不能问"你能说详细点吗"
   - **不设轮数上限**，但每轮必须带来信息增量

2. **能查到必须给**
   - 检索到相关内容时，回答结构固定包含：**推荐 + 为什么推荐 + 有什么作用 + 不能替代药物治疗的提醒**
   - 禁止因"医疗话题敏感"退回成免责声明——判据是**平台有没有依据**，不是话题

3. **"没有"的正确说法**
   - 只有 RAG 与图谱都查不到时，说"知识库里没有收录相关商品"
   - **禁止**说"你这种情况不能吃"——这是医学结论，平台没有资格下

### 改动落点

- `agent-core/.../rag/KnowledgePrompt.java`：症状类查询的澄清优先与回答结构约束
- `agent-core/.../rag/EvidenceGate.java`：确认"无依据"不与"症状类"错误耦合
- 可能涉及 `Agent.java` 的一轮提前返回（澄清轮不检索）
- 评测：`eval/` 下新增症状类样本（该澄清 / 该推荐 / 该说没有 三类）

### 验收证据

| 验收标准 | 证据来源 |
|----------|----------|
| "肠道不好"给澄清问题或带说明的推荐，**不得只有免责声明** | 重跑 `u1001-1791252142046` |
| 推荐包含"为什么推荐 + 有什么作用" | 断言回答文本含作用说明段 |
| 商品名/价格与工具返回逐字一致 | 同批次 A |
| "平台确实没有"样本说"知识库里没有"而非"不能吃" | 构造样本断言关键词 |
| 资料里有禁忌时给出就医建议 | 构造"肠梗阻"样本，断言引用资料里的禁用提示 |

### 回滚点

提示词与评测改动，还原文件即可；不涉及数据。

## 批次 D · P2-1 复杂任务编排（**最高优先级，拆三批**）

### D1 · 跨轮意图切换与上下文隔离

**问题**：真实用户在同一会话里混问（推荐 → 订单 → 成分 → 疾病），当前意图路由按**单轮**判断。

**改法**
- 维护会话级状态：`core_intent`、`current_subtask`、`pending_tools`、`completed_steps`、`context_snapshot`（字段命名与用户拍板一致）
- 状态机：`PLANNING → EXECUTING → WAITING_USER → CHECKING → DONE`，**合法流转校验**
- 按会话/线程 id 隔离；`taskId` 标识任务；关键步骤存 checkpoint
- 意图切换判据：本轮问题与 `core_intent` 的领域对象**不重叠**时切换，而不是"关键词命中"

**验收**：构造"先推荐再查订单再问成分"的单会话序列，断言每轮调用正确的工具集、上下文不串味；中断后能恢复。

### D2 · 多轮澄清

**问题**：C 批次给了澄清能力，但只是"一轮问一句"；真实场景需要**多轮收敛**。

**改法**
- `WAITING_USER` 状态承接澄清；把已收集的信息写进 `context_snapshot`
- 每轮用已收集条件**重新检索**（不是把条件堆在提示词里让模型自己推）
- 收敛判据：条件足以选出候选集时转入 `EXECUTING`

**验收**：三轮澄清后给出一致推荐；中途改口（"其实是腹泻"）能纠正而不是叠加。

### D3 · 推荐 → 加购 → 下单 → 支付卡片

**问题**：链路存在但需要模型自己串；用户"加两份到购物车""下单"时应有确定行为。

**改法**
- 推荐卡片 → 加购 → 购物车确认 → 下单 → **支付卡片**（前端可点，跳支付页）
- 结构化的 `$N.skuId` 引用已有（`ProductTool.withDefaultSku`）；补的是**跨轮的指代消解**（"把第二个加进去"指的是上一轮推荐的第 2 条）
- 支付卡片走既有支付流程，不新造

**验收**：完整跑通用户原话里那条链路，含前端卡片出现与点击跳转。

### 回滚点

D1/D2 是新增状态管理，落地在独立类里，可整体关闭（配置或开关）退化为当前单轮路由；D3 若前端风险大，先只做后端编排 + 文本确认。

## 批次 E · P2-2 情节召回过取上限

### 问题定义

`EpisodicMemory.recall` 用 `VectorStore.search(query, overFetch)` 后**在应用层按 userId 过滤**。
当记忆库很大、某用户条目被挤出过取窗口（`limit * 20`）时，**静默漏召回**。代码注释已自注这是已知上限。

### 改法

- `VectorStore` 接口新增带过滤条件的检索（Milvus 用 `filter expression`，`docId == userId`）
- 默认实现（`InMemoryVectorStore`）按同样语义过滤
- `EpisodicMemory.recall` 走新接口，去掉应用层过滤与过取倍数
- **保留** `mergeRecent` 兜底（过滤后仍可能不足 limit），但去掉那条"可能已触达过取上限"的日志——它描述的情况已不存在

### 改动落点

- `agent-core/.../rag/VectorStore.java`：新增 `search(query, topK, filter)` 或等价设计
- `agent-core/.../rag/InMemoryVectorStore.java`、`ai-service/.../rag/MilvusVectorStore.java`
- `agent-core/.../memory/EpisodicMemory.java`

## 批次 F · P1-2 冲突持久化

### 问题定义

冲突每轮现算，同一条矛盾下次还要再发现一遍。用户拍板："**正确的决策需要持久化**"。

### 前提：先把判据写清楚（**没有判据不动手**）

| 问题 | 判据 |
|------|------|
| 谁裁定 | 系统按 `SourceAuthority` + 版本时效裁定（已有），**人工确认仍走原有上报路径** |
| 依据什么字段 | `source` 权威度 + `version`/`updatedAt` 可比较性 + 冲突双方切片 id |
| 再出现时怎么办 | 命中同一条已裁定记录 → **沿用裁定结果并注明"已于 X 时裁定"**，不再重复上报 |
| 什么时候必须重新裁定 | 参与冲突的**任一切片内容或版本变化**时，旧裁定作废（按切片 id + 内容哈希判定） |

### 改法

- 新增冲突裁定记录（表 or 存储），键 = 冲突指纹（双方切片 id + 内容哈希）
- 裁定结果分"已裁定（含依据）"与"待人工确认"两态
- 回答里冲突段带上"已于 X 时裁定"的说明

**关键风险**：做错会让"上次判过"变成"这次不判"，把真实分歧静默吞掉。所以**内容哈希变化必须使旧裁定失效**——这也是本批最重要的断言。

### 验收证据

| 验收标准 | 证据来源 |
|----------|----------|
| 同一条冲突第二次出现时沿用裁定且注明 | 连跑两次同题查询，断言第二次带"已裁定"说明 |
| 切片内容变化后重新裁定 | 改一份文档重新入库，断言冲突重新上报 |
| 裁定依据可在输出里看出来 | 断言输出含权威度/版本依据 |
| 无冲突时不产生记录 | 断言干净轮次不写记录 |

### 回滚点

新增存储 + 读取路径；可通过开关退回"每轮现算"。

## 批次 G · P1-3b 组合禁忌（完整方案 B）

### 问题定义

`CAUTION_FOR` / `INTERACTS_WITH` 只支持单跳语义，风险写在边的 `effect` 上。**"三样两两没事、三样一起有事"表达不出来。**

### 改法（用户选定 B：超边/组合节点）

1. **表达**：新增组合节点，如 `(A,B,C)` 作为图上的中间节点，由三条 `PART_OF` 边连接
2. **抽取词表**：识别"同服/一起吃/搭配"等多实体组合句式
3. **写入期形状校验**：`relation.acceptsHead/Tail` 需接受新节点类型——**这是本批最容易出错的地方**（形状校验改动会连带影响既有写入）
4. **查询三处**：`GraphService` 召回、`InteractionCheckTool` 渲染、`InteractionReport` 输出

### 验收证据

| 验收标准 | 证据来源 |
|----------|----------|
| 构造"两两无事、三样有事"样本，能标出组合风险 | 图谱查询 + 工具输出 |
| 既有单跳关系不受影响 | 相邻用例断言 |
| 写入期拒绝形状非法的关系 | 单测 |
| 前端"关系与出处"能展示组合关系 | 截图确认 |

### 回滚点

图结构变更是高风险操作：先备份当前图谱构建产物，回滚 = 还原抽取/校验/查询三处代码并重建图谱。
