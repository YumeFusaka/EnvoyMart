## P1-1 · 语义档（✅ 已完成 2026-10-06）

**结果**（生产配置 = 混合 + 重排 + 扩写，夹具 90 篇 / 120 条）

| 档位 | 改造前 | 本次动手前 | 现在 |
|------|--------|-----------|------|
| 字面 | 0.975 | 1.000 | **1.000** |
| 口语 | 0.700 | 0.975 | **1.000** |
| **语义** | 0.225 | 0.725 | **0.875** |
| 全量 | 0.633 | 0.900 | **0.883**（同批口径 0.867 → 0.883） |

**根因（已定位）**：语义鸿沟档的样本形态是「生活口语 → 文档主题名」的映射
（「太贵了」→ 价格保护、「钱少了一部分」→ 退款到账时间），**这类映射不需要向量才能跨**——
把口语落到文档主题词上，词法侧就能命中。而原先的角度改写提示词只说
「同义词、上位词、口语说法、专业术语」，产出的是**同义改写**，没落到主题名上。

**改了什么（只有一处）**：`agent-core/.../rag/LlmQueryExpander.java` 的 angles 要求，
从「换一个同义词」改为「**落到知识库会用来命名一篇文档的主题词**」，给了四组示例，
并要求两条改写分别落在**两个不同主题**上、写成名词短语而非问句。
随后重采夹具（`RUN_EXPANSION_CAPTURE=true`，120 条真实调用，**120/120 覆盖、0 失败**）。

**没有动的地方**：仍是一次调用产出 `hypothetical` + `angles`；逃逸口仍收着；
HyDE 仍只喂语义路、angles 仍只喂词法路。

**证据**

| 检查 | 结果 |
|------|------|
| `RetrievalQualityTest`（CI 门禁，无 Key） | 5/5 通过 |
| 词法路语义档 | 0.350 → **0.475**（+5 条） |
| `RetrievalComparisonTest`（真实 embedding + 重排） | 语义档 0.650 → **0.875** |
| 重排调用 | 生效 720 次，降级 0 次 |
| 文档 | `docs/检索效果对照实验结果.md` 追加本轮章节 |

**一个值得记下的归因**：只加角度改写（不喂 HyDE）时语义档 0.625，**比不加扩写（0.650）还低**，
加上 HyDE 后跳到 0.875。上一轮结论是「增益全来自角度改写、HyDE 净效果≈0」，
本轮**翻面**——把 angles 锚到主题词后，它不再与 HyDE 争抢同一个作用面。
**"某一半没用"的结论，换一个提示词就可能翻面。**

**剩余差距（未覆盖，不许省略）**：夹具 90 篇短文档，线上 47 篇 / 408 片，形态脱节（P2-3）；
本轮所有数字都是**夹具数字**。
## P1-3 · 图谱三个缺口（对应「超重点」第 7 条）

溯源侧已强（`[n]` → 切片 → 原文高亮全链路可点），缺口在图谱本身。

### P1-3a · 实体别名覆盖（✅ 已完成 2026-10-06）

**现状**：`EntityAliases` 是手写表（设计正确——别名是领域知识，写错一条就是把两种药当成一种），但覆盖面有限。`EntityNames` 只处理同词的拼写差异（空白、大小写），处理不了「同一个东西的不同叫法」。

**已知未覆盖**：人群节点层次（`孕期` / `妊娠期与哺乳期女性` / `备孕期与孕早期女性` 三者互不连通）。类注释已写明这是**有意不合并**——它们确实是三个不同人群，压成一个会把漏报换成误报；缺的是 `IS_A` 上位关系，不是别名。

**改法**：
1. 补别名表里缺失的**同类异写**（有明确医学等价、且不改变结论的）；
2. 人群节点走**上下位关系**（新增 `IS_A` 或 `SUBSET_OF` 边），查询时沿父节点向上跳一跳——这要动抽取词表与提示词，成本比补表大；
3. 别名命中率做成可量化的：给一组「用户口语写法 → 期望规范节点」的样本，断言命中率。

**验收证据来源**：别名命中率用例；「富马酸亚铁→铁剂」跨文档多跳能查到（这是该表存在的原始理由）。

### P1-3b · 组合禁忌（三样两两没事、三样一起有事）—— ✅ 已完成（方案 B，2026-10-06）

**现状**：`CAUTION_FOR` / `INTERACTS_WITH` 只支持单跳语义，风险写在边的 `effect` 上。这是设计选择（风险本就由组合导致），但意味着**多元组合表达不出来**。

**为什么必须落到图上，A 方案不够**：A（Agent 侧把各自的单跳风险汇总、标「多项叠加」）只能回答「这几样各自有什么风险」，面对「两两没事、三样有事」时给不出任何提示——因为图上根本没有一条单跳边可说。而那类结论恰恰是文本检索也答不了、图谱独有的价值。**「没有可讲的边」不是聚合策略能补的，是结构缺了一块。**

**改法（B：组合节点）**——动了三处，每处的判据都写在下面对应的方法注释里：

1. **表达**：新增关系 `GraphRelation.COMBINED_WITH`（组合禁忌）与结构标记 `EntityKind.COMBINATION`。
   组合节点的键是成员名**排序后**拼接（`combo:维生素d|钙|铁剂`），因此同一个组合无论从哪篇文档抽出来都落到同一个节点，条数与来源可正确累加。
   `COMBINATION` **不出现在抽取提示词的类型清单里**（词表由 `EntityKind.values()` 生成）——它是结构不是知识，列进去会让模型到处去建组合节点。
2. **抽取**（`KnowledgeGraphBuilder`）：提示词加规则 5b —— 只有一句话把要一起服用的**全部成员都点名**时才抽组合；`linkProducts` 对组合三元组显式分流，不送进商品目录对齐（否则会被当作「对不上目录的商品」整条丢掉，而日志只有一句普通的丢弃）。
3. **写入期形状校验**（`TripleValidator.validateCombination`）：三条判据——成员 ≥ 2；**引文必须同时提到全部成员**；尾端必须出自原文。第二条是本批最要紧的一条：文档里「铁剂与钙剂同服影响吸收」逐字存在、也确实提到两样，但它支撑不了「铁剂+钙剂+维生素D」。少了它，模型只要找到一句提到部分成员的话就能把一个更大的组合挂上去，而图上看起来有完整出处。
4. **查询**（`KnowledgeGraphStore.combinationsOf` + `GraphService`）：判据是**成员被本次输入的集合全覆盖**（`covers`），不是「相交」。按相交匹配等于把一条**条件边**当成无条件边——用户只带了其中两样时也会被告知「有组合风险」，而他分开吃、以为规避了，真实风险与第三样有关。挂在报告上时按「成员与该项有交集」分发（组合天生跨项，任何单个 root 都装不下它）。

**验收证据（单测）**：`TripleValidatorTest` 21 项含 4 条组合用例；`GraphServiceRecallTest` 8 项含 3 条组合用例（三样都问到→出现、只问到两样→不出现、键形状反例）。

**已知边界（如实列出）**：① 线上 47 篇语料里**没有**「三样同服才出事」的原句，因此这条链路**没有真跑过端到端**，四个用例都是构造样本；抽取提示词是否真能稳定抽出组合，要等有这类文档时才知道。② 组合节点目前不进 `nearestEntity` 兜底词典。

### P1-3c · 图外实体的最近实体兜底（✅ 已完成 2026-10-06）

**现状**：图上没有的实体直接返回空。用户说「鱼油」而图上是「深海鱼油」时命中不稳定。

**改法**：`GraphService.recall` 在精确/子串都未命中时，走一次近似匹配（别名变体 → 编辑距离/token 重合），返回「最相近实体 + 明确标注这是近似命中」，而不是空。**必须标注是近似**——否则模型会把猜出来的当成事实。

**验收证据来源**：未收录写法能返回近似实体且标注清晰；已收录写法不受影响。

## P1-2 · 冲突决策（对应第 8 条）

**现状**：`ConflictReporter` 只呈现不裁决（刻意——模型替用户选一条会把「资料打架」伪装成「查证完毕」）。`KnowledgePrompt` 只裁「版本能分出先后」这一种。`source`（`manual`/`policy`/`regulation`/`spec`/`guide`）字段存在且随切片下发，但**没有任何一处按它排序或加权**。

### P1-2a · 来源权威度分级（✅ 已完成 2026-10-06）

**改法**：定义权威度序（如 `regulation` > `policy` > `spec` > `manual` > `guide`），在冲突判定里使用：权威度**明显**不同时按高者作答并注明；同级或无法比较时才写冲突段。落点可以是 `KnowledgePrompt` 的规则 + `ConflictReporter` 的结构化字段（带上双方权威度，让前端卡片能显示「监管规范 vs 厂商说明书」）。

**关键约束**：分级只解决「能排序」的冲突，**不要**把排序升格成「自动判对」——权威度高不等于内容正确。

### P1-2b · 时效优先级落成规则（✅ 已完成 2026-10-06）

**改法**：文档已有 `version` 与 `updatedAt`。把「较新版本取代旧版本」从提示词里的一句话，升级为 `ConflictReporter` 里的**可执行判定**：同源同题、版本可比较 → 直接采用新版并记录；版本不可比较（不同文档体系）→ 保留冲突。

**验收证据来源（两条共用）**：构造同题异源样本（监管规范 vs 厂商说明书、新旧版本），断言裁决有据可查；输出里必须能看出「凭哪个字段裁的」。

**已知边界**：**没有冲突的持久化与追踪**——冲突每轮现算，同一条矛盾下次还要再发现一遍。持久化属独立任务，成本中等，暂列出。

## P1-4 · 记忆（对应第 2 条）

**现状覆盖**

| 建议里的分类 | 覆盖 | 实现 |
|--------------|------|------|
| 短期记忆 | ✅ | `ShortTermMemory`（sessionId 隔离、滑动窗口、可持久化） |
| 长期记忆 | ✅ | 画像槽位 + `EpisodicMemory`（userId 隔离、语义召回） |
| 实体记忆 | ✅ | `UserProfile` / `ProfileSlot` |
| **感知记忆** | ❌ | 无对应实现 |
| 滑动窗口压缩 | ✅ | `ContextBudget`（4000 token 上界，按最旧丢弃） |
| 摘要压缩 | ✅ | `SUMMARY` 类型 + `MemoryConsolidator` |
| **重要性过滤** | ❌ | `EpisodicMemory` 有偏好/事件分层淘汰，但那是**类型分层**不是**打分** |

### P1-4a · 重要性打分过滤（✅ 已完成 2026-10-06）

**改法**：`MemoryItem` 加重要性维度，`EpisodicMemory.pickEviction` 从「先淘汰事件、后淘汰偏好」升级为「同类型内按重要性 + 新鲜度打分淘汰」。打分口径要**确定、可测**（如显式标记 + 实体密度 + 是否被反复引用），不要用模型自由打分——那会让淘汰行为不可复现。

**验收证据来源**：同类型两条记忆（「用户是学生党」vs「用户问过衬衫尺码」）在容量压力下淘汰顺序符合预期。

### P1-4b · 记忆注入可观测字段（✅ 已完成 2026-10-06）

**现状**：`RetrievalOutcome` 已带出图谱事实（`graphChunkIds` / `graphCandidateInPool` / `expansions`），但**记忆注入没有对应的可观测字段**——无法断言「本轮记忆真的注入过」。

**改法**：把「本轮注入了哪些记忆条目（条数 + id + 类型）」带进 Agent 的本轮产出，与 `RetrievalOutcome` 同层。判据同上：下游推不出来的事实必须由上游显式带出来。

**验收证据来源**：断言本轮产出里有记忆注入事实；无记忆时字段为空而不是缺失。

### P1-4c · 感知记忆（✅ 已完成 2026-10-06）

**现状**：多模态输入（图片、上传文件）或「本次交互的即时观测」没有独立承载。

**改法**：先定义承载范围——本次交互里用户给了什么（上传的图片摘要、选中的商品、页面上下文），生命周期随会话。**不要**一上来就做多模态模型接入。若项目当前没有多模态输入入口，先做「本轮观测」的承载与注入，把多模态留作扩展点。

**验收证据来源**：感知内容在一轮内可见、跨轮不污染长期记忆。

## P2 · 可更好但不阻断

### P2-1 · 复杂任务分解评测集（对应第 3 条）

规划与 replan 环已用 LangGraph4j 显式编排，`critique` 做失败诊断（四分类）。缺的是证据：没有「多步复杂任务」评测集，无法回答「5 步以上的任务规划质量如何」。现有评测集中在检索与问答质量。

**改法**：设计 10~20 条多步任务（如「我要买 A，预算 X，对比 B，看有没有券，算上运费」），标注期望子任务集合，断言分解覆盖率与顺序合理性。

### P2-2 · 情节召回过取上限（对应第 2 条）

`EpisodicMemory.OVER_FETCH_FACTOR = 20`——向量库契约没有过滤参数，只能在应用层按 `userId` 筛，于是要先多取再筛。代码注释已写明这是已知上限。真正解法是给向量库加 filter expression（Milvus 支持），让过滤下推到存储层。

### P2-3 · 夹具与线上语料形态对齐（对应第 5 条）

夹具 90 篇短文档，线上 47 篇 / 408 片。「切片级融合 +11.7pp」是夹具数字，**线上没做过 chunk 级 vs 文档级 A/B**。改法：从线上语料抽一组多切片文档做 A/B，或把夹具扩成多切片形态。**这条不解决，P1-1 的数字就只是夹具数字，材料里必须如实标注。**

### P1-3b · 组合禁忌（方案 B：组合节点）

**为什么单跳表达不了、A 方案也不够**：`INTERACTS_WITH` 的语义是「A 与 B 之间有事」；
「两两拆开谁都没问题、三样一起才有事」这类结论，图上**一条单跳边都没有**可写。
在 Agent 侧把各自的单跳风险汇总（A 方案）只能回答「这几样各自有什么风险」——
面对这个问题时它没有任何输入可用。**缺的是结构，不是聚合策略。**

**做了什么（四处）**：

- `GraphRelation.COMBINED_WITH`（组合禁忌）+ `EntityKind.COMBINATION`（结构标记，不进抽取词表）
- 组合节点键 = 成员名排序拼接（`combo:维生素d|钙|铁剂`）。排序是必须的：「钙+铁」与「铁+钙」
  不排序会在图上分成两个节点，同一件事的条数各算一半——而这是静默的
- `TripleValidator.validateCombination`：成员 ≥ 2；**引文必须同时提到全部成员**；尾端须出自原文
- `KnowledgeGraphStore.combinationsOf`：判据是**成员被集合全覆盖**，不是「相交」

**最关键的一条判据**（也是本批最容易静默出错的地方）：
「引文必须覆盖全部成员」。文档里「铁剂与钙剂同服影响吸收」逐字存在、也确实提到两样东西，
但它**不能**支撑「铁剂+钙剂+维生素D 三样一起有事」——那句话里没有维生素 D。
少了这一条，模型只要找到一句提到部分成员的话，就能把一个更大的组合挂上去，
而图上看起来有完整出处。少报一条组合，远好过多报一条。

**第二个关键判断**：查询按「集合包含」而不是「相交」。按相交匹配等于把一条**条件边**
当成无条件边——用户只带了其中两样也会被告知「有组合风险」，他分开吃、以为规避了，
而真实风险与第三样有关。

**单测**：`TripleValidatorTest` 4 条组合用例 + `GraphServiceRecallTest` 3 条
（三样都问到→出现 / 只问到两样→不出现 / 键形状反例）。

**端到端（新加，已跑通）**：`verify-knowledge-ui` 第七段自己造一条 `COMBINED_WITH` 边、验完即删——
断言「组合禁忌」出现在关系图例、组合节点有独立类型图例、画布显示成员名而非 `combo:` 键、
右栏读作「组合禁忌」、点开出处是逐字引文。**这补上了下面那条「已知边界」的空缺**：
链路现在真的被跑过一次，只是跑在构造边上。脚本从 **50/50 → 56/56**（原六段全绿 + 第七段 5 项）。

所以**真实语料这条链路仍然没跑过**，`verify-knowledge-ui` 里跑通的是自造边（脚本自己 `MERGE` 一条、
验收完在 `finally` 里删掉，断言图谱规模时不会带上它）。抽取提示词能否稳定抽出组合，要等这类文档进库才知道。
