## P0：明确未完成，且是原建议的核心诉求

### P0-1 · 上架商品与上传说明书未打通（对应 #1）

**现状**

- 文档侧已自动：管理台保存文档 → 自动调 `POST /ai/admin/knowledge/reindex/{docNo}` → 向量库与图谱同时更新。这条链路完整。
- **商品与说明书在数据库层面没有任何引用关系。** 绑定发生在图谱构建期，由 `KnowledgeGraphBuilder.linkProducts` 用商品目录（`GET /internal/catalog`）做实体链接，对不上的三元组整条丢弃。

**差距**

1. **操作被拆成两处、且有顺序要求**：必须先上架商品、再上传说明书；反过来的话这次图谱构建会丢掉商品边，得上架后**再重建一次**才能补。
2. **商品编辑页没有「附加说明书」入口**，管理员无从得知该商品有哪些文档、也看不到「有没有接上」。
3. **链接失败是静默的**：说明书写了商品但链接不上时，只在服务端日志留一行丢弃计数，管理台看不到。

**验收证据来源**：管理端新增入口可点；上传后图谱里 `CONTAINS` 边出现（`GET /knowledge/graph/entity?name=spu<N>&depth=1`）；链接失败在管理台可见。

## P1：有明确缺口，收益可验证

### P1-1 · 语义档（对应 #5）—— ✅ 已收口（2026-10-06）

**现状**（生产配置：混合 + 重排 + 扩写，夹具 90 篇 / 120 条）

| 档位 | 改造前 | 本次改造前 | 现在 |
|------|--------|-----------|------|
| 字面 | 0.975 | 1.000 | **1.000** |
| 口语 | 0.700 | 0.975 | **1.000** |
| **语义** | 0.225 | 0.725 | **0.875** |
| 全量 | 0.633 | 0.900 | **0.883**（同批口径 0.867 → 0.883） |

**做了什么**：语义鸿沟档的失败根因**不是向量不够强**，而是「生活口语 → 文档主题名」这类映射
两个字面都不重合。原先角度改写的提示词只说「同义词、上位词、口语说法、专业术语」，
产出的是同义改写；改成明确要求**落到知识库会用来命名文档的主题词**（并给了
「太贵了→价格保护」「钱少了一部分→退款到账时间」这类示例）后，语义档 0.725 → **0.875**。
改动只有一处：`LlmQueryExpander` 的 angles 提示词 + 重采 120 条扩写夹具。

**已量过的两件事（都不是瓶颈）**：候选池扩大无增益（`RERANK_CANDIDATES` 3/5/8 → 0.700/0.675/0.675）；
重排对语义档 Hit Rate 贡献有限（+5pp，且有 ±1 条波动）。

**剩余差距**：语义档 0.875 与其余两档仍差 0.125；且**夹具与线上语料形态已脱节**——
夹具 90 篇短文档，线上 47 篇成篇文档 / 408 片，线上没做过 chunk 级 A/B（见 P2-3）。
**本轮所有数字都是夹具数字，材料里不得当作线上表现引用。**

**验收证据来源**：`RetrievalComparisonTest` 语义档 Hit@3；CI 门禁 `RetrievalQualityTest` 不退化；线上形态的抽查。

### P1-2 · 冲突只有呈现，没有决策（对应 #8）

**现状**

- `ConflictReporter` 把冲突抽成结构化字段供前端渲染卡片，**不替用户裁决**——这是刻意的（模型替用户选一条会流畅地讲出来，把「资料打架」伪装成「查证完毕」）。
- `KnowledgePrompt` 的冲突处理规则只裁一件事：**版本能分出先后的**，采用较新版本、不必写冲突段。

**差距**

1. **没有基于时间的实效判断**：文档有 `version` 与 `updatedAt`，但「谁更新」只用于提示词里的一句话，没有落成可执行的优先级决策。
2. **没有来源权威度分级**：`source` 字段（`manual` / `policy` / `regulation` / `spec` / `guide`）存在且会随切片下发，但**没有任何一处按它排序或加权**。等于「厂商说明书」与「监管规范」在冲突时权重相同。
3. **没有冲突的持久化与追踪**：冲突是每轮现算的，同一条矛盾下次还要再发现一遍，也没有「这条已裁定过」的记录。

**验收证据来源**：刻意构造的同题异源冲突样本，验证裁决有据可查且可追溯。

### P1-3 · 图谱侧的三个真实缺口（对应 #7）

溯源侧已强（`[n]` → 切片 → 原文高亮全链路可点），缺口在图谱本身：

1. **实体链接是子串匹配，没有别名表**。`GraphService.recall` 按名字做子串匹配，用户说「鱼油」而图上节点是「深海鱼油」「精制深海鱼油」时命中不稳定；「维生素 D」「VD」「胆钙化醇」在图上可能是三个节点。`EntityAliases` 存在，但覆盖面有限。
2. **`CAUTION_FOR` / `INTERACTS_WITH` 只支持单跳语义**，组合禁忌（「同时吃 A 和 B」才成立的风险）没有表达——风险写在边的 `effect` 上，而这正是设计选择（风险是组合导致的），但也意味着**三样东西两两都没事、三样一起有事**这类结论图上表达不出来。
3. **语义档失败的那类查询图谱也接不住**：图上没有的实体直接返回空，没有「最相近实体」的兜底。

**验收证据来源**：别名命中率、组合禁忌样本、图谱召回与文本召回的互补性统计。

### P1-4 · 记忆缺感知与重要性过滤（对应 #2）

**现状**

| 建议里的分类 | 覆盖情况 |
|--------------|----------|
| 短期记忆 | ✅ `ShortTermMemory`（`sessionId` 隔离、滑动窗口、可持久化） |
| 长期记忆 | ✅ 画像槽位 + `EpisodicMemory`（`userId` 隔离、语义召回） |
| 实体记忆 | ✅ 用户画像（`UserProfile` / `ProfileSlot`） |
| **感知记忆** | ❌ **无对应实现** |
| 滑动窗口压缩 | ✅ `ContextBudget`（4000 token 上界，按最旧丢弃） |
| 摘要压缩 | ✅ `SUMMARY` 类型 + `MemoryConsolidator` |
| **重要性过滤** | ❌ **无**（`EpisodicMemory` 有偏好/事件分层淘汰，但那是**类型分层**，不是按重要性打分） |

**差距**

1. **感知记忆**没有着落——多模态输入（图片、上传文件）或「本次交互的即时观测」没有独立承载。
2. **重要性过滤**缺失：现在只有「偏好不淘汰、事件 FIFO」的类型分层，以及 200 条上限。同样两条事件，「用户是学生党」与「用户问过衬衫尺码」权重相同，只有类型不同才被区别对待。
3. **「每一步都运行的闭环」没有校验**：建议要求确认每个环节真的执行。目前**没有一处断言「记忆注入 / 检索 / 图谱召回 / 护栏 本轮都跑过」**——图谱召回是否生效要靠 `RetrievalOutcome.graphKeys` 带出（做了），但记忆注入没有对应的可观测字段。

**验收证据来源**：记忆注入的可观测字段；重要性打分的往返测试；感知路径的端到端。

## P2：可以更好，但不是阻断项

### P2-1 · 复杂任务分解的深度未验证（对应 #3）

- 规划与 replan 环已用 LangGraph4j 显式编排，`critique` 做失败诊断（四分类：参数不当 / 工具选错 / 数据缺失 / 下游故障）。
- **缺的是证据**：没有「多步复杂任务」的评测集，无法回答「5 步以上的任务规划质量如何」。现有评测集中在检索与问答质量。

### P2-2 · 情节召回的过取上限（代码里已自注）

`EpisodicMemory.OVER_FETCH_FACTOR = 20`——向量库契约没有过滤参数，只能在应用层按 `userId` 筛，于是要先多取再筛。**代码注释里已写明这是已知上限**：记忆库足够大、某用户的相关条目全被挤出过取窗口时会漏召回。真正解法是给向量库加 filter expression（Milvus 支持）。

### P2-3 · 检索夹具与线上语料形态脱节（对应 #5）

夹具 90 篇短文档，线上 47 篇 / 408 片。「切片级融合 +11.7pp」是夹具数字，**线上没做过 chunk 级 vs 文档级 A/B**。

## 建议的推进顺序

1. **P0-1**（商品-说明书打通）：功能缺口清晰、成本小，且直接对应原建议第 1 条的完整形态。
