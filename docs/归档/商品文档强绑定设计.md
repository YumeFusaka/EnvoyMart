## 〇、总原则（用户 2026-10-06 拍板）

1. **商品 SPU 是实体本身，说明书是它的孪生文档**，二者地位对等、生命周期绑定。
2. **商品下架 → 说明书同步下架**，且 `MySQL / ES(BM25) / 向量库 / 知识图谱` 四处**全部同步**。
3. **说明书修改 → 四处同步更新**（这一条现状已实现，见 §2）。
4. **唯一的例外**：文档本身不是建立在某个商品实体上的（退货政策、监管规范、物流说明……），
   这类文档**不绑定商品**，独立存在。

## 一、现状：四格里有三格是通的

| 触发 | MySQL 文档 | 向量库切片 | BM25 切片 | 图谱边 |
|------|-----------|-----------|-----------|--------|
| 新建文档 | 写入 | 自动 | 自动 | 自动 |
| 编辑文档 | 更新 | 自动 | 自动 | 自动 |
| 停用文档 | `status=0` | 自动删 | 自动重建 | 自动清 |
| **商品下架** | **不动** | **不动** | **不动** | **不动**（下次全量重建才消失） |

### 1.1 已经跑通的那条链路（不需要新造轮子）

`save()` → `syncOne(docNo)` → `POST /ai/admin/knowledge/reindex/{docNo}` → `KnowledgeIndexer.rebuildOne`：

```
corpus.reload()                        拉全量语料（status=1 过滤）
target == null  -> 只删不写：
    vectorStore.deleteByDocId(docNo)   向量库删切片
    retriever.rebuild(chunks)          BM25 重建快照
    graphBuilder.rebuildOne(docNo, null)   空 triples 整体替换 = 清边
target != null  -> 删旧写新：
    vectorStore.deleteByDocId + indexBatch
    retriever.rebuild(all)
    graphBuilder.rebuildOne(docNo, target)
```

**关键结论：四处同步的机制已经完整存在。** 缺的不是「怎么下架一篇文档」，
而是「商品下架时，系统不知道该下架哪几篇文档」。

### 1.2 为什么不知道：对齐结果没有被持久化

`KnowledgeGraphBuilder.linkProducts` 在构建期把文档里的商品端对齐到目录，
但**对齐结果本身不落库**——抽完三元组、写完 Neo4j 就丢掉了。
系统里没有「KB-0018 这篇文档描述的是 SPU7」这条记录，因此：

- **下架商品**：无法反查受影响的文档与边
- **上架一个说明书早已存在的商品**：无法提示「有 N 篇文档在等着补链」，只能人工点全量重建
- **商品改名**：图谱节点名要等下次重建，而重建结果取决于模型本次的抽取输出（非确定性）

### 1.3 深层原因：两类文档混在一张表里

`knowledge_document` 表里**没有任何指向商品的字段**（已核实实体类）：
`docNo / title / source / scope / version / tags / status / content`。

也就是说，「鱼油软胶囊说明书」和「七天无理由退货政策」在**数据结构上完全同构**，
`source=manual` 只是一个**分类标签**，不是**归属关系**。
系统从结构上就分不清这两类，自然也做不到「第一类随商品生死」。

## 二、目标形态：两类文档

| | 商品文档 | 领域文档 |
|---|---|---|
| 例子 | 说明书、成分表、质检报告、用法用量 | 退货政策、监管规范、物流说明、支付规则 |
| 描述对象 | 某个具体 SPU | 平台规则，与具体商品无关 |
| 脱离商品 | 没有独立价值 | 完全成立 |
| 生命周期 | **随商品同生共死** | 独立 |
| 数量关系 | 与商品多对多（见 §3.1） | 不参与 |

判据是**这篇文档的意义是否依附于某个商品**，不是 `source` 的取值。
（`source=manual` 目前天然接近商品文档，但这是语料惯例，不是系统保证。）

## 三、方案

### 3.1 用多对多关联表，不用外键列

最直觉的做法是给 `knowledge_document` 加一列 `spu_id`。三个理由说明它不成立：

1. **粒度可能不是 SPU**：用法用量按粒数算时，说明书是 SKU 级的（90 粒装 / 180 粒装）。
2. **一篇文档可能被多个商品共用**：「Omega-3 类补充剂通用说明」可能同时描述 SPU7 / SPU12 / SPU19。
3. **说明书正文会提到别的商品**：「本品与华法林合用需谨慎」——华法林若也在售，它是**被提及的实体**，不是**归属的主体**。

因此关系表要带**角色**：

```sql
CREATE TABLE knowledge_doc_product (
  id          BIGINT PRIMARY KEY AUTO_INCREMENT,
  doc_no      VARCHAR(32)  NOT NULL,   -- 指向 knowledge_document.docNo
  spu_id      BIGINT       NOT NULL,   -- 指向 product_spu.id
  role        VARCHAR(16)  NOT NULL,   -- SUBJECT（本文档描述的主商品）/ MENTIONED（文中提到）
  matched_by  VARCHAR(16)  NOT NULL,   -- KEY（模型给了 SPU7）/ NAME（按商品名对齐）
  matched_at  DATETIME     NOT NULL,
  UNIQUE KEY uk_doc_spu_role (doc_no, spu_id, role),
  KEY idx_spu_role (spu_id, role)      -- 下架时反查用：spu_id -> 文档
);
```

**生命周期只看 `role=SUBJECT` 的行。** 只要某文档的 SUBJECT 商品全部下架，该文档就下架。
`MENTIONED` 行只用于溯源展示（「这条边提到的华法林是 SPU23」），不参与生命周期。

### 3.2 写入时机

在 `linkProducts` 对齐成功之后写这张表（同一次构建里），随图谱写入一起提交：

- `linkProducts` 返回前，收集 `(docNo, spuId, role, matchedBy)` 四元组
- 写入接口由 knowledge-service 提供（它是文档与图谱的共同持有方）
- **SUBJECT 如何判定，取决于 §4.1 的拍板结果**（人工指定 / 模型输出 / tags 声明）。
  本文件倾向「上传时人工指定」：语义最清晰，且能当场拦住「商品还没上架就上传说明书」这个顺序问题。
  在拍板之前，下面的 §3.3–§3.5 都建立在「SUBJECT 是确定的」这个前提上，与判定方式无关。

### 3.3 商品下架时做什么

`ProductAdminServiceImpl.changeStatus` 目前只有 `derivedRefresh.afterCommit(spuId)`。新增一步：

```
下架 SPU7
  -> 查 knowledge_doc_product WHERE spu_id=7 AND role=SUBJECT
  -> 对每篇 docNo：
       PUT /knowledge/admin/documents/{docNo}/status?status=0     （事实源先改）
       POST /ai/admin/knowledge/reindex/{docNo}                   （复用现成的四处同步）
```

**注意：停用的是文档，不是删除。** 删了会让「已发出的引用点开是 404」；
停用则退出检索但保留可回溯——这条口径与现有 `toggleStatus` 完全一致。

### 3.4 反向：商品上架时

上架时反查 `role=SUBJECT AND status=0` 的文档，若存在则提示/自动恢复：

- 最小做法：**提示运营**「有 N 篇文档关联了该商品，是否一并启用并重建」
- 激进做法：自动启用 + 单篇重建
- **不建议**自动全量重建（七十几秒、十几次模型调用）

### 3.5 商品改名时

图谱节点键是 `SPU{id}`（不随名字变），但**节点 label 是商品名**，由目录覆盖。
改名后图谱上的 label 会陈旧到下次重建。若要即时，可在改名时对关联文档跑一次单篇 `rebuildOne`。
**优先级最低**——label 错了不影响检索命中，只影响展示。

## 四、与现有设计的冲突点（需要拍板）

1. **`role=SUBJECT` 谁来判定？**
   - 选项 A：模型在抽取时输出（提示词加一个字段，如 `subject` 布尔）——简单，但依赖模型判断
   - 选项 B：从文档的 `tags`/`source` 里明确指定——确定，但要运营填
   - 选项 C：文档只允许关联**一个** SUBJECT，由上传时在管理端下拉选择商品
   - **倾向 C**：语义最清晰（「这篇文档讲的是哪个商品」是一次人工声明，不该让模型猜），
     且顺带解决了「上架顺序」问题——上传时选不到商品就说明它还没上架，当场就能拦。

2. **一篇说明书对应多个 SKU 怎么办？**
   - 现状表结构按 SPU 记。若确定有 SKU 级说明书，需要把关联表升成 `sku_id` 维度。
   - **待定**：当前语料里是否真有 SKU 级文档？没有就先按 SPU，留扩展位。

3. **停用是级联还是标记？**
   - 商品下架时把关联文档 `status=0`，商品重新上架时**是否自动恢复**？
   - 若自动恢复，运营手动停用过的文档会被误恢复 → 需要区分「因商品下架而停用」与「手动停用」。
   - **倾向**：`knowledge_document` 增加 `disabled_by` 字段（`MANUAL` / `PRODUCT_OFF`），
     只恢复 `PRODUCT_OFF` 的那些。

4. **历史数据怎么办？**
   - 加表之后，现存 47 篇文档的关联关系需要**回填**——只能靠一次全量重建时顺便写入。
   - 回填不完整时，「下架商品」会漏掉一些文档。需要一个**孤儿检查**：
     图谱上存在但关联表里没有的边，列出来供人工核对。

5. **领域文档（退货政策等）怎样保证不被误绑？**
   - 若不选商品就是领域文档，那「忘记选商品」和「故意不选」无法区分。
   - **倾向**：上传时必选一个类型（商品文档 / 领域文档），选商品文档才要求指定商品。

## 五、不在本方案范围内

- **不做全文检索的强过滤**：向量库/BM25 召回时按「关联商品是否在售」过滤，属于检索链路改动，
  与 `评测页真实链路改造.md` 的第 3 条总原则（本阶段只做展示、不调检索）冲突，留到下阶段。
- **不改图谱的查询语义**：`InteractionTool` 的消费侧不动。
- **不引入外键约束**：跨服务（product / knowledge / ai 三个库）无法建数据库级外键，
  关联表是**应用级**的强约束，一致性由三个触发点（下架 / 上架 / 改文档）保证。

## 六、验收标准（草案，待商定后细化为可执行证据）

| # | 验收标准 | 证据来源 |
|---|----------|----------|
| 1 | 上传商品文档时能指定 SUBJECT 商品；领域文档不需指定 | 管理端页面操作 + `knowledge_doc_product` 落库 |
| 2 | 下架 SPU7 后，其 SUBJECT 文档 `status=0` | 接口返回 + 表查询 |
| 3 | 上一条执行后，该文档切片从向量库与 BM25 消失 | 检索该文档独有词，命中 0 |
| 4 | 同上，图谱上该文档贡献的边被清除 | Neo4j 查询该 docNo 的边数为 0 |
| 5 | 重新上架 SPU7 后能恢复（或明确提示） | 页面提示 + 文档 status 回到 1 |
| 6 | 领域文档不受任何商品下架影响 | 下架后仍可检索到 |
| 7 | 手动停用的文档不被下架-恢复循环误恢复 | 下架再上架，该文档仍为 `status=0` |
| 8 | 无关联表记录的历史文档有孤儿检查可发现 | 检查接口输出清单 |
