## P0-1 · 下单已成功却报「失败」

### 现象

Agent 结算时执行 `cart_checkout(receiverCity=上海市, receiverDistrict=浦东新区, ...)`，
返回：「订单服务连不上（RetryableException）。请告知用户稍后再试」。

### 实测证据

**ai-service 侧**（`logs/logs-local/ai-service.log`）：

```
22:59:29.871  [Agent] chat userId=u1001 approvalToken=已携带
22:59:35.059  WARN [下游失败] 订单服务 调用异常（RetryableException）
              feign.RetryableException: Read timed out executing POST http://127.0.0.1:9003/orders/checkout
              Caused by: java.net.SocketTimeoutException: Read timed out
22:59:35.124  [工具失败] 下单 业务码=-1 瞬时=true：订单服务连不上（RetryableException）
              [Tool] cart_checkout success=false latencyMs=5248
```

**order-service 侧**（同一 requestId `2c2ebf3861b3413e`）：

```
22:59:29.984  Begin new global transaction [172.18.0.12:8091:10891731516...]
22:59:32.566  Load compatible class io.seata.rm.datasource.exec.InsertExecutor   ← 2.6 秒后
22:59:34.895  用户 u1001 下单成功，订单号 YS202610062259324609                  ← 又 2.3 秒
22:59:34.949  [MQ] 订单创建事件已登记待发布
22:59:35.025  Load [org.apache.seata.rm.datasource.undo.parser.Protostuf...]
22:59:35.180  [HTTP] POST /orders/checkout -> 200 5292ms                        ← 实际成功
22:59:35.487  [MQ.Consumer] 收到订单创建事件
```

### 根因（两层）

**第一层：超时值选错**。`ai-service/application.yml` 的 Feign 默认 `read-timeout: 5000`，
而这个超时按注释是「按用户等一个页面定的」（为 knowledge-service 放宽到 30 秒时写的理由）。
下单是**写操作**，它的耗时不受调用方控制（Seata 全局事务 + 库存分支 + MQ 登记），
不该用「页面等待」这个标准去卡。

**第二层（真正的问题）：超时后没有核实实际结果**。
`Downstream.mutate` 把超时归类为「瞬时失败」，返回给模型的是「稍后再试」——
但订单**已经创建成功**。这是最危险的一类不一致：

- 用户按提示再点一次 → **两笔订单、两份库存占用**
- 用户以为没下单 → 实际有笔订单躺在待支付里直到超时关闭
- 「稍后再试」在写操作上不是一个安全建议，因为**第一次尝试可能已经成功**

**为什么 5292ms 这么慢**：order-service 日志显示时间主要花在 **Seata 的首次类加载**
（`InsertExecutor`、`Protostuf...`、`FuryUndoLog...` 都是首次执行时懒加载）。
这是**首次调用冷启动**开销，第二次下单会显著变快——但它不该由调用方来容忍。

### 影响

**这是本清单里最严重的一条。** 它不产生「少一条关系」这种静默缺失，
它产生**真实的资金与库存副作用**，而用户被告知「失败了」。

### 修法（三选一或组合）

**A. 给写操作单独放宽超时**（最小改动）
```yaml
openfeign:
  client:
    config:
      default: { connect-timeout: 2000, read-timeout: 5000 }
      order-service: { connect-timeout: 2000, read-timeout: 30000 }   # 下单是写操作
      knowledge-service: { ..., read-timeout: 30000 }                 # 已有
```
理由与 knowledge-service 那段注释完全同构：「这个超时不会保护任何东西，只会制造一条不存在的故障记录」。

**B. 幂等键 + 超时后查证**（治本）
`cart_checkout` 带一个幂等键（`requestId` 或 `sessionId+回合`），超时后用该键查询订单是否已创建，
据此区分「真失败」与「已成功但没等到响应」。需要 order-service 侧支持幂等查询。

**C. 缩短 order-service 的下单耗时**
预热 Seata 的类加载（启动时主动触发一次序列化器加载），把首次 2~3 秒的冷启动挪到启动期。
这能减少超时概率，但**不能替代 A/B**——耗时总有长尾。

### 建议

**A + C 先做（成本低、立刻消除大部分超时），B 记入待办**（需要跨服务改动，价值最高但要设计幂等键）。
无论做哪个，**「超时」都不该被翻译成「失败」**——这个语义修正本身就该做，
当前 `Downstream` 把超时归为「瞬时失败」并建议「稍后再试」，对写操作是误导。

### 验收标准（草案）

| # | 标准 | 证据来源 |
|---|------|----------|
| 1 | 正常下单不再触发 read timeout | order-service 日志 `POST /orders/checkout -> 200 <Nms`，N 应小于超时值 |
| 2 | 超时后能区分「已成功」与「真失败」 | 构造超时场景，验证不会重复下单 |
| 3 | 重复确认不会产生两笔订单 | 连续两次确认，订单表只多一行 |

## P0-2 · 商品覆盖不完整（13 个不在图谱、3 个无说明书）

### 现象

用户实测发现「有些商品没有对应的说明书，在知识图谱上没有这个实体」。

### 实测证据（2026-10-06 现场查询）

```
商品总数（GET /products/internal/catalog）  = 37
知识库文档总数（GET /knowledge/documents）   = 47，其中 source=manual 35 篇
图谱商品节点数（Neo4j name 以 spu 开头）     = 24
图谱规模：163 实体 / 261 关系
  其中 CONTAINS=41、INTERACTS_WITH=106、CAUTION_FOR=107、PROVIDES=7
```

**24 / 37 —— 13 个商品不在图谱上**：

| SPU | 商品名 | 有说明书？ |
|-----|--------|-----------|
| SPU25 | 孕妇钙片 | 有（KB-0033） |
| SPU10 | 碳酸钙 D3 咀嚼片 | 有（KB-0027） |
| SPU21 | 锌硒宝片 | 有（KB-0039） |
| SPU12 | 孕期复合营养包 | 有（KB-0029） |
| SPU11 | 柠檬酸钙胶囊 | 有（KB-0028） |
| SPU9 | 维生素 K2 软胶囊 | 有（KB-0026） |
| SPU28 | 维生素 B 族复合片 | 有（KB-0036） |
| SPU29 | 维生素 C 咀嚼片 | 有（KB-0037） |
| SPU31 | 锌硒宝片 | 有（KB-0039） |
| SPU32 | 镁维 B6 缓释片 | 有（KB-0040） |
| SPU33 | 深海鱼油胶丸（高纯度） | 有（KB-0041） |
| SPU35 | 维生素 AD 滴剂 | 有（KB-0043） |
| SPU36 | 儿童铁锌口服液 | 有（KB-0044） |

**3 个商品完全没有说明书**：

| SPU | 商品名 |
|-----|--------|
| SPU5 | 益生菌粉 |
| SPU16 | 褪黑素缓释片 |
| SPU17 | γ-氨基丁酸软糖 |

**反向缺口**：`KB-0047 氨糖维 D 钙片（中老年）` 有文档，但商品目录里没有对应 SPU。

### 根因

**注意这 13 个里大部分「有说明书」**——说明问题不只是「缺文档」，更可能是**实体链接失败**。
`linkProducts` 要求模型输出与目录能对上：

- 模型用商品名输出时，经 `normalize()` 后按名字匹配（去空白 + 转小写，**不做同义词归一**）
- 匹配失败 → **整条三元组被丢弃**（设计如此，避免孤儿节点）

可疑点（需进一步验证）：
1. 商品名里的**全角/半角括号**差异（`深海鱼油胶丸（高纯度）` 的括号）
2. 文档标题含**多个商品**（如 KB-0018「叶黄素酯软胶囊与越橘叶黄素片」），
   模型可能只标了其中一个，另一个的边没建
3. 文档正文用「本品」指代时，模型可能没识别出对应哪个商品
4. **图谱是某次构建的快照**——这些文档可能是**后加进语料的**，加完没有重建过

### 影响

直接违背项目「强检索、强溯源」的核心目标：
商品没有图谱节点 → 用户问它的成分/相互作用时**检索不到依据** → 
Agent 要么说「未收录」（假阴性），要么用通用文档拼接出**没有商品级依据**的回答。

### 修法

**分两步，顺序不能反：**

**第一步（数据）**：补齐 3 篇缺失说明书（SPU5/16/17），并核对 KB-0047 该对应哪个商品。

**第二步（机制）**：
- 全量重建图谱，观察 13 个缺失里有多少能自动补上
- 补不上的，逐条排查是「名字对不上」还是「模型没抽」
- **新增一个覆盖度检查接口**：列出「有商品但图谱无节点」的清单，把这类问题变成**可发现的**
  而不是靠人肉比对（现在的发现方式就是人肉，这本身就是问题）

**与 `docs/商品文档强绑定设计.md` 的关系**：那份文档提出的 `knowledge_doc_product` 关联表，
正是这个覆盖度检查的**数据基础**——有了它，「SPU10 有没有文档、文档有没有进图谱」是一次查询就能回答的。

### 验收标准（草案）

| # | 标准 | 证据来源 |
|---|------|----------|
| 1 | 37 个商品全部有 `source=manual` 的说明书 | 文档列表与 catalog 逐一比对 |
| 2 | 37 个商品全部在图谱上有节点 | Neo4j 查询商品节点数 = 37 |
| 3 | 覆盖度检查接口能列出缺口 | 接口返回空清单 |
| 4 | KB-0047 有明确归属 | 人工确认并在文档清单里登记 |

## P0-3 · 推荐了图谱中没有的商品

### 现象

alice 账号会话「我最近感觉脚酸腿软，可能是什么原因」，Agent 推荐了
**「碳酸钙 D3 咀嚼片（元气元素）」**，并给出「钙会影响四环素类、喹诺酮类抗生素和双膦酸盐的吸收，需错开两小时以上」。

### 实测证据

**`碳酸钙 D3 咀嚼片` = `SPU10`，它正好在 P0-2 的 13 个缺失清单里。**
也就是说：**Agent 推荐了一个图谱上没有节点的商品**。

### 根因

那句话的出处**不是这个商品的知识图谱依据**（它图上没节点），而是检索到了通用文档
（如 `KB-0010 膳食补充剂摄入上限与常见药物相互作用`），然后与商品信息拼接。

也就是说：**商品推荐走的是 `product_search`（ES 商品检索），而依据走的是 RAG**，
两条路各自独立，**没有任何机制要求「被推荐的商品必须有可溯源的依据」**。

### 影响

这是「0 幻觉」目标下最不能接受的一种：**推荐的商品本身没有依据，但回答看起来有依据**
（因为它确实引用了某篇文档，只是那篇文档不支撑这个商品的结论）。

### 修法

**先修 P0-2（补齐覆盖）**，这是治本。

在这之上，可以考虑一条**软约束**：
`product_search` 返回的结果里带上「该商品在图谱上的关系数 / 是否有说明书」，
为 0 的商品在推荐时**降权或标注「暂无详细资料」**——
把「这个商品没有依据」这件事**显式化**，而不是让它隐含在回答里。

> ⚠️ 这条软约束涉及推荐策略，属于产品决策，需要拍板后再做。

### 验收标准（草案）

| # | 标准 | 证据来源 |
|---|------|----------|
| 1 | 推荐的商品都有图谱节点或说明书 | 抽查会话，商品与依据一一对应 |
| 2 | 无依据商品不被推荐，或被显式标注 | 构造用例验证 |

## P1-4 · 所有回答无条件走 RAG

### 现象

「所有的回答，无论我是不是问商品问资料，他都要 rag，然后返回文档，哪怕只是正常聊天。」

### 实测证据

`agent-core/.../core/Agent.java:345`：

```java
// 2. RAG 检索 + 长期记忆召回 → system prompt
//    检索用改写句（有历史时），回答侧仍用用户原话——分工的理由见 QueryRewriter
RetrievalOutcome retrieval = ragEngine.retrieveWithOutcome(retrievalQuery, config.getRagTopK());
```

**这行没有任何条件判断**，位于 `doChat` 的主路径上，每次对话必经。

链路开销（每次对话都付）：query 改写（模型调用）→ 扩写含 HyDE（模型调用）→ 
向量检索 → BM25 → 图谱检索 → RRF → rerank（模型调用）。

### 旁证

`KnowledgeSearchTool` 的 description 里有一句：

> 「注意：入口已自动检索过一次用户原话，不要用它重复查询同一个问题。」

**这句话的存在本身就是证据**——它说明入口检索是无条件的，以至于工具侧要靠提示词去避免重复。

### 根因

设计上把「检索」当成了每一轮对话的**固定前置**，而不是**按需动作**。
在「强检索」的目标下这个选择是可理解的（宁可多查不漏查），但：

- 闲聊（「你好」「谢谢」）跑完整检索是纯浪费
- 查订单 / 查物流 / 查购物车 / 加购 这些**业务操作类**请求不需要知识库
- 每次检索含 2~3 次**计费模型调用**（改写 + HyDE + rerank），成本直接翻倍

### 影响

- **成本**：每一轮对话都付检索的模型调用费
- **延迟**：检索是同步前置，用户等回答前先等一次检索
- **体验**：闲聊时 AI 返回一堆文档依据，观感错位（用户原话「返回文档」）

### 修法

**加一层意图分流**：先判定本轮属于哪一类，再决定要不要检索。

| 类别 | 例子 | 是否检索 |
|------|------|----------|
| 闲聊 / 元对话 | 「你好」「你是谁」 | 否 |
| 业务操作 | 「加入购物车」「下单」「查订单」 | 否 |
| 商品咨询 | 「这个能不能和钙片一起吃」 | **是** |
| 规则咨询 | 「七天无理由怎么算」 | **是** |
| 混合 | 「脚酸腿软吃什么」（既要推荐又要依据） | **是** |

实现上有两条路：

- **A. 规则 + 关键词**（便宜、确定）：命中业务操作动词/闲聊句式就跳过。风险是覆盖不全
- **B. 模型判定**（多一次调用）：让规划器输出 `needRetrieval` 布尔字段。
  可与**现有的规划调用合并**（`LangChain4jLLMProvider` 已有任务规划器），不额外增加调用次数

**建议 B**，且必须与现有规划步骤合并——否则「为省一次检索而多一次模型调用」是负收益。

**注意**：`KnowledgeSearchTool` 必须保留。分流只是省掉**入口那一次**，
推理中途模型仍可主动再检索（那是它的正当能力）。

### 验收标准（草案）

| # | 标准 | 证据来源 |
|---|------|----------|
| 1 | 闲聊不触发检索 | 日志中该轮无 `retrieveWithOutcome` 记录 |
| 2 | 业务操作类不触发检索 | 同上（「加入购物车」用例） |
| 3 | 商品/规则咨询仍会检索 | 同上，且命中数与改造前一致 |
| 4 | 单轮 token 与费用下降 | 用量统计对比 |

## P1-5 · 确认弹窗展示原始代码而非商品名

### 现象

「我让 agent 帮我加入购物车，他弹出来的是代码里面还是 SPU 编号，而不是产品名。」
实测看到的形如：

```
cart_checkout(receiverCity=上海市, receiverDetail=张江路100号1号楼101室, 
receiverDistrict=浦东新区, receiverName=Alice, receiverPhone=13800138001, 
receiverProvince=上海市)
```

### 实测证据

`frontend/src/components/ai/PendingApprovalCard.vue`：

```vue
<li v-for="action in actions" :key="action">{{ actionLabel(action) }}</li>
```
```css
.approval__list li {
  font-family: var(--ys-font-mono);   /* 等宽字体 */
  word-break: break-all;
}
```

`frontend/src/utils/tools.ts` 的 `TOOL_LABELS` **只登记了 5 个工具**：

```ts
const TOOL_LABELS: Record<string, string> = {
  product_search: '商品检索',
  order_query: '订单查询',
  logistics_query: '物流查询',

  interaction_check: '成分相互作用核查',
}
```

而实际工具共 **11 个**，未登记的 4 个会**原样显示英文**：

| 未登记 | 后果 |
|--------|------|
| `cart_checkout` | 显示 `cart_checkout(...)` |
| `cart_add` | 显示 `cart_add(skuId=123, quantity=2)` ← **这就是「SPU/SKU 编号」的来源** |
| `address_list` | 显示 `address_list()` |
| `after_sale_apply` | 显示 `after_sale_apply(...)` |

### 根因（三个叠加）

1. **工具名未登记**：`TOOL_LABELS` 漏了 4 个工具，显示英文原名
2. **参数值是原始形式**：`receiverCity=上海市` 这种 `字段=值` 拼接，用户要自己翻译
3. **等宽字体**：强化了「这是代码」的观感

### 需要澄清的一点（重要的设计判断）

`actionLabel` 的注释写得很明确，而且**这个判断是对的**：

> 「**只翻译括号前的工具名，参数原样保留。**参数是用户判断『要动的是哪一个对象』的唯一依据，
> 翻译、截断或省略它都是在替用户改授权对象——一个写着『订单取消』却不说是哪一单的卡片，
> 点了确认等于盲签。」

**所以不能简单地把参数藏起来或翻译掉。**正确的做法是**结构化地展示参数**，
即「保留全部信息，但用人话排版」：

```
当前：cart_checkout(receiverCity=上海市, receiverDetail=张江路100号1号楼101室, ...)
目标：
  【下单结算】
  收货人：Alice  13800138001
  收货地址：上海市 浦东新区 张江路100号1号楼101室
```

信息量不减，但可读性完全不同。

### 修法

1. **补齐 `TOOL_LABELS`**（立即，覆盖全部 11 个工具）
2. **加一层参数渲染**：按工具名走各自的展示模板（下单渲染成收货信息卡片、
   加购渲染成「商品名 × 数量」——注意这里需要把 skuId 解析成商品名，可能需要一次查询）
3. **保留「原始参数」的兜底**：未知工具或渲染失败时，回退到当前的原始串显示，**绝不隐藏**

> 关于第 2 点里的「skuId → 商品名」：`cart_add` 的**执行结果**已经返回了 `item.getName()`
> （见 `AddToCartTool`），说明映射是可行的。但**确认弹窗在执行之前**，
> 所以需要在弹出确认时先查一次 SKU 对应的商品名。这是一个额外的下游调用，需要评估。

### 验收标准（草案）

| # | 标准 | 证据来源 |
|---|------|----------|
| 1 | 全部 11 个工具在卡片上显示中文名 | 逐个触发确认卡片 |
| 2 | 下单卡片显示结构化收货信息 | 截图检查 |
| 3 | 加购卡片显示商品名而非 skuId | 截图检查 |
| 4 | 未知工具仍回退到原始串（不隐藏） | 构造用例 |

## P1-6 · Agent 无法查购物车

### 现象

「我让他告诉我我的购物车里有什么，他说没有查阅购物车的功能。」

### 实测证据

**Agent 的 11 个工具**（`ai-service/.../tool/`）：

```
product_search   商品检索
order_query      订单查询
logistics_query  物流查询
interaction_check 成分相互作用核查
address_list     地址簿查询
cart_add         加入购物车
cart_checkout    结算下单
after_sale_apply 售后申请
order_cancel     订单取消
knowledge_search 知识库再检索
（+ MCP 侧若干）
```

**没有 cart 查询工具。**

**但后端接口存在**（`order-service/.../controller/CartController.java:42`）：

```java
@GetMapping
public Result<List<CartItem>> list(...) {
    return Result.success(cartService.list(userId));
}
```

### 根因

**接口装得下，只是没做成工具。**这与项目历史上那个「商品检索接口只有关键词+条数、
装不下多条件」是同一类问题的**镜像**——那次是「接口装不下」，这次是「有接口没工具」。

Agent 的能力边界 = 工具清单。用户说「我购物车里有什么」时，
模型手上没有任何工具能回答，只能如实说「没有这个功能」（**这个回答本身是诚实的，是好事**）。

### 影响

一个真实的、高频的用户意图无法完成。而且它**紧挨着 `cart_add` 与 `cart_checkout`**：
用户加购之后想确认一下，这是最自然的下一步。

### 修法

新增 `cart_query` 工具（只读，**不需要确认**）：

- 复用 `order-service` 的 `GET /cart`
- 返回商品名、规格、数量、小计、是否勾选
- 描述里写明「用户问『购物车里有什么』『我加了什么』时使用」

**顺带值得考虑的**：既然 `GET /cart` 已经有了，`cart_add` 之后用户常见的下一步是
「都买了吧」→ 这时 Agent 需要知道购物车里有什么才能确认金额，
所以 `cart_query` 也是**下单前置校验**的自然组成。

### 验收标准（草案）

| # | 标准 | 证据来源 |
|---|------|----------|
| 1 | 问「购物车里有什么」能返回清单 | 会话实测 |
| 2 | 空购物车有明确的空态说明 | 清空后实测 |
| 3 | 只读工具不触发确认卡片 | 实测无确认弹窗 |

## P1-7 · ~~`GET /products` 分页参数异常~~ → **经复核：误判，无此 bug**

### 结论（2026-10-06 二次复核）

**分页行为完全正确。** 首次排查时得出的「17 条」是一个**测量错误**，不是产品缺陷。

### 二次复核的实测（同一环境，逐条精确复现）

```
GET /products?page=0&size=100  -> 37 条 / total=37 / page 回显 0   ✓ 第 0 页，取全部
GET /products?page=1&size=100  ->  0 条 / total=37 / page 回显 1   ✓ 第 1 页，确实没有数据了
GET /products?page=1&size=50   ->  0 条 / total=37 / page 回显 1   ✓ 同上
GET /products?page=0&size=50   -> 37 条 / total=37 / page 回显 0   ✓ 37 < 100 上限，全返回
GET /products?page=0&size=10   -> 10 条，ids 前 5 = 20,3,5,26,1
GET /products?page=1&size=10   -> 10 条，ids 前 5 = 24,10,14,18,21   ← 与第 0 页不重复
GET /products?page=2&size=10   -> 10 条，ids 前 5 = 4,22,11,6,9      ← 逐页推进正确
```

`ProductQuery` 的语义是**对外页码从 0 开始**，代码注释里写得很清楚，而且专门警告过一个人为陷阱：

> 「**不要拿它直接构造 MyBatis-Plus 的 `Page`**：那边 `current` 从 1 开始，
> 且 `offset()` 对 `current <= 1` 一律返回 0，于是第 0 页与第 1 页查出重复数据。」

代码正确避开了这个陷阱（`zeroBasedPage()` / `mpCurrent()` 两个访问器分开），实测也证明避开了。

### 误判是怎么发生的（教训，值得留档）

首次排查时，多条 `curl` 命令的**输出被写进同一个临时文件**（当时正被 `/tmp` 路径问题困扰，
用的是共享文件名），于是后来读到的是一份**混合了两次请求的脏数据**，
`records` 既不是第 1 页也不是第 0 页，看起来像「分页丢数据」。

**这与项目已知的那类问题同构**：`改造进度.md` 的教训段落里有一条——
「**验收脚本自己会成为污染源与假红灯**」（脚本搜编造词把测试垃圾顶上热搜榜）。
这次是排查脚本自己制造了一份假数据。

**判据**：当一次测量的结果「看起来像 bug」时，先确认**这次测量本身干净吗**——
尤其当多个命令共用输出文件、或并发写同一路径时。本次两个异常值（17 条 / 0 条）
恰好都能用「文件被覆盖」解释，而「分页实现有 bug」解释不了为什么 page=0 是对的。

### 对总表的影响

本项从 `待办总表.md` 的 §B 中**移除**（不再作为待办），并在该表附上本结论。

## P2-8 · 图谱节点名是小写 `spu7`

### 现象

用户此前反馈「鱼油软胶囊的中心实体叫 spu7」。

### 实测证据

Neo4j 查询结果（本次现场）：

```
MATCH (n:Entity) WHERE toLower(n.name) STARTS WITH 'spu' RETURN n.name
-> spu1, spu2, spu3, spu4, spu5, spu6, spu7, spu8, ... （共 24 个）
```

**全部 24 个商品节点的 `name` 都是小写的 `spuN` 形式**，而不是商品名。

### 根因

`KnowledgeGraphBuilder.key(Long spuId)` 生成的是 `"SPU" + spuId`，
但写入 Neo4j 前经过 `EntityNames.normalize()`（**去空白 + 转小写**），
于是 `SPU7` → `spu7`。

设计上这是**刻意的**（注释：「用 SPU 编号而不是商品名：商品会改名、会重名，而编号不会」），
`name` 是**节点键**，承担的是「稳定标识」职责。

**问题在于展示**：图谱可视化时把 `name` 当成了显示名。

而商品名**其实在目录里**（`fetchCatalog()` 已经拉到了 `ProductSummary.getName()`），
`linkProducts` 甚至已经用目录名覆盖了 `headLabel`/`tailLabel` —— 
**信息是有的，只是展示层没取。**

### 修法

展示层（前端图谱页 + 中心实体下拉）取 `label` 字段而非 `name`；
或在图谱写入时把商品名一并存到节点属性上供展示。

**注意**：不要改 `name`（那是节点键，改了会**分裂节点**，见 `EntityNames` 的类注释）。

### 验收标准（草案）

| # | 标准 | 证据来源 |
|---|------|----------|
| 1 | 图谱页与下拉显示商品名而非 spu7 | 截图检查 |
| 2 | 节点键仍为规范化后的 spu7（未被改动） | Neo4j 查询 |
