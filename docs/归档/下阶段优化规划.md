## 〇、阶段总原则（用户 2026-10-06 拍板，优先级最高）

> 商品、RAG、知识图谱**能检索到相关内容，agent 就要结合用户提问做评估**；
> 拿不定主意时**不急着回答，先和用户对话几次把场景问清楚**，再评估、再给优质回答；
> **只有在 RAG 与图谱里都找不到与用户需求相关的商品时，才跟用户说没有**。
> 也就是说——**不是拒答，而是「没有就是没有」**。

这条原则管三层，冲突时以它为准：

1. **能动性**：能查到的就必须评估并给出推荐与说明，不得退化成泛泛的免责声明
2. **澄清优先**：信息不足时先问清楚再检索，不拿模糊输入硬查、拿不相关结果凑答案
3. **诚实边界**：说「没有」的唯一条件是两条路都查不到；且要说「查不到」而不是「不能吃」

### 补充判据：质量是三级传递的（用户 2026-10-06 追加）

> **回答质量依赖检索质量，检索质量依赖存储质量。存储质量也要把关。**

> 如果数据库/向量库/知识图谱里**存在相符的商品**，但它**对应的资料不全面**，
> 导致没能到达「可以推荐给用户」的阈值，**就算是有问题了**。

这条把前面那三条原则的**责任往下压了一层**：agent 说「查不到」之前，
必须先排除「其实是资料缺失」这种可能。否则「诚实边界」会变成一个**免责装置**——
系统永远可以躲在「库里没有」后面，而真相是**库里本该有**。

#### 三级传递链（每一级的缺口表现都是同一个「查不到」）

| 环节 | 缺什么 | 用户看到的现象 | 谁来兜 |
|------|--------|---------------|--------|
| **存储** | 商品没有说明书 / 说明书没进向量库 / 三元组没进图谱 | 查不到 | 管理台上架流程 + 覆盖率把关 |
| **检索** | 有资料但召回不到（语义鸿沟、实体链接失败、过取上限） | 查不到 | 检索层（P0-A / P2-2 / 别名片） |
| **回答** | 检索到了但被闸门剔除 / 阈值不够 | 查不到 | 校验层（P0-A） |

**判据**：一个商品**只要有相符的商品存在**，就应当有可推荐的依据；
「有商品但没资料」是一个**应当被发现的缺陷**，不是一个可以接受的终态。

#### 落成两条可执行要求

1. **商品必须带说明书**：上架流程要能保证/提示每个在售商品都有对应说明书入库
   （商品编辑页已有「说明书与知识依据」面板，P0-1 已做——本阶段把它从「可见」升级为「可把关」：
   在售但无说明书的商品要能被列出来）
2. **覆盖率要可观测**：有一个能回答「多少在售商品是有资料的、多少没有」的读数，
   而不是靠人工抽查。缺的那部分就是**存储质量的欠账**，要能被看见。

## 二、新增需求：Agent 的真实使用形态（第 2 项的展开）

用户的描述（**这是本阶段最重要的一段需求**，逐字保留）：

> 一个普通用户他并不知道 agent 到底是什么原理，他只知道遇到问题就问 agent，
> 甚至不知道开新会话，可能就在一个会话里问各种各样的事情，一会问商品推荐，
> 一会要查订单要退货，一会要查一些药和营养素的成分以及能不能在一起吃，
> 可能还会问得了什么病能不能吃什么。

**这否定了「一次一问、单意图」的设计前提。**当前的意图路由是按**单轮**判断的，
而真实场景是**同一会话内意图来回切换**。需要的能力：

1. **跨轮意图切换**：上一轮在聊订单、这一轮问营养素，上下文不能串味（`core_intent` 要跟得上变化）
2. **多轮澄清**：用户说「最近肠道不好应该吃什么」时，**不急着出结果**，先问清（不通畅/腹泻/腹胀是三种完全不同的情况），拿到明确信息再过滤
3. **会话隔离不靠用户自觉**：用户不知道要开新会话，系统得自己处理「一锅粥」的上下文

**期望的完整链路**（用户原话整理）：

```
用户：最近肠道不好，应该吃什么？
  → agent 搜索肠道相关商品 + 查 RAG + 查知识图谱
  → 回复「如果是肠道不通畅可以吃益生菌」+ 卡片推荐到前端 + 说明为什么推荐、有什么作用
  → 用户满意：「加两份到购物车」
  → agent 加入购物车
  → 用户：「下单」
  → agent 推送支付卡片
  → 用户点击 → 跳转支付页
```

**支线**：也可以「推荐前先多问几轮」，得到明确信息再过滤出结果。

## 三、现场排查：三个真实会话暴露的缺陷（P0）

alice 账号（`u1001`）的三个会话：`u1001-1791252059073`（发烧了应该吃什么药）、
`u1001-1791252238126`（有没有儿童适合吃的补品）、`u1001-1791252142046`（最近肠道不好，应该吃什么药）。

### P0-A · 商品被引用校验器整段剔除（**已定位，未修**）

**现象**：回答里出现空的商品表格，只剩表头：

```
| 商品 | 规格 | 价格 | 说明 |
|---|---|---|---|
**关于「肠道不通畅」的调理依据**
```

**根因（代码级确认）**：模型**确实搜到了商品并写进了表格**，但被剔除。响应体里的原话是铁证：

```json
"unsupportedClaims": [
  "| SPU5 益生菌粉 | SKU9（30袋）/ SKU10（60袋） | 158 / 278 元 | 每袋 100 亿活菌，已售 1560 件 |",
  "| SPU6 膳食纤维粉 | SKU11 | 69 元 | 水溶性膳食纤维，已售 320 件 |",
  "| SPU23 白芸豆膳食纤维片 | SKU32 | 128 元 | 含白芸豆提取物 |",
  "要不要我帮你把 SPU5 或 SPU6 加进购物车？"
],
"unsupportedStripped": true
```

`CitationVerifier` 的判据是：

```java
boolean knowledgeAnswer = cited > 0;   // cited 只数 [n] 角标
boolean stripped = knowledgeAnswer && withinBudget && !unsupported.isEmpty();
```

- 本轮的 `[n]` 引用来自知识库切片（`cited = 4 > 0`），于是 `knowledgeAnswer = true`
- 商品表的出处是 **`product_search` 工具返回**，没有 `[n]` 角标，商品名也不在 `citableTitles` 里
- 于是它们被判定成「讲事实却没出处」→ **整段剔除**，表格只剩表头

**这不是表格渲染 bug，是「商品的出处形态没被闸门承认」。**闸门本身是对的（防编造），
缺的是「工具返回的事实同样算有依据」这条判据。

**修法方向**（待实施）：
1. 有工具执行记录时，**工具返回里出现过的实体名（商品名/SPU 编号/SKU 编号）应视为可引用的出处**，
   与 `citableTitles` 同一层——识别面要收窄到「工具真的返回过」，不能放开到任意字符串
2. 剔除的粒度值得重新审视：现在是按句剔除，表格行被拆开后**表头留在原地**，
   渲染成一张空表，比整段消失更让人困惑

**验收证据来源**：重跑那三个会话，商品表**必须还在**且商品名/价格与工具返回逐字一致；
同时构造一个「模型编造了不存在的商品」的样本，断言**仍被剔除**（闸门不能因此失效）。

### P0-B · 症状类查询的行为（**用户已拍板**）

三个会话都是「症状 → 商品」类查询（发烧吃什么药、肠道不好吃什么、儿童补品）。
共同问题是：用户说的是**症状**，语料写的是**成分与适应症**，图谱能接住
「成分能不能一起」却接不住「症状 → 商品」。

#### 用户拍板的判据（原话）

> 我认为商品、rag、知识图谱能检索到相关的内容，agent 就要结合用户提问做评估。
> agent 在拿不定主意时，也可以不急着给出回答，而是和用户再对话几次，将场景问清楚，
> 然后确定下来再做评估然后给出优质回答。总的来说就是 agent 有应对灵活和复杂的能力。
> 只有在无法从 rag 和知识图谱中找到与用户需求相关的商品，才跟用户说没有。
> 也就是说**不是拒答，而是没有就是没有**。

#### 这条判据要拆成三条可执行规则

1. **能查到就必须给**。商品库 / RAG / 图谱任一路径能捞到与用户需求相关的内容，
   agent 就有义务结合用户提问做评估，**给出推荐 + 为什么推荐 + 有什么作用**。
   不得因为「医疗话题敏感」而退回成一段泛泛的免责声明——那不是谨慎，是把该做的事省掉了。

2. **拿不准就先问，不急着答**。信息不足（比如「肠道不好」可能是便秘/腹泻/腹胀，
   三者适用的商品完全不同）时，agent **先澄清场景再检索**，而不是拿模糊输入硬查、
   再拿一堆不相关的结果凑一个回答。澄清轮数不设死上限，但每轮必须问出**能缩小结果集的信息**。

3. **只有真的没有，才说没有**。说「没有」的**唯一**条件是：RAG 与图谱都找不到
   与用户需求相关的商品/依据。此时要**说清是「查不到」而不是「不能吃」**——
   这两句话在本场景里意思相反（对照 `InteractionReport` 里「没有收录 ≠ 安全」的同一条原则）。

#### 与「拒答」的边界（必须写进材料，面试会追问）

本项目的拒答门（`EvidenceGate`）防的是**模型拿常识编造平台事实**，
判据是「有没有平台依据」。这条拍板**不推翻拒答门**，而是明确它的适用面：

- 有依据 → 正常回答（哪怕话题是医疗，只要平台有对应商品的说明书依据）
- 无依据且不该编 → 如实说「知识库里没有」，**不说「你这种情况不能吃」**——
  这是一个关于**平台资料覆盖度**的陈述，不是一个**医学结论**

#### 一个必须守住的边界（安全）

拍板不等于「对任何症状都给商品推荐」。以下两类仍要拦住，且要在处理方式上分开：

- **平台查得到相关商品** → 推荐 + 说明作用 + 提醒「不能替代药物治疗」
- **平台查不到，或症状提示需要就医**（如肠梗阻、便血、持续发烧）→ 明确建议就医，
  不给商品推荐。**判据是「资料里有没有相应的禁忌/就医提示」，不是「话题敏不敏感」**——
  膳食纤维说明书里写着「肠梗阻、肠道狭窄者禁用」，那就是资料说该就医，照着说即可

#### 验收证据来源

重跑 alice 那三个会话：

- 「肠道不好」类：要么给出澄清问题，要么给出带说明的推荐卡片，**不得只有一段免责声明**
- 商品表**必须还在**（依赖 P0-A 的修复），商品名/价格与工具返回逐字一致
- 构造「平台确实没有相关商品」的样本，断言回答是「知识库里没有收录」而**不是**「不能吃」
