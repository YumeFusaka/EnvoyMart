## 〇、四个根因（解释框架，不直接执行）

三份文档的条目按「谁在什么时刻决定一件事」重新归类后，只落成 4 个根因：

| 根因 | 一句话 | 表现面（跨文档） |
|------|--------|------------------|
| **R1** | 派生数据没有「重新对齐」的时机 | 商品下架说明书不动 · 13 商品不在图谱 · 覆盖度无检查 · 图谱链接失败不可见 |
| **R2** | 同一事实在两处各算一遍 | 节点键 vs 展示名 · `TOOL_LABELS` 只登记 5 个 · 材料数字写死漂移 |
| **R3** | 该有判断的地方没有判断 | 所有回答走 RAG · 写超时被当成「失败」而不核实 · 推荐不检查有无依据 |
| **R4** | 检查/评测的口径与生产链路不一致 | 评测页跑假链路 · 夹具与线上两套 · 「测量错误被当成产品 bug」（P1-7 教训） |

**为什么根因不能直接当执行顺序**：一个改动常常同时修掉多个根因（如关联表同时修 R1 与 R4），
而执行必须按**依赖**——覆盖度检查依赖关联表，关联表依赖 `linkProducts` 挂钩子。

## G1 · 写操作超时与语义修正（修 R3）

**修掉**：P0-1（下单已成功却报失败）。附带更正一处**误导性的错误消息**
（「订单服务连不上」实为 `Read timed out`，服务一直健康）。

### 改动

| # | 动作 | 落点 |
|---|------|------|
| 1.1 | 给 order-service 单独放宽 read-timeout（5000 → 30000） | `ai-service/application.yml` |
| 1.2 | 预热 Seata 类加载，把首次 2~3 秒冷启动挪出首单 | `order-service` 启动期 |
| 1.3 | **「超时」不再被翻译成「失败」**——措辞与语义同时修正 | `Downstream` / `CheckoutTool` |
| 1.4 | （待定）幂等键 + 超时后查证实际结果 | 跨服务，需先设计幂等键 |

### 为什么 1.3 比 1.1 重要

放宽超时只是**减少**超时概率，耗时总有长尾。真正的缺陷是：
**写操作超时后，系统直接判定「失败」而没有核实订单是否已创建。**
用户按「稍后再试」再点一次 → 两笔订单。1.1 治标，1.3 治语义，1.4 治本。

### 验收

| 标准 | 证据 |
|------|------|
| 正常下单不再触发 read timeout | order-service 日志 `POST /orders/checkout -> 200 <Nms` |
| 超时话术不再说「连不上」 | 构造超时，检查给用户的消息 |
| （1.4 后）重复确认不产生两笔订单 | 连续两次确认，订单表只多一行 |

## G2 · 存储补齐 + 覆盖度检查（修 R1 的数据侧）

**修掉**：P0-2（13 个商品不在图谱、3 个无说明书）。

### 改动

| # | 动作 | 说明 |
|---|------|------|
| 2.1 | 补齐 3 篇缺失说明书 | SPU5 益生菌粉 / SPU16 褪黑素缓释片 / SPU17 γ-氨基丁酸软糖 |
| 2.2 | 核对 KB-0047 的归属 | 「氨糖维 D 钙片（中老年）」有文档无商品 |
| 2.3 | 全量重建图谱，观察 13 个缺失能自动补上几个 | 区分「名字对不上」与「模型没抽」 |
| 2.4 | **新增覆盖度检查** | 列出「有商品但图谱无节点」，把这类问题变成**可发现的** |

### 为什么 2.4 是关键

现在的发现方式是**人肉比对**（用户在前端一页页看出来的）。
这说明系统**没有能力回答「37 个商品覆盖全了吗」**——那正是 R1 的元层面表现。
2.4 让这个问题变成一次接口调用就能回答。

### 与 G3 的关系

2.4 的**完整形态**依赖 G3 的关联表（有了它才能回答「SPU10 有没有文档、文档进图谱了吗」）；
但**简化版可以先做**——纯比对「catalog 的 37 个 id」与「图谱里 name 以 spu 开头的节点」，
不需要关联表。**先做简化版让问题变得可见，G3 落地后再升级。**

## G4 · 生命周期联动（修 R1，依赖 G3）

**修掉**：商品下架说明书的四处同步（MySQL / BM25 / 向量库 / 图谱）。

### 改动

```
下架 SPU7
  -> 查 knowledge_doc_product WHERE spu_id=7 AND role=SUBJECT
  -> 对每篇 docNo：
       PUT /knowledge/admin/documents/{docNo}/status?status=0   （事实源先改）
       POST /ai/admin/knowledge/reindex/{docNo}                 （复用现成的四处同步）
```

**关键：四处同步的机制已完整存在**（就是 `toggleStatus → syncOne` 那条链路，
停用走 `rebuildOne` 的 `target == null` 分支已经能正确清理四处）。
**缺的只是「商品下架时，系统不知道该下架哪几篇文档」**——G3 补上这个。

**反向**：上架时反查 `role=SUBJECT AND status=0`，提示或自动恢复。

## G5 · 入口检索意图分流（修 R3）

**修掉**：P1-4（所有回答无条件走 RAG）。

### 改动

| # | 动作 | 说明 |
|---|------|------|
| 5.1 | 判定本轮是否需要检索 | **必须与现有规划调用合并**，不新增模型调用 |
| 5.2 | 不需要时跳过入口检索 | 闲聊 / 业务操作类 |
| 5.3 | 保留 `KnowledgeSearchTool` | 分流只省掉**入口那一次**，推理中途仍可主动检索 |

### 为什么必须合并到规划调用

「为省一次检索而多一次模型调用」是**负收益**。
现有 `LangChain4jLLMProvider` 已有任务规划器，让它多输出一个 `needRetrieval` 布尔字段即可。

### 分类口径

| 类别 | 例子 | 检索 |
|------|------|------|
| 闲聊 / 元对话 | 「你好」「你是谁」 | 否 |
| 业务操作 | 「加入购物车」「查订单」 | 否 |
| 商品咨询 | 「这个能不能和钙片一起吃」 | **是** |
| 规则咨询 | 「七天无理由怎么算」 | **是** |
| 混合 | 「脚酸腿软吃什么」 | **是** |

## G6 · 工具清单补全 + 参数渲染（修 R2）

**修掉**：P1-5（弹窗显示原始代码）+ P1-6（无法查购物车）。

### 改动

| # | 动作 | 落点 |
|---|------|------|
| 6.1 | 新增 `cart_query` 工具（只读，不需确认） | `ai-service/tool/`，复用 `GET /cart` |
| 6.2 | 补齐 `TOOL_LABELS`（11 个工具全覆盖） | `frontend/src/utils/tools.ts` |
| 6.3 | 参数结构化渲染（下单 → 收货信息卡片、加购 → 商品名×数量） | `PendingApprovalCard.vue` |
| 6.4 | **保留原始参数兜底**（未知工具或渲染失败时回退，绝不隐藏） | 同上 |

### 6.4 是硬约束，不是可选项

`actionLabel` 的注释写得很清楚，而且**这个判断是对的**：

> 「参数是用户判断『要动的是哪一个对象』的唯一依据，翻译、截断或省略它都是在替用户改授权对象——
> 一个写着『订单取消』却不说是哪一单的卡片，点了确认等于盲签。」

所以 6.3 的目标是**信息量不减、可读性提升**，不是把参数藏起来。

**待评估**：6.3 里「加购显示商品名」需要在确认**之前**把 skuId 解析成商品名（多一次下游调用）。

## G9 · 管理台前端整体优化

**来源**：用户 2026-10-06 实测发现「`/admin` 下大多页面没优化过，样式布局乱且原始」。

**范围**：10 个页面（概览 / 商品列表 / 商品编辑 / 类目品牌 / 订单 / 售后 / 评价 / 用户 / 工单 / 知识库）。

**授权**：用户明确「不提要求，完全由我的审美与考虑来改进」。

**设计约束**（来自项目规范，不是用户要求）：

- 沿用现有设计系统（`styles/tokens.css` 的语义 Token），**不另起一套**
- 覆盖自然状态：加载 / 空态 / 错误 / 禁用 / 悬停 / 聚焦 / 长文本 / 极端数据
- 优先复用现有组件与图标库

**已知**：`AdminKnowledgeView`（10-06）与 `AdminProductEditView`（10-05）改得较晚，
可能相对好一些；`AdminCatalogView` / `AdminTicketView`（9-30）最早，大概率最原始。
**逐页核对，不一刀切重写。**
