## 一、为什么做、判据为什么这么定

plan -> act -> evaluate -> replan 这条执行图早已用 LangGraph4j 编排，`critique` 也做了
四分类失败诊断，但此前**没有任何一条用例回答「复杂任务规划得怎么样」**——所有评测都集中在
检索与问答质量上。「5 步以上的任务规划质量如何」只能靠描述机制，给不出数字。

判据刻意**不掺模型自评**（那等于拿一个黑箱去评另一个黑箱），全部落在可确定性计算的结构与顺序上：

| 指标 | 口径 |
|---|---|
| 工具覆盖率 | 期望工具集合里，有多少条任务的工具被全部规划到 |
| 顺序满足率 | `mustPrecede` 的偏序（如「先查商品、再加购」）是否满足 |
| 步数达标率 | 计划长度是否落在 `[expectMinSteps, expectMaxSteps]` |
| 依赖声明率 | 至少有一条 `dependsOn` 非空的任务占比 |
| 累计缺工具 / 多规划 | 漏掉的期望工具次数 / 规划出多余工具的条数 |

## 二、结果（两次连跑）

| 指标 | 第 1 次 | 第 2 次 |
|---|---|---|
| 整条通过率 | 9/12 = 0.750 | 10/12 = 0.833 |
| 工具覆盖率 | 9/12 = 0.750 | 10/12 = 0.833 |
| 顺序满足率 | 12/12 = 1.000 | 11/12 = 0.917 |
| 步数达标率 | 10/12 = 0.833 | — |
| **依赖声明率** | **2/12 = 0.167** | **2/12 = 0.167** |
| 累计缺工具 | 3 | 3 |
| 累计多规划 | 1 | 1 |

样本量只有 12 条，比率会随模型采样抖动（通过率 9~10/12），**但依赖声明率两次都钉在 2/12**，
这不是抖动，是一个稳定现象。

## 三、最值钱的发现：Plan-and-Execute 的结构性卖点没被兑现

Plan-and-Execute 相对 ReAct 的结构性优势是「**互不依赖的步骤可以并发执行**」——这正是执行图
里 `dependsOn` 分层调度的意义。但实测：**12 条任务里只有 2 条声明了依赖**。

更具体的失败形状：

- 「查订单 20240001 到哪了」→ 规划出 `[logistics_query]`，**缺了 `order_query`**。
  用户给的是**订单编号**，物流工具需要的是从订单查出的物流单号——模型把「查物流」当成了单步，
  没有意识到它依赖「先用订单编号查订单」。这正是「顺序/依赖判据」要抓的形态，而只数工具名是抓不到的。
- 「找益生菌 + 我之前买过吗」→ 只规划了 `[product_search]`，漏掉 `order_query`。
  两个子任务互不依赖，本应都出现、且**都不填 dependsOn**（并发）。模型漏了第二个。

**结论**：规划器在「单域、工具选择清晰」的任务上表现稳定（顺序 11~12/12、该拒答的不硬调工具），
但在两个方向上有系统性问题——**① 跨域任务会漏子任务；② 几乎不声明依赖**，后者使「并发执行」
这个卖点在真实规划里基本没被触发（执行器有能力，但规划器没喂给它可并发的结构）。

这是一条**可讲的经验**：一个能力「实现了」不等于「被用上了」——`dependsOn` 的并发调度链路
在代码里是真的（`AgentGraph` 按依赖分层），但没有一条真实任务让它跑起来。

## 四、边界（如实列出）

- **样本量小**：12 条，够定性、不够精细的分档统计；比率随采样抖动。
- **不是 CI 门禁**：要调真实模型（计费 + 不可复现），靠 `RUN_PLAN_EVAL` 显式开关触发。
- **只测规划阶段**：不测执行与重规划；`critique` 的质量是另一个课题。
- **工具集是精简版**：测试里注册了 10 个真实工具名与描述，但参数 schema 简化了
  （规划只读描述，不填真实参数），因此「参数填得对不对」不在本评测范围内。
