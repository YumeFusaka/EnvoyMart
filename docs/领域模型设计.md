# EnvoyMart 领域模型设计

> 批次 0 产出。定义平台的数据模型、状态机与服务边界。配套实施计划见 `平台改造规划.md`。

## 一、服务边界

| 服务 | 端口 | 承载域 | 说明 |
|---|---|---|---|
| gateway-service | 8080 | 路由 / 鉴权 / 限流 | 保持 |
| auth-service | 9001 | **用户 / 地址 / 认证** | 地址簿并入用户域 |
| product-service | 9002 | **商品 / 类目 / 品牌 / SKU / 库存** | 库存并入商品域 |
| order-service | 9003 | **购物车 / 订单 / 履约 / 售后** | 四者共享订单聚合根，同一事务边界 |
| payment-service | 9005 | **支付 / 退款** | 退款单与支付单同源 |
| review-service | 9006 | 评价 | 保持 |
| **promotion-service** | 9007 | **优惠券 / 活动** | 新增 |
| ai-service | 9004 | Agent 编排 / 会话 / 记忆 | 保持 |
| **knowledge-service** | 9008 | **文档 / 检索 / 图谱 / 溯源** | 新增 |

**边界原则**：不为微服务而拆。售后与履约跟着订单聚合根走——它们共享订单的状态机、事务边界与幂等键；单独起服务只会把一次本地事务摊成分布式事务，得不偿失。营销独立则是因为它的核心实体（券模板、活动）与订单**不是同一个生命周期**：券在订单之前就存在，订单结束后券的统计还在继续。

### user_address

```sql
CREATE TABLE user_address (
  id            BIGINT      NOT NULL AUTO_INCREMENT,
  user_id       VARCHAR(32) NOT NULL,
  receiver_name VARCHAR(64) NOT NULL,
  receiver_phone VARCHAR(20) NOT NULL,
  province      VARCHAR(32) NOT NULL,
  city          VARCHAR(32) NOT NULL,
  district      VARCHAR(32) NOT NULL,
  detail        VARCHAR(255) NOT NULL,
  is_default    TINYINT     NOT NULL DEFAULT 0,
  tag           VARCHAR(16) COMMENT '家 / 公司 / 学校',
  created_at    DATETIME    NOT NULL,
  updated_at    DATETIME    NOT NULL,
  PRIMARY KEY (id),
  KEY idx_user (user_id, is_default)
);
```

**默认地址的唯一性由应用层保证**（同一用户至多一条 `is_default = 1`），换默认地址时在同一事务内先清后置。不加数据库唯一索引，因为需要先清后置两步，唯一索引会在中间态冲突。

## 三、商品域（product-service）

### 类目与品牌

```sql
CREATE TABLE category (
  id        BIGINT      NOT NULL AUTO_INCREMENT,
  parent_id BIGINT      NOT NULL DEFAULT 0,
  name      VARCHAR(64) NOT NULL,
  level     TINYINT     NOT NULL COMMENT '1/2/3 级',
  path      VARCHAR(255) NOT NULL COMMENT '祖级路径 1/5/12，便于查子树',
  sort      INT         NOT NULL DEFAULT 0,
  status    TINYINT     NOT NULL DEFAULT 1,
  PRIMARY KEY (id),
  KEY idx_parent (parent_id),
  KEY idx_path (path)
);

CREATE TABLE brand (
  id      BIGINT      NOT NULL AUTO_INCREMENT,
  name    VARCHAR(64) NOT NULL,
  logo    VARCHAR(512),
  description VARCHAR(500),
  status  TINYINT     NOT NULL DEFAULT 1,
  PRIMARY KEY (id),
  UNIQUE KEY uk_name (name)
);
```

`path` 存祖级路径（形如 `1/5/12`），前缀匹配即可取整个子树，避免递归查询。这是类目树的常用做法。

### SPU / SKU

```sql
-- SPU：商品概念层（"iPhone 15"）
CREATE TABLE product_spu (
  id          BIGINT       NOT NULL AUTO_INCREMENT,
  spu_code    VARCHAR(64)  NOT NULL,
  name        VARCHAR(255) NOT NULL,
  subtitle    VARCHAR(255),
  category_id BIGINT       NOT NULL,
  brand_id    BIGINT,
  main_image  VARCHAR(512),
  images      VARCHAR(2048) COMMENT '轮播图，逗号分隔',
  detail_html MEDIUMTEXT   COMMENT '图文详情',
  status      TINYINT      NOT NULL DEFAULT 0 COMMENT '0 下架 / 1 上架',
  sales       INT          NOT NULL DEFAULT 0,
  rating_avg  DECIMAL(3,2) NOT NULL DEFAULT 5.00,
  review_count INT         NOT NULL DEFAULT 0,
  created_at  DATETIME     NOT NULL,
  updated_at  DATETIME     NOT NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_spu_code (spu_code),
  KEY idx_category_status (category_id, status),
  KEY idx_brand (brand_id)
);

-- SKU：可售单元层（"iPhone 15 黑色 128G"）——价格与库存挂在这一层
CREATE TABLE product_sku (
  id             BIGINT      NOT NULL AUTO_INCREMENT,
  spu_id         BIGINT      NOT NULL,
  sku_code       VARCHAR(64) NOT NULL,
  price          BIGINT      NOT NULL COMMENT '售价（分）',
  original_price BIGINT      COMMENT '划线价（分）',
  stock          INT         NOT NULL DEFAULT 0,
  image          VARCHAR(512),
  status         TINYINT     NOT NULL DEFAULT 1,
  PRIMARY KEY (id),
  UNIQUE KEY uk_sku_code (sku_code),
  KEY idx_spu_status (spu_id, status)
);

-- 规格项与规格值（颜色 / 容量）
CREATE TABLE product_spec (
  id     BIGINT      NOT NULL AUTO_INCREMENT,
  spu_id BIGINT      NOT NULL,
  name   VARCHAR(32) NOT NULL,
  sort   INT         NOT NULL DEFAULT 0,
  PRIMARY KEY (id),
  KEY idx_spu (spu_id)
);

CREATE TABLE product_spec_value (
  id      BIGINT      NOT NULL AUTO_INCREMENT,
  spec_id BIGINT      NOT NULL,
  value   VARCHAR(64) NOT NULL,
  sort    INT         NOT NULL DEFAULT 0,
  PRIMARY KEY (id),
  KEY idx_spec (spec_id)
);

-- SKU ↔ 规格值
CREATE TABLE product_sku_spec (
  sku_id        BIGINT NOT NULL,
  spec_id       BIGINT NOT NULL,
  spec_value_id BIGINT NOT NULL,
  PRIMARY KEY (sku_id, spec_id),
  KEY idx_spec_value (spec_value_id)
);
```

**规格用规范化三表而非 JSON 串**：JSON 存法写起来快，但"找出所有黑色的 SKU"这类查询只能全表扫后内存过滤；规范化后是一次索引命中。价格与库存**必须挂在 SKU 上**——挂在 SPU 上就表达不了"128G 比 256G 便宜 800 块"。

### 商品属性（参数，非规格）

```sql
CREATE TABLE product_attribute (
  id          BIGINT       NOT NULL AUTO_INCREMENT,
  category_id BIGINT       NOT NULL COMMENT '属性归属类目，同类目商品共用',
  name        VARCHAR(64)  NOT NULL COMMENT '屏幕尺寸 / 电池容量',
  input_type  VARCHAR(16)  NOT NULL COMMENT 'TEXT / SELECT / MULTI_SELECT',
  unit        VARCHAR(16),
  sort        INT          NOT NULL DEFAULT 0,
  PRIMARY KEY (id),
  KEY idx_category (category_id)
);

CREATE TABLE product_attribute_value (
  id           BIGINT      NOT NULL AUTO_INCREMENT,
  attribute_id BIGINT      NOT NULL,
  value        VARCHAR(255) NOT NULL,
  sort         INT         NOT NULL DEFAULT 0,
  PRIMARY KEY (id),
  KEY idx_attribute (attribute_id)
);
```

属性挂在**类目**上（同类目商品共用一套参数模板），值挂在**商品**上。这与规格的区别：规格决定"买哪一个"，属性只是"描述是什么"。

### 库存流水

```sql
CREATE TABLE stock_log (
  id           BIGINT      NOT NULL AUTO_INCREMENT,
  sku_id       BIGINT      NOT NULL,
  type         VARCHAR(16) NOT NULL COMMENT 'DEDUCT / RESTORE / INBOUND',
  quantity     INT         NOT NULL,
  before_stock INT         NOT NULL,
  after_stock  INT         NOT NULL,
  biz_type     VARCHAR(32) COMMENT 'ORDER / AFTER_SALE / MANUAL',
  biz_id       VARCHAR(64) COMMENT '订单号或售后单号',
  remark       VARCHAR(255),
  created_at   DATETIME    NOT NULL,
  PRIMARY KEY (id),
  KEY idx_sku_created (sku_id, created_at),
  KEY idx_biz (biz_type, biz_id)
);
```

库存变动**全部留痕**。回补失败、对账、排查"库存为什么少了"都靠它——原实现里回补失败只能打一行日志，根因就是没有这张表。

## 四、交易域（order-service）

### 购物车

```sql
CREATE TABLE cart_item (
  id         BIGINT      NOT NULL AUTO_INCREMENT,
  user_id    VARCHAR(32) NOT NULL,
  spu_id     BIGINT      NOT NULL,
  sku_id     BIGINT      NOT NULL,
  quantity   INT         NOT NULL,
  selected   TINYINT     NOT NULL DEFAULT 1 COMMENT '是否选中结算',
  created_at DATETIME    NOT NULL,
  updated_at DATETIME    NOT NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_user_sku (user_id, sku_id),
  KEY idx_user (user_id)
);
```

`UNIQUE (user_id, sku_id)` 让"同商品累加"由数据库保证幂等，而不是靠先查后写的应用逻辑。**购物车条目引用 SKU 而非 SPU**——加购时必须已经选定规格。

### 订单

```sql
CREATE TABLE shop_order (
  id        BIGINT      NOT NULL AUTO_INCREMENT,
  order_no  VARCHAR(32) NOT NULL,
  user_id   VARCHAR(32) NOT NULL,
  status    VARCHAR(24) NOT NULL,

  -- 金额，单位一律为分
  total_amount    BIGINT NOT NULL COMMENT '商品总额',
  freight_amount  BIGINT NOT NULL DEFAULT 0 COMMENT '运费',
  discount_amount BIGINT NOT NULL DEFAULT 0 COMMENT '优惠合计',
  pay_amount      BIGINT NOT NULL COMMENT '应付 = 总额 + 运费 - 优惠',

  -- 收货信息快照（下单时冻结，地址簿后续修改不影响历史订单）
  receiver_name     VARCHAR(64)  NOT NULL,
  receiver_phone    VARCHAR(20)  NOT NULL,
  receiver_province VARCHAR(32)  NOT NULL,
  receiver_city     VARCHAR(32)  NOT NULL,
  receiver_district VARCHAR(32)  NOT NULL,
  receiver_detail   VARCHAR(255) NOT NULL,

  -- 时间轴
  expire_at   DATETIME NOT NULL COMMENT '支付截止时间',
  created_at  DATETIME NOT NULL,
  paid_at     DATETIME,
  shipped_at  DATETIME,
  received_at DATETIME,
  closed_at   DATETIME,
  finished_at DATETIME,

  remark        VARCHAR(255),
  cancel_reason VARCHAR(255),
  PRIMARY KEY (id),
  UNIQUE KEY uk_order_no (order_no),
  KEY idx_user_status (user_id, status),
  KEY idx_status_expire (status, expire_at) COMMENT '超时关单扫描走这个索引'
);

CREATE TABLE shop_order_item (
  id            BIGINT       NOT NULL AUTO_INCREMENT,
  order_id      BIGINT       NOT NULL,
  order_no      VARCHAR(32)  NOT NULL,
  spu_id        BIGINT       NOT NULL,
  sku_id        BIGINT       NOT NULL,
  -- 下单时的商品快照：商品改名改价不影响历史订单
  spu_name      VARCHAR(255) NOT NULL,
  sku_spec_text VARCHAR(255) COMMENT '颜色:黑;容量:128G',
  sku_image     VARCHAR(512),
  unit_price    BIGINT       NOT NULL,
  quantity      INT          NOT NULL,
  subtotal      BIGINT       NOT NULL,
  PRIMARY KEY (id),
  KEY idx_order (order_id),
  KEY idx_sku (sku_id)
);

CREATE TABLE order_status_log (
  id            BIGINT      NOT NULL AUTO_INCREMENT,
  order_id      BIGINT      NOT NULL,
  from_status   VARCHAR(24),
  to_status     VARCHAR(24) NOT NULL,
  operator_type VARCHAR(16) NOT NULL COMMENT 'USER / SYSTEM / ADMIN',
  operator_id   VARCHAR(32),
  remark        VARCHAR(255),
  created_at    DATETIME    NOT NULL,
  PRIMARY KEY (id),
  KEY idx_order (order_id, created_at)
);
```

**两个关键决策**：

1. **金额一律用 `BIGINT` 存分**，不用 `DECIMAL`/`DOUBLE`。浮点会累积误差，而"分摊后各子项之和必须等于总额"是硬约束。用分做整数运算，这条恒等式可以被断言。
2. **订单行存商品快照**。商品改价后，历史订单必须显示下单当时的价格与名称——这是订单表不引用商品表的唯一理由。

### 订单状态机

```
                 ┌──────────────► CANCELLED   （用户主动取消）
                 │
CREATED ─────────┼──────────────► CLOSED      （超时未支付，定时关单）
（待支付）        │
                 └──► PAID ──► SHIPPED ──► RECEIVED ──► COMPLETED
                     （已支付）  （已发货）   （已收货）    （已完成）
                        │                                  │
                        └──────────► REFUNDING ──► REFUNDED
                                     （退款中）    （已退款）
```

**枚举与守卫**：

```java
public enum OrderStatus {
    CREATED, PAID, SHIPPED, RECEIVED, COMPLETED,
    CANCELLED, CLOSED, REFUNDING, REFUNDED;
}
```

流转集中在一处校验，非法流转抛业务异常而非静默更新。**每条流转必须写 `order_status_log`**——用户问"订单为什么是这个状态"，答案在流水里，不在客服记忆里。

**超时关单**：`CREATED` 状态的订单在 `expire_at` 到期后由定时任务扫描关闭并回补库存。索引 `idx_status_expire` 专为此扫描建立。这是原实现最硬的缺陷——未支付订单永久占用库存。

### 履约（物流）

```sql
CREATE TABLE order_delivery (
  id            BIGINT       NOT NULL AUTO_INCREMENT,
  order_id      BIGINT       NOT NULL,
  order_no      VARCHAR(32)  NOT NULL,
  carrier_code  VARCHAR(32)  NOT NULL COMMENT '承运商编码',
  carrier_name  VARCHAR(64)  NOT NULL,
  tracking_no   VARCHAR(64)  NOT NULL COMMENT '运单号',
  status        VARCHAR(24)  NOT NULL COMMENT 'CREATED / PICKED_UP / IN_TRANSIT / DELIVERING / SIGNED',
  shipped_at    DATETIME     NOT NULL,
  signed_at     DATETIME,
  PRIMARY KEY (id),
  UNIQUE KEY uk_tracking_no (tracking_no),
  UNIQUE KEY uk_order (order_id)
);

CREATE TABLE order_delivery_trace (
  id          BIGINT      NOT NULL AUTO_INCREMENT,
  delivery_id BIGINT      NOT NULL,
  happen_at   DATETIME    NOT NULL,
  status      VARCHAR(24) NOT NULL,
  description VARCHAR(255) NOT NULL,
  location    VARCHAR(128),
  PRIMARY KEY (id),
  KEY idx_delivery_time (delivery_id, happen_at)
);
```

物流是**独立实体**而非订单上的几个字段：一个订单可以分批发货，承运商与运单号有独立生命周期，轨迹是随时间增长的时间序列。

### 售后

```sql
CREATE TABLE after_sale (
  id            BIGINT       NOT NULL AUTO_INCREMENT,
  after_sale_no VARCHAR(32)  NOT NULL,
  order_id      BIGINT       NOT NULL,
  order_no      VARCHAR(32)  NOT NULL,
  order_item_id BIGINT       NOT NULL,
  user_id       VARCHAR(32)  NOT NULL,
  type          VARCHAR(24)  NOT NULL COMMENT 'REFUND_ONLY / RETURN_REFUND / EXCHANGE',
  status        VARCHAR(24)  NOT NULL,
  reason        VARCHAR(64)  NOT NULL,
  description   VARCHAR(500),
  images        VARCHAR(1024),
  refund_amount BIGINT       NOT NULL,
  applied_at    DATETIME     NOT NULL,
  audited_at    DATETIME,
  finished_at   DATETIME,
  audit_remark  VARCHAR(255),
  PRIMARY KEY (id),
  UNIQUE KEY uk_after_sale_no (after_sale_no),
  KEY idx_order (order_id),
  KEY idx_user_status (user_id, status)
);

CREATE TABLE after_sale_log (
  id           BIGINT      NOT NULL AUTO_INCREMENT,
  after_sale_id BIGINT     NOT NULL,
  from_status  VARCHAR(24),
  to_status    VARCHAR(24) NOT NULL,
  operator_type VARCHAR(16) NOT NULL,
  operator_id  VARCHAR(32),
  remark       VARCHAR(255),
  created_at   DATETIME    NOT NULL,
  PRIMARY KEY (id),
  KEY idx_after_sale (after_sale_id, created_at)
);

CREATE TABLE after_sale_policy (
  id            BIGINT       NOT NULL AUTO_INCREMENT,
  category_id   BIGINT       COMMENT 'NULL 表示全类目默认',
  type          VARCHAR(24)  NOT NULL,
  returnable    TINYINT      NOT NULL DEFAULT 1 COMMENT '该类目是否支持退货',
  return_days   INT          NOT NULL DEFAULT 7 COMMENT '可退天数',
  quality_days  INT          NOT NULL DEFAULT 15 COMMENT '质量问题可退天数',
  max_refund_ratio DECIMAL(3,2) NOT NULL DEFAULT 1.00 COMMENT '最高退款比例',
  requirements  VARCHAR(500) COMMENT '附加条件描述',
  doc_ref       VARCHAR(128) COMMENT '对应知识库文档编号，用于溯源',
  PRIMARY KEY (id),
  KEY idx_category_type (category_id, type)
);
```

**售后状态机**：

```
APPLIED ─► APPROVED ─► RETURNING ─► RECEIVED ─► REFUNDING ─► FINISHED
（已申请） （已通过）  （退货中）   （已收货）  （退款中）   （已完成）
   │
   ├──► REJECTED   （审核驳回）
   └──► CANCELLED  （用户撤销）
```

**政策引擎与知识层的交汇（本设计的关键点）**：

"我这个订单能退吗"的判定走**两条腿**：

- **规则引擎**给出结论——`after_sale_policy` 表按类目与售后类型匹配，校验订单状态、时间窗、金额上限。结论是确定性的，不受模型影响。
- **知识库**给出依据——政策条文以文档形式入库，结论附带 `doc_ref`，前端可点击跳转到政策原文。

**为什么不全交给 RAG**：政策判定涉及金额与时间窗，模型算错就是资损；为什么不全交给规则：规则能给出"能不能退"，但答不出"为什么"。**规则判定 + 检索解释**，两条腿各司其职。

## 五、支付域（payment-service）

```sql
CREATE TABLE payment (
  id             BIGINT      NOT NULL AUTO_INCREMENT,
  payment_no     VARCHAR(32) NOT NULL,
  order_id       BIGINT      NOT NULL,
  order_no       VARCHAR(32) NOT NULL,
  user_id        VARCHAR(32) NOT NULL,
  amount         BIGINT      NOT NULL,
  channel        VARCHAR(24) NOT NULL COMMENT 'ALIPAY / WECHAT / MOCK',
  pay_type       VARCHAR(24) COMMENT 'APP / WEB / QR',
  status         VARCHAR(16) NOT NULL COMMENT 'PENDING / SUCCESS / FAILED / CLOSED',
  transaction_no VARCHAR(64) COMMENT '渠道流水号',
  paid_at        DATETIME,
  created_at     DATETIME    NOT NULL,
  updated_at     DATETIME    NOT NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_payment_no (payment_no),
  UNIQUE KEY uk_order (order_id) COMMENT '一单一次支付',
  UNIQUE KEY uk_transaction (transaction_no)
);

CREATE TABLE refund (
  id             BIGINT      NOT NULL AUTO_INCREMENT,
  refund_no      VARCHAR(32) NOT NULL,
  payment_id     BIGINT      NOT NULL,
  order_id       BIGINT      NOT NULL,
  after_sale_id  BIGINT      COMMENT '售后退款时关联',
  user_id        VARCHAR(32) NOT NULL,
  amount         BIGINT      NOT NULL,
  status         VARCHAR(16) NOT NULL COMMENT 'PENDING / SUCCESS / FAILED',
  reason         VARCHAR(255),
  channel_refund_no VARCHAR(64),
  created_at     DATETIME    NOT NULL,
  refunded_at    DATETIME,
  PRIMARY KEY (id),
  UNIQUE KEY uk_refund_no (refund_no),
  KEY idx_order (order_id),
  KEY idx_after_sale (after_sale_id)
);

CREATE TABLE payment_callback_log (
  id             BIGINT      NOT NULL AUTO_INCREMENT,
  order_no       VARCHAR(32) NOT NULL,
  transaction_no VARCHAR(64),
  status         VARCHAR(16),
  payload        TEXT        COMMENT '原始报文，留痕供对账与纠纷排查',
  signature      VARCHAR(128),
  verified       TINYINT     NOT NULL COMMENT '验签是否通过',
  created_at     DATETIME    NOT NULL,
  PRIMARY KEY (id),
  KEY idx_order_no (order_no),
  KEY idx_transaction (transaction_no)
);
```

**回调流水必须落库，且包含验签失败的记录**——被伪造的回调攻击是有价值的排查线索，只记成功日志等于把线索丢掉。`refund` 与 `payment` 分离，因为一次支付可以有多次部分退款。

## 六、营销域（promotion-service）

```sql
CREATE TABLE coupon (
  id             BIGINT       NOT NULL AUTO_INCREMENT,
  name           VARCHAR(128) NOT NULL,

  threshold      BIGINT       NOT NULL DEFAULT 0 COMMENT '使用门槛（分）',
  scope_type     VARCHAR(16)  NOT NULL DEFAULT 'ALL' COMMENT 'ALL / CATEGORY / SPU',
  scope_ids      VARCHAR(1024) COMMENT '适用范围 ID 列表',
  total_count    INT          NOT NULL COMMENT '发行总量',
  received_count INT          NOT NULL DEFAULT 0,
  valid_days     INT          COMMENT '领取后有效天数；为空则用绝对时间',
  start_time     DATETIME,
  end_time       DATETIME,
  status         TINYINT      NOT NULL DEFAULT 1,
  PRIMARY KEY (id)
);

CREATE TABLE user_coupon (
  id          BIGINT      NOT NULL AUTO_INCREMENT,
  user_id     VARCHAR(32) NOT NULL,
  coupon_id   BIGINT      NOT NULL,
  status      VARCHAR(16) NOT NULL COMMENT 'UNUSED / USED / EXPIRED',
  order_no    VARCHAR(32) COMMENT '使用于哪张订单',
  received_at DATETIME    NOT NULL,
  used_at     DATETIME,
  expire_at   DATETIME    NOT NULL,
  PRIMARY KEY (id),
  KEY idx_user_status (user_id, status),
  KEY idx_coupon (coupon_id),
  KEY idx_status_expire (status, expire_at) COMMENT '过期扫描'
);
```

**发券的并发安全**：`received_count` 递增用条件更新 `UPDATE coupon SET received_count = received_count + 1 WHERE id = ? AND received_count < total_count`，`affected = 0` 即"已领完"。与库存扣减同一套模式，不引入新的并发原语。

## 八、知识域（knowledge-service）

```sql
CREATE TABLE knowledge_document (
  id             BIGINT       NOT NULL AUTO_INCREMENT,
  doc_no         VARCHAR(32)  NOT NULL COMMENT '对外引用的文档编号',
  title          VARCHAR(255) NOT NULL,
  doc_type       VARCHAR(32)  NOT NULL COMMENT 'POLICY / MANUAL / FAQ / SPEC / GUIDE',
  issuer         VARCHAR(128) COMMENT '发布机构',
  version        VARCHAR(32)  COMMENT '版本号',
  effective_date DATE         COMMENT '生效日期',
  status         TINYINT      NOT NULL DEFAULT 1 COMMENT '0 停用 / 1 启用',
  file_path      VARCHAR(512),
  content        MEDIUMTEXT   NOT NULL,
  created_at     DATETIME     NOT NULL,
  updated_at     DATETIME     NOT NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_doc_no (doc_no),
  KEY idx_type_status (doc_type, status)
);

CREATE TABLE knowledge_chunk (
  id          BIGINT      NOT NULL AUTO_INCREMENT,
  doc_id      BIGINT      NOT NULL,
  chunk_index INT         NOT NULL,
  content     TEXT        NOT NULL,
  chapter     VARCHAR(128) COMMENT '章',
  clause      VARCHAR(128) COMMENT '条',
  page_no     INT          COMMENT '页码',
  char_offset INT          COMMENT '文档内字符偏移',
  vector_id   VARCHAR(64)  COMMENT 'Milvus 主键',
  PRIMARY KEY (id),
  UNIQUE KEY uk_doc_chunk (doc_id, chunk_index),
  KEY idx_doc (doc_id)
);
```

**`knowledge_chunk` 的四个位置字段（chapter / clause / page_no / char_offset）加上 `knowledge_document` 的 version / issuer / effective_date，构成引用的七元组**——这是"点引用跳原文并高亮"能成立的全部前提。缺任何一项，溯源就退化成"某份文档里说过"。

图谱实体与关系存 Neo4j，通过 `doc_id` / `chunk_id` 回指来源，使图谱推理的每一步也能溯源到原文。

## 九、状态机汇总

| 实体 | 状态 | 流转入口 |
|---|---|---|
| 订单 | CREATED → PAID → SHIPPED → RECEIVED → COMPLETED<br>CREATED → CANCELLED / CLOSED<br>PAID / COMPLETED → REFUNDING → REFUNDED | 下单 / 支付回调 / 发货 / 收货 / 定时关单 / 售后 |
| 支付 | PENDING → SUCCESS / FAILED / CLOSED | 渠道回调 |
| 退款 | PENDING → SUCCESS / FAILED | 售后审核通过 |
| 物流 | CREATED → PICKED_UP → IN_TRANSIT → DELIVERING → SIGNED | 物流轨迹推送 |
| 售后 | APPLIED → APPROVED → RETURNING → RECEIVED → REFUNDING → FINISHED<br>APPLIED → REJECTED / CANCELLED | 用户申请 / 客服审核 |
| 优惠券 | UNUSED → USED / EXPIRED | 下单使用 / 定时过期 |
| 评价 | PENDING → PUBLISHED / HIDDEN | 发布 / 审核 |

**共性约束**（全部靠条件更新落地，不靠悲观锁）：

```sql
UPDATE shop_order SET status = 'PAID', paid_at = NOW()
 WHERE id = ? AND status = 'CREATED';
-- affected = 0 → 状态已被并发请求推进，幂等吞掉，不报错
```

所有状态流转一律带**前态条件**。这是支付回调幂等、重复投递幂等、并发取消只生效一次的同一套机制，不需要额外的幂等表。

## 十一、设计要点速查（面试口径）

| 问题 | 一句话答案 |
|---|---|
| 为什么金额用分不用 DECIMAL | 浮点会累积误差，而"分摊后子项之和 = 总额"是必须成立的恒等式，整数分可以被断言 |
| 为什么价格库存挂 SKU 不挂 SPU | 挂在 SPU 上表达不了"128G 比 256G 便宜 800 块" |
| 为什么订单行存商品快照 | 商品改价改名后，历史订单必须还原下单当时的样子 |
| 为什么状态流转都带前态条件 | 支付回调、MQ 重复投递、并发取消——三种并发场景用同一套机制兜住，不需要额外幂等表 |
| 为什么售后不单独起服务 | 它和订单共享状态机、事务边界与幂等键，拆出去只会把本地事务摊成分布式事务 |
| 为什么营销单独起服务 | 券的生命周期与订单不同源——券在订单之前存在，订单结束后统计还在继续 |
| 为什么政策判定不用 RAG | 涉及金额与时间窗，模型算错就是资损；规则给结论，检索给依据，两条腿 |
| 为什么库存要流水表 | 回补失败、对账、排查缺货都靠它——原实现回补失败只能打日志，根因就是没这张表 |
