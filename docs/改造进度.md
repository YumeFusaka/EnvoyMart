## C2 · 服务间契约模块（已完成）

**起因：一次对抗评审扫出「AI 服务的商品/订单契约整体失配」——AI 输出全是 null。**
顺着查下去发现这不是一处笔误，而是<b>一套做法</b>：每个服务各自复刻一份 DTO，
字段名靠人记着对齐，Jackson 对不上时**不报错、只给 null**。

三处真实事故：

| 位置 | 表面现象 | 根因 |
|---|---|---|
| AI 商品工具 | 输出「商品名 (null 元)」，模型当事实说给用户 | 本地写 `price: BigDecimal(元)`，上游实际是 `minPrice: Long(分)` |
| AI 订单工具 | 收件人永远为空 | 本地写 `recipientName`，上游是 `receiverName` |
| 评价服务 | **评价功能 100% 不可用** | 订单行写 `productId`，上游早已改名 `spuId` |

**做法**：新增 `backend/contract` 模块，跨服务传输的 DTO 只定义一次；
product / order / payment / review / ai 五个服务依赖它。

迁移中一并清掉的重复定义：
`SkuSnapshot`×2、`StockChangeRequest`×2、`LogisticsResponse`×2、`RefundRequest`×2、
`OrderSnapshot`×2（payment / review 各自手写的「窄视图」——正是 `productId/spuId`
那个 bug 的形状，改为直接用 `contract.OrderResponse`，让编译器接管一致性）。

金额展示另加一层 `Money`（分 → 元）：工具输出是喂给模型的文本，模型会原样复述，
单位错 100 倍既不抛异常也不进日志，只能在展示层挡住。

**顺带修掉一个更严重的**：`HEAD` 上 `product-service` **根本编译不过** ——
`ProductServiceImpl:213` 用了 `Function.identity()` 却没 import（`git worktree` 建
HEAD 干净副本复现确认）。服务此前一直跑的是 IDE（Eclipse JDT）写进 `target/classes`
的旧 class，`mvn compile` 从未真正跑过这个模块。
**教训：增量编译 + IDE 后台编译会让「能跑」与「能编译」脱钩。**

**验证**：`mvn -T1C test` 全反应堆绿；新增 `ToolOutputFormattingTest`（5 条）
把「分转元」「差字段」「空结果」三类锁住。

## D1 · 引用溯源链路与拒答门（已完成）

**问题不是「没有溯源字段」，是链路每一段都在丢东西。**

`DocumentChunk` 上早就备好了 `title` / `source` / `version` / `position` / `charOffset`，
但没有任何一段代码填过它们，也没有任何一段代码读出来。四段链路各断一次：

| 环节 | 断法 | 后果 |
|---|---|---|
| 切分 `StructuralSplitter` | 只写 `chunkId` / `docId` / `content` | 溯源字段从源头就是 null |
| 入库 `MilvusVectorStore` | 元数据只序列化 `docId` + `chunkIndex` | 就算切分填了，过一次 Milvus 也没了 |
| 取回 `toChunk` | 丢掉 `match.score()` | 只剩「检索到了什么」，没有「有多确信」 |
| 下发 `convertKnowledge` | `title` 填的是 `docId`，`scope` 硬编码 `"rag"` | 引用渲染成「[1] doc_12」 |

**外加一条从来就没接上的**：售后政策表 `data.sql` 的 `doc_ref` 写的是 `KB-0001`，
而知识库文档 id 是 `after_sale_1` —— 政策引擎给出的「依据编号」点开是空的。
这条链路断在两份互不知道对方存在的文件之间，没有任何机制会发现。
现在 `KnowledgeCorpusTest` 会读 `order-service/src/main/resources/data.sql`
把两个仓库的约定对一遍，对不上就让构建失败。

**分数语义重新定过。** 融合分（RRF）刻意<b>不透传</b>：它的量纲是 `1/(60+rank)`，
第 1 名与第 5 名只差 1/60 与 1/64 —— 它是为排序设计的，绝对大小不表达相关性，
拿它当阈值等于拿名次当置信度。`DocumentChunk.score` 现在只承载跨查询可比的
相关性信号：重排分（`reranked=true`）或向量余弦相似度（`reranked=false`）。

**拒答门（`EvidenceGate`）** 三档：无召回 → 拒答；有召回但最高分低于阈值 →
只当线索、禁止下结论；达标 → 可引用。两把尺子两个阈值（余弦 0.45 / 重排 0.20），
因为两种分数的分布本来就不同。**没有相关性信号时 fail-open**：
指标缺失是链路没给信号，不是「不相关」的证据。

**语料换代。** 15 篇内联在 Java 里的短文档 → 15 篇 `resources/knowledge/*.md`
（front-matter + 正文），其中 6 篇营养/保健/特殊医学用途的长文说明书与规范。
理由不只是「偏营养医疗更好演示」：<b>上一版语料每篇不到 512 字，结构分层切分
在它上面零收益</b>——每篇恰好一片，章条下钻与位置前缀都无从触发。
换成长文后这条链路才有可观察的行为。

**验证**：`mvn -T1C clean install` 全反应堆绿。新增 23 条用例：
`EvidenceGateTest`(7)、`KnowledgePromptTest`(5)、`StructuralSplitterTraceabilityTest`(5)、
`KnowledgeCorpusTest`(6)。偏移的用例不只断言非空，而是<b>从偏移处读回原文比对</b>
——偏移算错比没有偏移更糟，用户点进去看到的是另一段话，却以为看的是依据。

**尚未做**：前端的引用卡片与「跳原文高亮」；`docRef → 文档` 的解析接口。

## D2 · 知识库成为事实源（已完成）

**D1 之后，知识库的「事实源」有两个，而且它们会各自漂移。**

语料是 Java 里的 15 个字符串常量，`knowledge-service` 启动时把它灌进
`knowledge_document` / `knowledge_chunk` 两张表；`ai-service` 启动时**另**把同一份
常量灌进 Milvus。同一份数据两条装载路径，谁也不认识谁。

这不是「重复代码」那种洁癖问题，是**三处会静默错开的具体后果**：

| 漂移点 | 症状 |
|---|---|
| 两边切分参数不一致 | 检索命中 `KB-0005_3`，点引用 404；两边日志都正常 |
| 改了语料但只重启了一个服务 | 引用卡片显示的标题/版本是上一版 |
| 库里的行被手工改过 | ai-service 不知道，索引里还是旧文 |

根因是**装载（业务数据）与索引（检索数据）被两条腿各自实现了一遍**。
做法是把知识库的归属划清楚：

- **`knowledge-service` 是知识库的唯一事实源**。语料 `.md` 降级为**种子数据**，
  只在文档不存在时插入。表里有什么，知识库就是什么。
- **`ai-service` 不再持有语料**。启动时经 `GET /knowledge/internal/corpus`（Feign + 重试）
  拉全量文档，用同一个 `StructuralSplitter.standard()` 切，建 Milvus 索引。
- **拉不到就不启动**（fail-fast）。宁可启动失败，也不要带着空索引给一个健康的 health check——
  后者会把「检索永远返回 0 条」伪装成「知识库里确实没有相关内容」，而拒答门会正常地拒答。

**切分参数漂移做成自愈的。** `seed()` 原先的判据是「这篇文档在不在库里」，
于是改切分参数后旧切片原样留着。现在比的是**重建后的切片与库里的是不是同一组**
（逐片比 `chunkId` + `content`）：文档行没变而切片对不上，只可能是切分参数改过了。
两个条件分开判——合并成一个「文档变了」会漏掉后者，而后者恰恰是最难发现的那种。

扰动验证：把 `minChars` 40 → 0，重启后 knowledge-service 重建 15 篇、348 片
（与离线预测的 348 完全一致），ai-service 跟随重建；改回 40，回到 132 片。

**`position` 有长度上限了。** 本语料把条款编号与正文写在**同一行**
（`3.2 水溶性维生素。维生素 B1 …`），而 `CLAUSE_HEADING` 匹配整行——
于是那一段几百字的正文成了「条」标签，被拼进该条下钻出的**每一个**切片的路径前缀。
KB-0016 的 3.2 一节有 700 余字，直接把 `knowledge_chunk.position` 撑爆（`Data too long`）。
现在 `label()` 截到第一个断句标点、上限 24 字。**截断不补省略号**：
位置串末段必须仍是原文对应位置的前缀，否则「点引用跳原文」的定位校验会对不上。

顺带修掉一个**会静默删正文**的写法。`withoutHeading()` 一度改成「首行像不像标题行」
就删——但长条款的标签只截了前 24 字，`3.2 优惠叠加规则：` 并不包含首行后半段的正文，
按模式删会把这半段**连同标题一起删掉**，切分器自己毫无察觉。
判据是**首行等于位置标签**（完整包含），不是「首行长得像标题」。这类长条款的标题行
留在正文里是对的：它就是这一条的开头。

**语料补第 16 篇（KB-0016 膳食营养素参考摄入量速查）。** 换成长文之后
「逐级下钻」这条分支**仍然一次都没执行过**——所有结构块都短于 512 字，
`maxChars` 在 300~512 之间完全是惰性的（实测 512/400/300 切出同样的 109 片）。
KB-0016 的 3.2 一节是一整段无分段的长文本，才真正踩到下钻。
并把这件事写成用例：`语料里两个切分旋钮都真的在起作用` —— 把旋钮拧到不可能触发的极端值
再切一遍，片数必须不同。**功能在、触发条件不在，是上一版语料栽过的坑换了层皮。**

**契约 DTO 的构造器。** `KnowledgeDocumentPayload` 加了 `@Builder` 但漏了两个构造器注解，
ai-service 侧 Feign 24 次重试后抛
`Cannot construct instance ... (no Creators, like default constructor, exist)`。
`@Builder` 生成的是全参构造，Jackson 3 不把它当 creator——**即便 parent pom 已经开了 `-parameters`**。
同包的 `ProductDetail` 早就踩过并留下了这两个注解。fail-fast 在这里起了作用：
没有让「health check 绿、索引空」蒙混过去。

**验证**：`mvn -T1C clean install` 全反应堆绿（126 用例 / 0 失败 / 5 跳过）。
端到端矩阵：

```
knowledge-service 总片数 132  ==  ai-service 索引 132 片     ← 引用回跳能成立的前提
POST /ai/internal/knowledge/reindex → {"documentCount":16,"chunkCount":132}
GET  /knowledge/documents            → 200   公开读知识库
GET  /knowledge/chunks/KB-0005_3     → 200   公开读切片
GET  /knowledge/internal/corpus      → 404   内部语料口（网关屏蔽）
POST /ai/internal/knowledge/reindex  → 404   内部重建索引（网关屏蔽）
GET  /orders/1                       → 401   对照组：未登录读订单
GET  /products                       → 200   对照组：公开读商品
```

种子幂等：连续两次 `seed()` 第二次输出「种子语料 16 篇，与库中一致，无需重建」。

**顺带修掉的启动脚本隐患**：`run-local.sh` 里与 `SERVICES` 逐位对齐的 `PORT_OF` 数组，
插入 `knowledge-service` 时忘了同步，脚本以为它在 9004（ai-service 的端口）——
**停止与健康检查全部指向别的进程**，而服务自己按 yml 绑 9008，一切看起来正常。
端口的事实源是每个服务自己的 `application.yml`，现在从那里读，数组整个删掉。
`DB_OF` 保留（库名在 yml 里是变量拼的，读不出来），并写明「改 SERVICES 顺序必须同步改它」。

**尚未做**：前端的引用卡片与「跳原文高亮」（D2 的前端部分）；`docRef → 文档` 的解析接口。

## 关键设计决策（避免后续推翻）

| 决策 | 理由 |
|---|---|
| 金额一律 `BIGINT` 存**分** | 浮点误差会破坏「子项之和 = 总额」这个必须成立的恒等式 |
| 订单行存**商品快照**（含 categoryId） | 商品改价改名不影响历史订单；政策按类目判定需要它 |
| 状态流转一律**带前态条件** | 支付回调、MQ 重复投递、并发取消三种场景用同一套机制兜住 |
| 售后政策：**规则给结论 + 知识库给依据** | 涉及金额与时间窗，模型算错就是资损；但用户需要知道「为什么」 |
| 退款三步操作**必须持有支付单行锁** | 否则并发退款各算各的，两笔各退 60% 都能过检查 |
| 验签失败的回调**也要落库** | 伪造回调是有价值的排查线索，它在校验处就中断了 |
| `@PathVariable` 一律**显式写 name** | 依赖编译期 `-parameters` 会时灵时不灵，现象是「昨天好好的今天报参数名缺失」 |
| 前端只**共用一个设计系统**（`styles/tokens.css`） | 之前 token 定义在 `main.css` 与 `App.vue` 两处且值重复 |
| 跨服务 DTO **只定义一次**（`contract` 模块） | 「靠字段名对齐」是一种编译期无提示、运行期只给 null 的约定；本仓库已因此出过三次事故 |
| 给模型看的文本**必须经过展示层转换** | 模型会原样复述工具输出。枚举名（`PAID`）与原始单位（分）都会直接变成用户看到的话 |
| 相关性阈值**不建在 RRF 融合分上** | 融合分量纲是 `1/(60+rank)`，表达名次而非相关度；阈值只建在余弦相似度与重排分上 |
| 溯源字段**随切片走完全程** | 切片一旦离开切分器，没有任何环节还持有原文；少抄一个字段下游补不回来 |
| 缺相关性信号时**放行而非拒答** | 指标缺失是链路没给信号，不是「不相关」的证据；因为工程缺陷拒答是把成本转嫁给用户 |
| 知识语料放**资源文件**而非 Java 常量 | 长文塞进字符串后 diff 全是噪音；改语料的成本应和改文本一样低 |
| 知识库**只有一个事实源**（knowledge-service 的表） | 装载与索引各持一份语料时，两边会各自漂移且**谁都不报错**；语料文件降级为种子 |
| 索引构建拉不到语料就**拒绝启动** | 空索引 + 绿色 health check 会把「检索永远 0 条」伪装成「知识库里确实没这条」 |
| 切片重建的判据是**重建结果与库里是否同组** | 只判「文档在不在」会漏掉「切分参数改了」——而后者正是引用回跳对不上号的成因 |
| 位置标签**截断不补省略号** | 位置串末段必须仍是原文的前缀，否则「跳原文定位校验」对不上 |
