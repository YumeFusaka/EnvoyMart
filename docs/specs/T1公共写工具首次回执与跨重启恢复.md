# T1 公共写工具首次回执与跨重启恢复

日期：2026-10-11。状态：**用户已批准实施，两张回执表已在实际订单库与营销库创建，代码与验收进行中**。

本文是 T1 八个公共写工具幂等与未知结果恢复的补充契约。初稿仅只读分析并落盘方案，随后用户明确批准实施及新增两张回执表。主代理已执行新增表并核对联合唯一键；下游、Agent、审批恢复分工实施，验证与提交仍按主计划执行。不得把初稿已审阅或表已创建当作功能已验收。

## 目标与边界

同一用户对同一签名动作确认、并发确认、超时重试或跨 AI/下游重启恢复，最多提交一次对应业务副作用，并取回**该次提交的原始权威回执**。业务后来变化，不改变这份历史回执。用户可以明确发起新的业务意图，新意图使用新的 operationId。

不把进程缓存、Redis 审批占位、HTTP 200、模型文字或写后列表查询作为提交证据；不以新令牌/新 operationId 重试未知操作。不改变不携带操作头的 API_ONLY 用户接口契约，不回填或修订历史业务记录。

失败分为确定性拒绝、执行中、结果未知、已提交四类。确定性拒绝不保存成功回执；执行中/结果未知不能表述为“未执行”或“已成功”。接受并提交的状态也未必意味着最终流程完成，例如订单 REFUNDING 只能称为“退款处理中”。

## 已核对事实与共同根因

- `agent-core/.../tool/ToolRegistry.java`：`operationResults` 和 `operationLocks` 都是进程内 Map；key 将 user/tool/op 与 `Map.toString()` 拼接。改变参数产生新 key，未产生参数冲突；重启清空结果；非 transient 的错误也会被缓存。默认 IDEMPOTENT 元数据不能证明下游已幂等。
- `ApprovalTokens.java`：签名包括用户、会话、完整动作参数及可选 operationId；只有 cart_checkout 被附加批次级 requestId。未配置已有 `AGENT_APPROVAL_SECRET` 时，进程随机密钥导致旧令牌重启失效，Agent 与 MCP 分别构造校验器也不能假定随机密钥相同。
- `Agent.executeApproved/runApproved` 已直接按签名动作执行，恢复这批动作不需要重新规划。但成功复合任务会接续调用模型，恢复入口必须阻止这一分支重复触发。
- `AiAssistantServiceImpl` 非流式和 SSE 都在执行前调用 `ChatHistoryStore.claimApproval`；后者把最新消息的 token 删除、状态置 CONFIRMED/DONE。相同 token 再来被拒；外层 60 秒请求号占位也可能拒绝恢复。
- `OrderClient`、`TicketClient`、`PromotionClient` 八个写方法均未传 operationId。旧 `shop_order.request_id` 全表唯一、带用户归属检查，但返回现时订单，未保存首次回执；不足以保护另外七个写工具。
- Cart add/update/remove 当前没有完整事务，add 是读后改数量；不同意图并发存在覆盖风险。领券有事务、发行量条件更新，但重复领取检查在更新锁之前，`user_coupon` 没有 `(user_id,coupon_id)` 唯一键。
- 工单 create 已将主记录与首条消息放在同一事务；售后 apply 已有交易域政策判定及申请/日志事务。售后工具的写前预检会在重放时被已有申请挡住。购物车/工单/券的写后复读会拿到后来状态或误把复读失败当作写失败。
- checkout 现有 `@GlobalTransactional` 与本地 `@Transactional`，订单创建/取消已有 Outbox。不能在它外面随意增加提前开启的本地事务，也不能把 Seata AT 分支提交误当作全局已提交。

证据均为上述本地源码和 order/promotion 的 `schema.sql`、order 的 `schema-mysql.sql`；没有读 `.env` 或查询现有数据库。

## 方案选择

采用**下游同数据库成功回执**：订单服务与营销服务各新增一张回执表，唯一认领、业务写入、JSON 回执在同一业务事务中完成。复用 Spring 事务、MyBatis/JdbcTemplate、Jackson、现有 Feign 和 Seata，无新增依赖。八个入口显式调用，不增加 AOP、反射、Filter 拦截框架。

Redis 或进程缓存方案不能覆盖下游已提交而缓存尚未保存的窗口；业务唯一键方案不能还原加购增量、删除回执、工单创建等首次结果。这两种方案均不作为权威层。业务现有唯一约束和 Outbox继续负责其既有不变量。

## 八个写动作的完整映射

|---|---|---|---|
| cart_add / AddToCartTool | order POST /cart/items | skuId，quantity 缺省归一为 1 | CartItemResponse：本次写后的行及数量、当时价格/规格 |
| cart_update / CartUpdateTool | order PUT /cart/items/{id} | cartItemId，quantity | CartItemResponse：此次目标数量对应的快照 |
| cart_remove / CartRemoveTool | order DELETE /cart/items/{id} | cartItemId | Result<Void> 成功 + receipt 元数据；工具确定性生成该 id 的 removed=true，不靠现时列表 |
| cart_checkout / CheckoutTool | order POST /orders/checkout | 收件六字段、remark、实际支持的 userCouponId；不含协议 requestId | 原 OrderResponse，保留首次金额/订单行/状态 |
| order_cancel / CancelOrderTool | order POST /orders/{id}/cancel 或 /orders/by-no/{orderNo}/cancel | 明确区分数字 id 与订单号的 locator | 原 OrderResponse；按 CANCELLED/REFUNDING/REFUNDED 等真实状态渲染 |
| after_sale_apply / AfterSaleTool | order POST /after-sales | orderItemId、type、reason、qualityIssue 缺省 false；DTO 的其他实际字段若支持也纳入 | 原 AfterSaleResponse，含申请 id、单号、政策引用和金额 |

## 操作契约与兼容性

1. Agent 写 Feign 方法新增必传 `X-Operation-Id`；普通用户控制器将它声明为可选请求头。该值只能来自服务端签名的 PendingAction，不能来自模型参数或客户端自行声明的 confirmed。MCP 同样由已验证的签名动作取值。
2. operationId 按现有生成值原样保存，允许长度 1–256 的可打印 ASCII；现有计划由最大 100 字会话号、plan UUID 与 step 组成，**不能使用 varchar(64)**。同用户唯一键是 `(user_id, operation_id)`，工具名是该键的受校验属性；把工具名/哈希塞进唯一键反而会允许同 op 换动作执行。
3. 服务端从受信身份头取用户，由显式入口确定 toolName；不接收任意 toolName。使用 `SHA-256` 对版本化的规范 JSON `{version:1,userId,toolName,parameters}` 计算哈希。按固定字段构建，递归排序对象键、保留数组顺序，数值/布尔为 DTO 真实类型，省略参数按当前 DTO 缺省归一。空字符串与 null 是否同义沿用当前字段处理，不能自行合并业务不同值。排除 approvalToken、operationId、requestId 等协议字段。不得使用 Map.toString()。
4. 同一下游库中，相同用户+op 的 tool/hash/hashVersion 不符，HTTP 与业务码均返回 409，且不触发业务调用。两库不能用各自唯一键证明跨库唯一：审批签发与执行端显式验证批次 operationId 不重复、op 与签名工具绑定，跨服务换工具在授权入口拒绝，不发送下游请求。其他用户不能查询或重放该用户回执；不同用户即使 op 字面相同也独立执行自己的授权动作。
5. 不带操作头的接口保留原 `Result<T>` body 和现有行为。带头的成功 body 仍为同一 `Result<T>`，附 `X-Operation-Id`、`X-Operation-Parameters-Hash`、`X-Operation-Receipt-Version`、`X-Operation-Replayed` 响应头。Feign 操作方法使用 `ResponseEntity<Result<T>>` 收取元数据，避免为兼容改造所有普通 API DTO。
6. 写操作 helper 必须同时校验 Result.code=200、完整匹配的回执元数据和对应 typed data（cart_remove 允许 data=null）；缺元数据、解码失败或数据缺失视为 UNKNOWN，不猜成功。回执元数据只能由完成事务的应用门面生成，不能由 controller 无条件 Result.success 拼出来。
7. 新签发的每个写动作都必须有 operationId、显式幂等策略和 acceptsOperationId=true。签发时为缺 op 的旧入口动作分配一次服务端 UUID，并签入；禁止恢复时补新 op。ReAct 当前以模型 tool-call id 组成 operationId，必须改为此次服务端捕获动作时生成 UUID，不能让跨轮重复的模型 id 吞掉用户新意图；计划路径保留已有请求 nonce。旧令牌如果没有 op，不能升级为新动作偷偷执行。
8. 新 Agent checkout 的内部 requestId 从 `SHA-256(userId + 分隔符 + operationId)` 确定性导出，长度 64，复用旧订单唯一键但不使用批次共享 requestId；它不参与业务参数哈希。普通 API 的原 requestId 机制不变，历史记录不迁移。

## 回执表与事务算法

拟议 DDL 单独放在同目录 `T1公共写工具回执-拟议SQL.sql`，**没有加入启动 schema**。订单库 `order_operation_receipt`、营销库 `promotion_operation_receipt`，字段/索引相同：自增 id 主键、user_id、operation_id、tool_name、parameters_hash、hash_version、receipt_version、response_json、created_at、completed_at；唯一 `(user_id,operation_id)`，完成时间索引用于观察积压/规模。MySQL JSON 保存完整首次 Result body，不存模型文字或现时实体引用。回执包含业务原本可能含有的地址等敏感字段，沿用同库数据权限，不写原始 token/地址到日志或证据文件。

业务事务内按以下顺序运行，回执组件不得使用 REQUIRES_NEW 提前提交认领或完成行：

```text
入口校验身份、header 和静态 DTO，构造 tool + hash
受全局锁保护的已有成功回执读取：匹配则原 JSON 重放，不符则 409
进入业务事务：INSERT 唯一认领行（response_json/completed_at 此时为 NULL）
执行一次领域业务，返回真实 DTO（删除为 null）
序列化完整首次 Result body；序列化失败也抛出并回滚
UPDATE 同行设置 response_json、completed_at；影响行数必须恰好为 1
同一次 commit 提交业务行、状态流水/Outbox、回执
事务/全局事务代理成功返回后，控制器才发成功及回执头
```

认领唯一键冲突必须退出并回滚本次事务，由**事务外门面**开启新读取事务再查询胜者回执。不能在被标记 rollback-only 的同一事务中继续 select 并返回。InnoDB 第二个 INSERT 等待第一笔锁：胜者提交则重放；胜者回滚后第二笔可重新认领执行；锁等待/死锁/提交不明返回 UNKNOWN/IN_FLIGHT，保留原 op，不能新建意图。业务自己的唯一键冲突只按业务语义处理，不能把任何 DuplicateKeyException 都当回执重放。

事务内业务异常全部向外传播，不吞为“成功 DTO”；不缓存/提交失败行。认领阶段进程退出→事务自动回滚；业务和回执已提交后响应丢失→原 op 读出原 JSON；提交阶段断连→UNKNOWN，经新连接同 op 查询/重试，由唯一键裁决。不依据当前购物车/工单列表猜最初结果。已落库但 JSON 缺失、版本不支持或 JSON 损坏是完整性错误，报警并 UNKNOWN，不重执业务覆盖坏回执。

### 现有事务边界必须守住

- checkout 的认领和 finish 放入**现有** `@GlobalTransactional + @Transactional` 方法覆盖的本地事务，而不是包在其外层早开本地事务。事务外门面只做查回执、调用事务代理、冲突后新事务重放。
- Seata AT 的一阶段提交会让本地行可见而全局仍可能回滚。这里只处理 **checkout 新回执的局部读取**：使用现有 Seata 能力的 `@GlobalLock` + `SELECT ... FOR UPDATE` 检查该回执行的全局锁，并在锁未释放时等待或返回 UNKNOWN；返回成功前必须证明全局提交已决。只有普通 SELECT 的实现不满足本契约。新行尚不可见/全局恢复中同样不能据此宣布未执行。测试必须覆盖全局回滚删除回执与全局锁持有时不得提前重放。不改造全站查询，也不新增一般性的分布式事务读框架；实际部署关闭 Seata 时按本地事务验证并明确该证据范围。
- 其余七动作认领与已有/补齐的本地事务共用连接。工单主记录+首条消息、售后申请+日志、取消状态+Outbox 都纳入同一次提交。外部库存/退款最终状态继续由现有幂等账本/Outbox负责；回执不得承诺“库存已回补”或“已退款”而交易状态尚未证明。
- Cart add 把已有行的增量改为同事务原子 SQL `quantity=LEAST(quantity+:delta,99)`，缺行 insert 用现有 `(user,sku)` 唯一键竞争后执行同一原子累加；update/remove 用用户归属条件及必要行锁，避免“旧对象 updateById”覆盖并发新值。响应快照在持有相应行锁期间装配，序列化失败回滚。
- coupon receive 在已有 coupon 模板行 `SELECT FOR UPDATE` 后检查当前用户是否已领，再条件扣发行量并插入券。由模板行串行化同券竞争，无需改 user_coupon 历史索引或去重旧数据。不同 op 重复领券仍按现有业务拒绝；同 op 已成功则在资格/重复检查前取回回执。
- AfterSaleTool 的写操作不再用执行时预检挡在回执读取前；确定性流程保留预览，实际资格始终由领域 apply 在**认领后且仅首次执行**判定。所有写后复读仅供额外现时展示；其失败或现时状态差异不能覆盖已提交原回执。

## 审批批次恢复与前端交付

Redis 继续管理授权/交互状态，数据库继续管理副作用回执；两个角色不互相冒充。`ChatHistoryStore.claimApproval` 改成基于原消息与 token 指纹的原子状态转换，保留原签名载荷，不能执行前标记 DONE。授权账本键取 `(user,session,sha256(token))`，保留原 messageId/turnId、原 token、acceptedAt、ownerNonce、leaseUntil、阶段及每个原 op 的结果状态；存续期沿用历史七天，不添加未公开用户设置。

| 审批阶段 | 相同原 token 的行为 |
|---|---|
| PENDING | 验签/用户/会话/有效期及当前待确认消息匹配，原子接受→IN_FLIGHT；登记 acceptedAt 和 lease |
| IN_FLIGHT（租约有效） | 返回“处理中”状态，可读既有回执；不启动第二个批次，不更换参数 |
| UNKNOWN 或 IN_FLIGHT（租约过期） | 获取新租约，按签名中**原工具、原参数、原 op**查/重试；下游唯一键为最终裁决 |
| CONFIRMED | 从下游原回执恢复这批结果；没有模型调用，不重新续作旧复合任务 |
| DISMISSED / CANCELLED | 不执行任何未开始动作；只允许查看已提交动作回执；不能把用户停止解释成继续同批任务 |
| REJECTED（确定性业务拒绝） | 显示本次拒绝，不保存权威失败回执；原授权仍有效且用户明确重试时，可用同工具/同参数/同op重新判定。改变参数或意图必须重新确认，不能用新op偷偷重发原未知操作 |

租约内部常量必须覆盖正常批次执行时间，并可由进行中执行续租；过期抢占不承诺原进程已停止，因而仍依赖下游唯一键。租约 owner 校验防止旧执行者覆盖新状态。进程退出、断流、记录历史失败、未知工具结果均不得销毁授权批次。已接受批次不能因“最新消息变了”失去结果恢复入口。恢复失败保留 UNKNOWN；失败结果不进入 ToolRegistry 权威缓存，建议删除写工具的两张无限 Map，所有写结果直接交下游裁决。

批次按签名顺序逐项恢复：已有回执项只读重放；第一项未知或被拒即停止本轮，后续未开始项保留原载荷，不跨过依赖继续写。下一次恢复重复读取已成功项并处理第一项未完成动作，不复制已完成操作，不重新绑定 `$N` 或重新问模型。数据库回执证明的项才记为成功；所有已批准项取得确定结果后，批次阶段才能离开 IN_FLIGHT/UNKNOWN。用户取消后只读恢复已提交结果，绝不执行后续未开始项。

首次签名过期且从未接受的令牌不能发起写调用。新签名包含接受后恢复时长 `r=86400`，已接受且未取消删除的批次，必须同时核验原 token 的签名、用户/会话、持久化 acceptedAt 与 recoveryUntil；24小时内明确继续确认才允许沿原工具、参数和 operationId 重试未完成项，不扩充动作。老签名没有 `r` 时仍只在原签名期限内允许继续写。执行租约30秒，续租不延长恢复授权；过期 owner 不得续租或发布新卡，慢调用仍可能在下游结束，由数据库回执避免同操作重复。Redis 授权记录丢失/不可读时，允许经单独**只读回执查询**恢复已有成功结果，不能凭过期签名对没有回执的动作重新写。没有记录和回执即“无法证明已执行/未执行”，不得换令牌自动补写。原签名验签失败永远拒绝，不能放宽为只比 token 字符串。完整期限契约与证据见 [审批恢复授权与医学可见事实核验](T1审批恢复授权与医学可见事实核验.md)。

需要显式增加下游用户隔离的回执查询接口：order `GET /orders/internal/operation-receipts/{operationId}`，promotion `GET /coupons/internal/operation-receipts/{operationId}`，用 Spring 已有 URL 编码工具编码含冒号的 op，并通过内部认证头；返回原 Result 与回执头或明确 NOT_FOUND。查询参数含期望工具/哈希，由应用层白名单校验，不能泄漏其他用户回执。现有网关内部路径规则已经覆盖这两个前缀，仍补契约测试禁止外部用户直访。

AiAssistantService 对携带原 token 的恢复分支使用 batch 身份，不能让外层 transport requestId 占位阻止它；普通问答请求号幂等不变。增加显式恢复路径/模式（`POST /ai/sessions/{sessionId}/approvals/recover`，body 仅原 token；没有模型 message），由该服务/Agent 共享的确定性执行方法完成；模型的 continuation 只允许首次成功正常执行分支，不在恢复入口运行。SSE 重放发送规范 done 帧和结构化状态，不伪造模型流。

前端保留原确认卡与 token/messageId，点击后变“处理中”，未知结果显示“结果待确认”和“恢复结果”，不把 token 清除并把按钮永久禁用；重载会话恢复同一状态。UI 既有取消语义按上述 CANCELLED执行。历史写入只更新对应原消息的状态与结果，不新建一次意图；保存 tool/op/result 状态，敏感 token 只在原授权记录内，不进日志或 eval 证据。

已有 approval-secret 配置需要跨进程稳定，MCP 与 Agent 注入同一 ApprovalTokens 校验器；启动时只报告配置是否就绪，不读取/输出密钥内容。生产缺失时必须阻断有恢复保证的写能力并报告原因，不能偷偷生成随机密钥并宣称跨重启可恢复。配置已有，本文不增加设置或修改环境；若本地实际缺失，按用户规则另行请求配置授权。

## 存量、上线与回滚

1. 两张新表为空，不迁移/回填已有购物车、订单、售后、工单或券。旧业务行无法证明原始回执，不能根据当前状态合成过去回执。旧 token/无 op 的未知操作不自动重写，明确返回无法安全恢复的边界。
2. 下游先部署支持操作头/回执的版本，AI 后部署强校验版本。AI 发出操作头但下游没有回执元数据视为 UNKNOWN，不能降级无头重新写。暂停旧 Agent 写确认并保留待恢复队列，避免混合版本执行绕过回执门；只读与 API_ONLY 原功能可继续。
3. 迁移仅新增两张表。创建前检查当前配置实际目标库与表是否存在；若已有同名表，比较字段/唯一键/引擎，禁止 IF NOT EXISTS 隐藏不兼容结构。generic schema.sql 提供 H2 同构 JSON 表；新 MySQL 库须在服务启动前按已批准 SQL 创建具有 binary collation 的回执表。启动只读检查列长度、JSON 类型、binary collation、联合唯一键与 InnoDB，不自动修表。H2 JSON 绑定使用 UTF-8 字节避免把对象双重编码为字符串，MySQL 仍按 JSON 文本绑定；MySQL 并发/Seata 验证不可用 H2 替代。
4. 回执不设置业务 TTL、不自动删除，避免记录过期后同一 op 再次产生副作用；容量/归档需要另行数据保留决策，不能为缩表破坏契约。
5. 回滚仅撤回本次代码，**保留两张表及全部数据，不 DROP，不删除业务/审批历史**。回滚时停止 Agent 新写执行，避免旧缓存链路接管未知原 op；保留原 token/op 供升级恢复。API_ONLY 原接口不依赖新头仍可运行。回滚没有破坏性历史数据操作。

新真实脚本的 `--matrix=eight-writes` 必须包含八工具，每项有 SERIAL、CONCURRENT、LOST_RESPONSE_RESTART 三组断言。不默认触发模型；原审批setup与失响应恢复可走独立测试账号，必要的首轮模型调用严格按既有真实验收额度。新脚本缺受审本地故障控制模块、运行目标不是持久化MySQL、未证明secret稳定或当前仍有连续重启验收占用时，明确 BLOCKED，不假跑PASS。MySQL/Seata实验安排在正在运行的故障验收结束、实施与结构变更获批后，使用已批准的本地控制适配器；不自动安装/启动服务。

脚本当前提供 `--capture` / `--compare` 两模式，不调用模型、不自动重启、不自动删除测试账号或记录。capture 注册两个隔离账号，捕获八写首次回执及购物车/订单/券/工单/售后的权威状态；并发覆盖加购、工单、领券，修改现时购物车/工单/订单/售后状态后仍要求原回执摘要稳定，另验哈希冲突、用户隔离、无操作头普通API、失败后同op纠正输入。公开证据路径为 `frontend/.evidence/write-operations-<runId>.json`，仅保存请求号、回执/状态摘要及脱敏业务数据；随机测试账号登录凭据与精确请求载荷只放同目录 gitignore 的 `.private.json`，不输出或提交。

compare 使用 capture 的原 op 和参数重放，检查原 JSON 摘要一致且权威状态不新增副作用；capture 不完整或存在失败时拒绝比较成 PASS。联合重启证据必须形如 `{services:[{service:"order",beforePid:123,afterPid:456,afterReady:true},{service:"promotion",beforePid:789,afterPid:901,afterReady:true}]}`，两服务 PID 均需真实变化；缺证据时联合重启为 BLOCKED。脚本本身**不模拟或声称丢响应已验收**，LOST_RESPONSE_RESTART 仍由主代理故障控制专项按下一段完成。售后前提使用已存在的模拟支付开关和管理员发货/收货 API；前提不可用时保留失败，不自动改配置。

真丢响应必须由可审的测试代理**完整转发一次请求、取得下游已提交成功响应、在回传AI前主动断开/丢弃响应**，不能用“请求没发出去”或before-call抛错代替。持久化记录仅保存user匿名标识、op/hash、首次response摘要，不落原token/手机号。然后真实重启AI及对应order或promotion，使用客户端仍持有的**原 token**恢复；校验回执同一id/JSON摘要及R1副作用不变。提交前kill另设一组：确认认领与业务全部回滚，相同原op恢复只能执行一次。Seata专项另按R7证明全局未决门。

可观测日志必须有 requestId、脱敏user、tool、operationId、hashVersion、receiptVersion、replay/claim/rollback/conflict/inFlight/unknown、耗时和业务状态摘要；不能写完整参数、签名token、地址或密钥。指标分别统计回执重放、参数冲突、未知结果和全局锁等待，不以总成功率掩盖UNKNOWN。

## 当前设计验证与剩余风险

审批恢复接口已落地为 `POST /ai/sessions/{sessionId}/approvals/recover`，body 只含 `approvalToken` 和显式 `retry`：缺省 false 只查询首次回执；true 表示按原参数继续确认，要求原接受账本、未取消、有效期与租约仍允许。过期原 token 保留验签后的只读查询；正常聊天重复同 token 不自动重试已接受批次。返回 `approvalStatus/approvalRetryAllowed` 与原消息身份；工具轨迹返回 `operationId/operationState/receiptReplayed`。

授权账本使用 `chat:approval:{user}:{session}:{sha256(token)}` HASH 的 `record` 字段保存完整批次，CAS 比较整份记录避免字段拼装的中间态。原子接受校验原消息、墓碑与账本不存在；15 分钟租约每个动作前续租；旧 owner 不能完成新 owner 的批次。已提交步骤先查询权威回执，恢复不续作模型任务；第一项非 COMMITTED 停止后续。完成/观察只更新原 messageId 且再次校验原 token 与账本，未知和取消保留原授权及每次结构化结果。
