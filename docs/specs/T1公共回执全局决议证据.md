# T1 公共回执全局决议证据

日期：2026-10-11。状态：设计与实现中，尚未执行迁移或完成真实 TC 验收。

## 契约与边界

成功回执必须同时证明业务事务写入成功及其所属全局事务已经成功决议。`response_json` 完整、本地阶段提交、全局锁暂时可取得，都不能独立证明成功。原回执 JSON、协议四响应头和版本 1 不变。

两张已有回执表新增可空 `global_xid` 和 `decision_mark`。认领时由服务端读取受信 Seata `RootContext`，不接受客户端 XID 参数。无 XID 的新本地事务标记 `LOCAL`；有 XID 的事务标记 `GLOBAL_PENDING`。TC 成功核验后可标记 `GLOBAL_COMMITTED`，该标记不豁免后续权威检查。

公共模块只定义决议检查端口，不依赖 Seata。订单与营销服务分别通过现有 Seata 依赖调用官方 `GlobalTransactionContext.reload(xid).getStatus()`，并只读检查自身 `undo_log` 中该 XID 的剩余记录。

只有 TC 明确 `Committed`，或 `Finished` 且该 XID 已无待结算 undo、成功回执行仍在，允许重放。`Begin`、`Committing`、`AsyncCommitting`、回滚中、回滚失败、未知、TC 不可达、undo 仍存在都返回结果未知。TC 明确回滚但成功行仍在，按完整性异常处理，禁止重放成功。

事务内 `commit()` 仅返回草稿。首次 HTTP 成功必须在业务和全局事务代理返回之后调用 `OperationReceiptService.verifyCommitted(operation, type)`，核验成功后才构造协议响应。不得在原全局事务内部核验其最终状态。

## 存量与迁移

新列均可空，不修改任何原始回执 JSON。历史 `global_xid=NULL、decision_mark=NULL` 的普通本地工具回执保留兼容；旧 `cart_checkout` 缺少 XID，无法证明原全局事务成功，查询返回未知，不自动重写业务或换操作号。

只允许对本任务已定位的订单回执 39，在主代理核对原用户、操作号、回执行与可信 undo 的精确 XID 后定向补充事务来源；未核对前不执行补充 SQL。其他旧结算回执不得猜测或批量回填。

迁移 SQL 见同目录 `T1公共回执全局决议迁移.sql`。回滚应用代码时保留新增列与证据，不删除 undo 或 TC 存储；涉及重新暴露旧不安全写链路的应用回滚须由主代理维持交易维护边界。

## 验收证据

- 完整成功 JSON 但 TC 未决、失败或不可达：确定性回归必须拒绝 `COMMITTED`。
- TC 成功但本 XID undo 未结算：确定性回归返回未知；无 undo 且成功行存在才允许重放。
- 明确回滚却成功行存在：确定性回归拒绝并报告完整性异常。
- 旧结算缺 XID、新本地 `LOCAL`、其他旧本地工具：逐项兼容性回归。
- 参数哈希冲突与用户隔离：沿用原回执回归；TC 检查不能改变首次 JSON。
- 真 MySQL/TC：未决、提交、回滚及跨服务重启联合验收；单测与本地事务替身不能替代真实终态证据。

## 风险

TC 查询是必要的权威依赖，不可达时必须降为未知，不能以数据库可读代替。全局事务终态与本服务 undo 清理可能存在时间窗口，窗口内返回未知，用户按原操作号查询恢复。有限真实样本不证明所有并发时序均正确。
