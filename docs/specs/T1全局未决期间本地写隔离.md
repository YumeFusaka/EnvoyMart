# T1 全局未决期间本地写隔离

日期：2026-10-11。状态：方法级增强与外层回执锁已修复，20:01:26 Java21真实parser/adapter及相邻回归36项通过；真实AT阶段一和旧失败事务恢复待主代理统一部署验收，原TYPE失效FAIL保留。

## 根因与边界

真实失败 XID 尾 6959 的阶段一本地提交已被普通本地写修改，导致 AT after-image 校验失败。AT 的物理行锁在阶段一提交释放；未使用全局锁校验的普通 UPDATE 可以修改未决行。购物车还有第二种问题：结算删除旧主键后，同用户同 SKU 新插入使用新主键，无法由旧购物车 PK 全局锁保护。

本改动覆盖 StockServiceImpl、ProductAdminServiceImpl、CouponServiceImpl、CartServiceImpl、OrderDomainServiceImpl，以及 OrderAdminServiceImpl 和 AfterSaleServiceImpl 的订单写入入口。Outbox和成功回执由独立改动覆盖；不清理原失败事务、undo 或用户数据，不增加配置开关。

## 契约和方案

1. 商品库存/管理、营销、购物车与订单所有本地事务入口显式使用方法级GlobalLock，禁止以TYPE标记代替实际方法增强。已有XID时仍登记AT，无XID时本地提交校验写入行全局锁。Seata2.5 parser只读取class GlobalTransactional及METHOD GlobalTransactional/GlobalLock，并按methodsToProxy过滤调用；TYPE GlobalLock即使可反射读出也不能证明入口被增强。GlobalTransactional优先于GlobalLock，本地事务取连接和提交都须被方法级拦截上下文覆盖。
2. 订单的取消、支付推进、发货、签收、轨迹补录，必须在业务判断和跨服务副作用前SELECT FOR UPDATE订单行，启用方法级GlobalLock。回执commit外层也必须方法级GlobalLock：其本地事务在内层业务方法之前就取连接，无全局上下文时SeataAutoDataSourceProxyAdvice会返回raw连接，不能等内层再绑定标志。未决订单不得触发退款、回补、退券或事件登记。保留状态条件UPDATE及归属约束。
3. 批量关单与自动完成只扫描候选 ID；通过 ObjectProvider 获取自身 Spring 代理，每单执行独立事务。每单锁读后复查状态与期限；失败记录订单 ID 和异常类型并继续，不得因后一单冲突回滚前一单本地状态但保留已发生远端动作。
4. 新增 order_user_trade_guard(user_id 主键、revision)。首次建闸是永久基础设施元数据：独立无XID/无GlobalLock线程通过新自动提交连接，先非锁查询存在性，缺行则原子 INSERT ... ON DUPLICATE KEY UPDATE user_id=user_id，仅创建revision=0，不覆盖已有revision。所有购物车写和checkout在原业务事务锁读稳定用户PK、推进revision；AT仅登记revision UPDATE，同业务一起回滚。checkout必须在幂等订单/购物车读取前进入，无XID写在锁读时验证全局锁，不能换cart_item主键绕过。业务失败后允许保留revision=0的元数据闸行。无删除、租约、TTL或外部守锁服务。
5. MySQL 闸表采用 varchar(32) CHARACTER SET ascii COLLATE ascii_bin、InnoDB；H2 schema 使用等价大小写敏感 varchar，只用于真实本地事务并发测试，不能作为 Seata/MySQL 证明。存量用户惰性建立闸行；不回填或改写旧业务记录。
6. 已经结束但回滚失败的 XID 可能释放全局锁并留下订单，因此单靠 GlobalLock 不够。shop_order 新增可空 global_xid，checkout 保存真实 ROOT XID；当前同 XID 允许内部返回草稿，其他调用必须通过共享 SeataOperationReceiptDecisionProbe 的 TC Committed/Finished 与本库 undo=0 证明。未决、失败、不可达均拒绝读取为有效订单或产生远端副作用；NULL 兼容历史本地订单。原751的可信属性补录由恢复审计独立处理，本改动不回填历史。
7. 售后写按订单→售后固定锁顺序，锁读当前售后版本后才判状态、回补或退款。管理备注也锁读订单并验证创建事务；不在退款后的私有投影位置才补锁。

## 风险与回滚

锁等待遵循已有 Seata 有限重试策略，不新增用户不可见行为配置。全局锁不可获得必须拒绝写并保留原业务状态。用户闸让同用户购物车写串行，这是交易一致性的边界；不同用户独立。存在失败回滚存量时禁止未经核对部署后直接重放原数据。本改动不能修复既有 dirty undo，只防止新 dirty 写入。

TC 失败终态是否保留全局锁已由主代理实证：18:37:48 的 TC 日志对 XID 尾6959（TimeoutRollbackFailed）仍报告 order_operation_receipt:39 全局锁被该 XID 持有，GlobalLockQueryResponse.lockable=false。用户闸沿用同一 AT 资源锁规则，维持两字段，不增加 lastXid、TTL 或设置项。订单与回执另以持久 global_xid 和权威 TC/undo 判据防止锁已释放或事务状态不可确认时误认成功。

回滚保留闸表和数据，不 DROP；停止新写、等待活动 XID 决议后可撤回源码。不在持有未决事务期间切回无锁版本。编译/重启与真实实验由主代理统一协调。

## 冷行死锁复审与修复

只读评审发现初版先锁读缺行、再INSERT存在InnoDB gap-lock死锁：同用户两个首次写请求均可持有缺失键gap锁，插入时互等。真实隔离表实验确定性复现ERROR1213；此前H2八并发预先建立闸行没有覆盖此入口，原门禁不删除、不冒充新修复证明。

不能直接在AT连接换INSERT IGNORE：Seata2.5普通InsertExecutor即使受影响0也构造after-image和INSERT undo，可能误将旧闸行作为新插入回滚删除。ON DUPLICATE UPDATE执行器又在beforeImage中先FOR UPDATE，冷行仍有gap问题。因此元数据认领完全脱离Seata和业务事务，业务只锁读已有行并更新revision。独立非锁查询也避免在业务REPEATABLE READ事务过早建立快照、使结算读到上一笔已删除的购物车。

同用户并发准备合并为一个在途任务，不建立无界用户缓存；执行结束才移除合并项，超时调用方不得提前移除仍在借连接的任务。准备最多等2.5秒，SQL最多2秒；超时/连接不可用/关闭均fail-closed，中断工作线程，不进入业务锁/写入。已有业务事务可能已经占池连接，准备仍需独立连接；池完全耗尽时可拒绝本次写，不能改成借用原AT连接、无限等待或绕过元数据。独立连接用try-with-resources释放，服务关闭中断准备线程。无新增用户配置或池参数。
